# ISEKAI portal — UDP サイズ契約と経路移行時の PMTU 保持

実装計画。対象は `seera-msquic` / `isekai-p2p` / `portal-core` / `portal-client` /
`portal-server` と `docs/portal.md`。

---

## 0. 何を決めたか

portal が UDP フォワードのサイズについてアプリに与える契約を、いま暗黙に置かれている
「約 1200 バイト」ひとつから、明示的な二段に置き換える。

| | 内容 |
| --- | --- |
| **契約 A** | 接続が生きている限り必ず通るサイズ。経路にも時間にも依存しない定数 |
| **契約 B** | 実効上限は PMTU に応じて上がる。**下がることはない** |

契約 B は、パスが切り替わっても実効上限を維持するという約束であって、上限が上がることの
約束ではない。上がるかどうかは経路次第で、上がらなくても契約は破れていない。

この二段構成には、契約 A の側にも変更が要る。現在 `docs/portal.md` に書かれている
約 1200 バイトという数字は、内側 QUIC のパケットオーバーヘッドと portal 自身の
セッションヘッダを勘定に入れておらず、**実際より約 46 バイト大きい**。契約として提示する
前に直す必要がある。

---

## 1. 前提として確定していること

### 1.1 構成

- 内側 QUIC（peer connection）は、リレー経路では外側 QUIC の CONNECT-UDP
  トンネルに載り、直接経路では素の UDP で流れる。**移行するのは内側**。
- 外側 QUIC は `MinimumMtu = 1350`。ハンドシェイクのデータグラム自体がこのサイズまで
  padding されるため、外側の接続が成立した時点でこのサイズの疎通は経路上で証明済み。
  結果として、**リレー経路の内側 MTU は 1248 を常に満たす**。
- MsQuic は fork / upstream ともに **MTU はパス単位、データグラム最大長は接続単位**。
  接続単位の値はどこかのパス（優先パス）から導かれるため、優先パスが動けば動く。
- 内側は現在 `MaximumMtu = 1248`（`QUIC_DPLPMTUD_MIN_MTU` の clamp 下限と同値）。
  両パスが同じ値に張り付いているため、上限が経路で変動する問題が今は表面化していない。
  これは設計上の保証ではなく clamp の副作用である。

### 1.2 算術

内側 QUIC の `MaximumMtu = 1248`（IP レベル）に対して:

```
  内側 MaxUdpPayloadSize      1200          IPv6 前提。IPv4 なら 1220
  − QUIC パケット + DATAGRAM   -42 (仮)      要実測。§2.1 参照
    フレームのオーバーヘッド
  = DatagramMaxSendLength     1158
  − portal の [u32 session]     -4
  = アプリに提示できる payload 1154
```

保証値は最悪ケースで置くべきなので、IPv6 前提の 1200 を起点とする。IPv4 の接続では
20 バイト余るが、それは契約に載せない。

**42 は暫定値**。外側の接続で実測した数字であり、内訳に 18 バイト前後の CID を含む。
内側の CID 長は `isekai-p2p` が決めるもので同じとは限らない。

## 2. 責務の割り当て

### 2.1 `seera-msquic`

**責務: サイズを条件としたパス検証を提供する。上限の維持そのものはやらない。**

1. **サイズ付きパス検証**（draft-seemann-quic-ppdplpmtud §6 相当）
   候補パスの検証時に、`PATH_CHALLENGE` / `PATH_RESPONSE` / `NEW_CONNECTION_ID` を
   PADDING で指定サイズまで膨らませて送る。応答が返れば、そのパスがそのサイズを通すことが
   検証と同時に確定する。
   - API: `ADD_PATH` に要求サイズを渡すか、`QUIC_PARAM_CONN_PATH_REQUIRED_MTU` を新設。
     既存の 5 つの追加 API（`ADD_PATH` / `REMOVE_PATH` / `ACTIVATE_PATH` /
     `ADD_BOUND_ADDRESS` / `REMOVE_BOUND_ADDRESS`）の並びに素直に入る。
   - 必要なのはサイズ探索ではなく **現在値 1 点での可否判定**。プローブは 1 本で足りる。
     draft の並列プローブ機構をフルに実装する必要はない（フェーズ 3 参照）。
2. **要求サイズを満たさないパスをアクティブ化しない**
   検証は通ったがサイズが足りない場合、パスは候補のまま残し、`ACTIVATE_PATH` は
   失敗を返す。アプリに判断を返すのがここの仕事で、勝手に終了させたりリレーへ戻したりは
   しない。
3. **パス単位の確定 MTU の公開**
   各パスについて、検証済みのサイズをアプリから読めるようにする。
4. **`MaximumMtu` の引き上げを受け入れる**
   1248 → 1500。clamp は下限側のみなので上げること自体に変更は要らないが、
   パス間で MTU が分岐した状態が初めて常態になるため、接続単位のデータグラム最大長が
   どのパスから導かれているかを確認しておく。

**やらないこと**: 上限の単調性を msquic 側で強制する。接続単位の値を「下がらない」ように
書き換えるのは侵襲的で、かつ実際に狭いパスへ大きいパケットを送りうる。単調性は
「狭いパスをアクティブ化しない」ことで上位が担保する。

### 2.2 `isekai-p2p` / `isekai-p2p-core::transport`

**責務: 契約 B のポリシーを実装する唯一の場所。**

1. **内側接続の MTU 設定**
   `MinimumMtu = 1248`（リレー経路で成立する必要があるため上げられない）、
   `MaximumMtu = 1500`。
2. **移行判断**
   直接経路の検証時に、現在の確定データグラム最大長を要求サイズとして渡す。満たせば移行、
   満たさなければポリシーに従う:
   - `stay-on-relay` — 移行せず、候補パスを捨てる。リレー経路を使い続ける
   - `end-session` — セッションを終了する
3. **`PathRemoved` の扱い**
   直接経路が確立後に死んだ場合、リレーへの復帰が「下げる」に当たるかを判定する。
   - リレー経路は外側 `MinimumMtu = 1350` に守られているため **1248 は常に満たす**。
     直接経路で 1248 を超えて上がっていなかったなら、復帰は無害で契約 B を破らない
   - 上がっていた場合のみ、復帰は契約違反になる。セッションを終了する
   この分岐は `--on-path-downgrade` フラグの対象外である（フラグは移行判断時の選択で、
   これは事後の落下）。設計として常に終了とするか、フラグを共用するかは §5 の未決事項。
4. **確定サイズの単一の窓口**
   `portal-core` が読むのはこの値ひとつ。MsQuic の接続単位の値を直接読ませない。
5. **MTU floor 定数と算術**
   §1.2 の導出をコメントとして残す。外側 1350 → 内側 1248 の連鎖は、片方だけ直すと
   静かに壊れる種類のものなので、根拠を数式ごと書く。

### 2.3 `portal-core`

**責務: 契約 A の定数を持ち、両契約をワイヤ形式の上で正しく計算する。**

1. **契約 A の定数**
   `1200 - overhead - 4 = 1154`。overhead は `isekai-p2p` から取得した実測値で、
   定数にハードコードしない。導出をコメントに残す。
2. **`[u32 session]` の 4 バイトを勘定する**
   現在の上限計算はこれを引いていない。契約 A・B の両方に効く。
3. **超過データグラムの扱いは現状維持**
   落として数える。分割しない。上限が上がっても状態を持たず、単に通るようになるだけ。
4. **カウンタの分離**
   契約 A を超えたもの（アプリの誤り）と、契約 A は満たすが現在の実効上限を超えたもの
   （経路が狭い）を別に数える。後者は契約 B が効いていれば直接経路の確立後に止まるはずで、
   止まらなければ設計かパスのどちらかが疑わしい。

### 2.4 `portal-client`

1. **フラグ `--on-path-downgrade {stay-on-relay|end-session}`**
   既定は `stay-on-relay`。理由: 黙って遅くなる方が、黙って落ちるより既存の利用と整合する。
   `end-session` は、リレー経由の往復を許容できない呼び出し側のためのもの。
2. **ログ**
   接続時とパス確定時に、契約 A の値と現在の実効上限の両方を出す。
   `--map` の行に添えるのが素直。

### 2.5 `portal-server`

追加の責務なし。上限はクライアント側の接続で決まり、サーバはサービスカタログの判断に
専念する。ログに実効上限を出す点だけ揃える。

### 2.6 `docs/portal.md`

1. 「約 1200 バイト」を **1154** に修正する。現在値は誤りである旨を変更履歴に残す。
2. 二段契約を説明する節を追加。「上限は上がるが下がらない」を明示する。
3. DNS の節を書き換える。契約 A の 1154 は EDNS0 の一般的な 1232 バイトに届かないが、
   契約 B により直接経路が立てば 1232 を超え、以後下がらない。
   「大きい応答は常に落ちる」から「直接経路が立つまで落ち、その後は通り続ける」への変化を
   書く。これがこの設計の一番分かりやすい見返りである。

## 3. フェーズ

### P0 — 実測（コード変更なし）

- 内側接続の `DatagramMaxSendLength` と `MaxUdpPayloadSize` を実際に読む
- 内側の CID 長を確認し、42 という数字を確定させる
- 接続単位のデータグラム最大長が優先パス切り替えでどう動くか、直接経路への移行前後で観測する

**P0 の結果で 1154 が動く。以降のすべてがこの数字に乗るので、ここを飛ばさない。**

**結果は §6 に記録した。P0 は完了。**

### P1 — 契約 A のみ

- `portal-core` の上限を実測値に直す（`[u32 session]` の 4 バイト込み）
- カウンタを分ける
- `docs/portal.md` を修正
- `MaximumMtu` は 1248 のまま、`isekai-p2p` の移行判断も現状のまま

P1 単独で意味がある。現在の上限が大きすぎるという既存の不具合が直り、契約 B に
進まない判断をしてもここまでは残る。

**P1 は完了。** 上限は 1163 に、カウンタは `oversize` と `refused_too_big` に
分かれ、`docs/portal.md` は算術ごと書き直した。定数は `isekai-p2p` の
`PEER_MTU` / `DATAGRAM_OVERHEAD` / `GUARANTEED_DATAGRAM` から導かれ、portal 側に
数字は残っていない。`refused_too_big` はループバックでは踏めない — v4 経路の実効
上限 1187 が portal の 1167 を上回るためで、これは floor が効いている証拠である。

### P2 — 契約 B

- `seera-msquic` にサイズ付きパス検証を追加（§2.1 の 1〜3）
- `isekai-p2p` に移行判断とポリシーを実装（§2.2 の 2〜3）
- 内側 `MaximumMtu` を 1500 に
- `portal-client` にフラグを追加

### P3 — 並列プローブ（任意）

直接経路で 1500 までを速く見つける部分。draft 本体の実装にあたる。P2 では逐次
DPLPMTUD が数 RTT かけて登るのに任せてよく、契約 B は P2 の時点で成立している。
スループットの最適化であって正しさの要件ではない。

なお draft-seemann-quic-ppdplpmtud は **-00 の個人提出で WG 採択前**。新しいフレームも
トランスポートパラメータも要らず片方向で独立に動くため、fork に入れても相互運用上の
リスクはないが、仕様が動く前提で読む。

## 4. テスト

| 対象 | 内容 |
| --- | --- |
| 境界 | 1154 ちょうどが通り、1155 が落ちて数えられる |
| IP バージョン | IPv4 / IPv6 の両方で契約 A が 1154 で一定 |
| リレーのみ | 直接経路が張れない接続で、実効上限が接続の生涯を通じて変わらない |
| 狭い直接経路 | `stay-on-relay` でリレーに留まること、`end-session` で終了すること |
| `PathRemoved` | 直接経路で上がった後に落ちた場合の終了。#165 と同じ再現の難しさがあり、テスト用に強制的に落とす経路が要る |
| 単調性 | 接続の生涯を通じて、実効上限が一度も減少しないことを観測する |

`PathRemoved` の再現手段は P2 の中で用意する。契約 B を明文化したことで、#165 が
「未検証の分岐」から「契約の履行を確かめる唯一の手段」に変わっている。

## 5. 未決事項

1. **42 の実測値**（P0 で決着）。1154 が動く。
2. **`PathRemoved` 後の落下をフラグに含めるか**。移行判断とは別の事象なので、
   常に `end-session` とするのが契約 B に忠実だが、フラグを共用する方が説明しやすい。
3. **直接経路の `MaximumMtu` を 1500 とするか、ローカル I/F MTU に従うか**。
   draft は探索上限を `min(1500, ローカル I/F MTU)` と定めており、これに合わせるのが素直。
4. **UDP フォワードの開始タイミング**。契約 B は上限が上がることを許すため、フォワードの
   途中で上限が変わる。アプリから見て上がる分には無害だが、フォワードの生涯を通じて
   固定の値を提示したいなら、直接経路の確定を待ってから開くという選択もありうる。
   計画書によれば切り替えは検証の 276µs 後、フォワード開始前に起きるので、実際には
   ほぼ差がない可能性が高い。P0 の観測で判断する。

## 6. P0 の結果

再現手段: `cargo run -p portal-core --example mtu_probe`。ループバックに本番と同じ
`peer::client_config` で接続を張り、msquic が言う値を読む。

### 6.1 オーバーヘッドは 42 ではなく 33

実測 33。ソースからの導出とも一致する:

```
MIN_SHORT_HEADER_LENGTH_V1   5   (QUIC_SHORT_HEADER_V1 1 + パケット番号 4)
CID                          9
DATAGRAM_FRAME_HEADER_LENGTH 3
CXPLAT_ENCRYPTION_OVERHEAD  16
                            ──
                            33
```

**CID 長は 9。** `MsQuicLib.CidTotalLength = CidServerIdLength + QUIC_CID_PID_LENGTH
+ QUIC_CID_PAYLOAD_LENGTH` = `0 + 2 + 7`（ロードバランシング無効時、`library.c`）。
暫定値 42 が外側から借りた約 18 バイトの CID を含んでいたのが差の出どころである。

### 6.2 契約 A は 1154 ではなく 1163

| family | IP+UDP | MaxUdpPayload | MaxSendLength | portal payload | |
| --- | --- | --- | --- | --- | --- |
| IPv4 | 28 | 1220 | 1187 | 1183 | 実測 |
| IPv6 | 48 | 1200 | 1167 | **1163** | 導出 |

**IPv6 は導出であり実測ではない。** `peer::dial` は毎回 `set_remote_addr` で
`Ipv4Addr::LOCALHOST` に固定する — 内側接続のリレー経路は MASQUE トンネルの
ローカル端であり、常に 127.0.0.1 だからである。したがってループバックでは v6 の
パスを作れない。導出は厳密で、`QuicCalculateDatagramLength` が family を使うのは
IP ヘッダ長を選ぶためだけである（`quic_datapath.h`）。

`send_path_mtu` は 1248 で、`MaximumMtu` の前提どおりだった。

現在の `MAX_PAYLOAD = 1180` は **17 バイト大きい**。1164〜1180 のペイロードは
portal が受け付けて IPv6 接続が拒否する。IPv4 では 1183 まで通るので、いま表面化
していないのはリレー経路が常に v4 だからである。

### 6.3 接続単位の上限は `Paths[0]` から導かれ、パス切り替えでは再計算されない

`QuicDatagramOnSendStateChanged` は `Connection->Paths[0]` の family・MTU・CID 長から
上限を出す（`datagram.c`）。そして呼ばれるのは 2 か所だけである:

- ピアのトランスポートパラメータ受領時（`connection.c`）
- **MTU プローブが ACK されて MTU が変わったとき**（`loss_detection.c`）

`QuicPathSetActive` からは呼ばれない（`path.c` に `QuicDatagram` の呼び出しは無い）。
非 multipath では同関数が新しいパスを `Paths[0]` へ swap するので、**切り替えた瞬間の
上限は古いパスから計算された値のまま**であり、その後 MTU 探索が動いたときに初めて
新しいパスの値へ飛ぶ。

### 6.4 §2.1-4 への回答、および計画に無かった経路

計画 §2.1 の 4 は「接続単位の値がどのパスから導かれているか確認しておく」としている。
答えは `Paths[0]`、すなわちアクティブパスである。加えて **family が経路間で異なりうる**
ことが §6.2 から分かる:

- リレー経路は常に IPv4（127.0.0.1、MASQUE のローカル端）
- 直接経路は相手の実アドレスで、IPv6 でありうる

つまり v4 リレー → v6 直接の移行では、MTU が同じでも上限が **20 バイト下がる**。
計画は MTU の分岐だけを契約 B の脅威として書いているが、アドレスファミリでも同じ
ことが起きる。しかも §6.3 により、下がるのは切り替えの瞬間ではなく、その後 MTU 探索が
動いたときである。

P2 の「要求サイズを満たさないパスをアクティブ化しない」は、要求サイズを MTU ではなく
**`QuicCalculateDatagramLength` の結果**で比較すれば両方を覆う。

### 6.5 残り

P0 の 3 番目のうち、**実接続での観測**（移行前後で接続単位の値がどう動くか）は未了。
2 本のパスが要るので実機が要る。機序は §6.3 でソースから確定しているが、観測は
別である。§4 の「単調性」の行と同じ手当てが要り、#165 と同じ再現の難しさを持つ。

### 6.6 §5 未決事項への影響

1. **42 の実測値** — 33 に確定。契約 A は 1163。
2. **`PathRemoved` 後の落下** — 変わらず未決。
3. **直接経路の `MaximumMtu`** — 変わらず未決。
4. **UDP フォワードの開始タイミング** — §6.3 が効く。上限は切り替えの瞬間には動かず、
   その後の MTU 探索で動く。つまり「直接経路の確定を待ってから開く」だけでは上限が
   固定されない。固定したいなら MTU 探索の収束まで待つ必要があり、それは数 RTT では
   済まない。
