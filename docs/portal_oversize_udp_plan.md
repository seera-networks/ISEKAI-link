# ISEKAI portal — 大きい UDP データグラムを単方向ストリームで運ぶ

実装計画。対象は `portal-core`（`datagram` / `frame` / `udp`）と `docs/portal.md`、
および **`msquic-async`（別リポジトリ、§6 の S0）**。
`docs/portal_mtu_plan.md` の姉妹編で、同じ問題に別の側から当たる。

---

## 0. 何を決めたか

**DATAGRAM フレームに載らないサイズの UDP データグラムは、単方向ストリームで運ぶ。
1 データグラムを 1 ストリームで送り、FIN がデータグラムの終端である。**

いまの portal は 1163 バイトを超える UDP ペイロードを**落として数える**
（`datagram.rs` の `MAX_PAYLOAD`、`docs/portal.md` §451）。`portal_mtu_plan.md` は
この上限を上げる方向で契約 A / B を立てたが、**上げ方には天井がある** — 契約 B が
うまくいっても実効上限は PMTU までで、1500 バイト級の経路でも 1400 程度にしかならない。
DNS の 1232 バイトは入るが、それ以上を要求するものは入らないままである。

ストリームで運べば**上限は UDP そのものの上限（65507 バイト）まで外れる**。
代償は払うが、払うものは「落ちる」ではなく「遅くなる」である。
**そして遅くなるのが嫌なら、落ちるほうを選べる** —
`QUIC_SEND_FLAG_CANCEL_ON_LOSS` が MsQuic にあり、損失検知で再送せずに
ストリームを畳む（§1.7、§3.1.1）。使えるようにする作業は `msquic-async` 側で、
この計画の先頭に置いた。

| | いまの扱い | この計画での扱い |
| --- | --- | --- |
| ≤ 1163 バイト | DATAGRAM フレーム | **変わらない。** DATAGRAM フレーム |
| > 1163 バイト | **落として数える** | 単方向ストリーム 1 本 |

**契約 A は残り、契約 B は要件から外れて最適化になる。** 契約 A（経路に依存しない
保証サイズ）は「不確実だが即座に届く」帯の約束として意味を失わない。契約 B は
その帯を広げる話だが、広げられなかったサイズが落ちるのではなく遅く届くのであれば、
それは正しさの要件ではなくスループットの話になる。

## 1. 現状として確定していること

コードを読んで確かめた。計画の全体がここに乗るので、数字と行番号を残す。

### 1.1 送信側には絞り口が 1 つしかない

`Sessions::send`（`portal-core/src/udp.rs:252`）が唯一の送信経路で、
**両方向がここを通る** — サーバ側が `udp.rs:502`、クライアント側が `udp.rs:755`。
分岐を入れる場所は 1 箇所で足りる。

```rust
fn send(&self, session: u32, payload: &[u8]) -> bool {
    let Some(framed) = encode(session, payload) else {
        self.oversize(session, payload.len());   // ← ここが分岐点になる
        return false;
    };
    ...
}
```

**`fn send` は `async` ではない。** 「データグラムには待つものが無い」という理由で
同期にしてあり、ストリームを開くのは `async` なので、ここから直接は開けない。§2.3。

### 1.2 ローカル側はもう最大サイズを読めている

`RECV_BUFFER = 65_536`（`udp.rs:95`）。**65507 バイトのデータグラムは今日すでに
全部読まれていて、運ぶ手段が無いので捨てられている。** 受信バッファを広げる作業は
要らない。

この定数のコメントは「`recv` はバッファに切り詰めて何も言わないので、運べるサイズに
合わせたバッファは『大きすぎて落とした』を『黙って切った』に変えてしまう」と書いて
いる。その判断がそのまま効いて、今回の前提になっている。

### 1.3 受信側は単方向ストリームを 1 本も受け取っていない

`accept_inbound_stream`（`udp.rs` 経由で `server.rs:172`）は**双方向専用**で、
単方向は `accept_inbound_uni_stream` という別の関数である
（`msquic-async/src/connection.rs:206` と `:240`）。portal はこちらを呼んでいない。

**そして呼ばないと溜まる。** `poll_accept_inbound_uni_stream` が読む
`inbound_uni_streams` は `VecDeque` で、**上限が無い**
（`connection.rs:1105`、push は `:1421`）。peer がストリームを開くと誰も accept
しなくてもキューに積まれる。これは §5 の互換性の話を「あったほうが良い」から
**「無ければ壊れる」** に変える。

### 1.4 単方向ストリームの枠はもう取ってある

`set_PeerUnidiStreamCount(100)` が**両側に**ある — 発側が
`isekai-p2p/src/peer.rs:199`、受け側のリスナが `utils/src/lib.rs:67`。
**相手が開ける単方向ストリームを 100 本まで既に許している**ので、設定変更なしに
受信側の枠はある。この 100 が同時実行の上限になる（§2.5）。

**両方を挙げるのは §2.3 が両方向に送るからである。** 片方だけ確かめて
「枠はある」と言うと、確かめていない向きで足りていない可能性が残る。
どちらも 100 なので結論は変わらない。

### 1.5 開くときに「待たない」を選べる

`open_outbound_stream(stream_type, fail_on_blocked)`（`connection.rs:192`）。
**`fail_on_blocked: true` は枠が尽きたときに待たずに失敗する**ので、送信側は
詰まらずに落として数えられる。`datagram.rs` が流量について取っている立場
（`Streams have flow control and datagrams have none, so something has to` —
`QUEUE_DEPTH` の doc、`datagram.rs:120`）と同じ向きである。

**ただし観測できるのはストリームの本数だけである。** `poll_write_generic` は
フロー制御で `Pending` を返すことがない — `put_zerocopy` は渡された `Bytes` を
push して長さを返すだけで上限を持たず（`buffer.rs:233`）、ペイロードを丸ごと
受け取って MsQuic に渡して戻る。送信側が見られる限界は `fail_on_blocked` が返す
`StartError::LimitReached` だけなので、**これはフロー制御ではなく
「ストリーム数の受け入れ制御」である**（§3 の表もそう直した）。

### 1.6 書き込みは 1 回で済む

`open_outbound_stream` が返すのは `Stream`（`connection.rs:2151`）で、その
`write_chunk(&chunk, fin)` / `write_chunks(&[chunk], fin)`
（`stream.rs:247` / `:262`）。**ヘッダとペイロードを 2 つの `Bytes` として渡し、
同時に FIN を立てられる**ので、コピーも往復も要らない。

受信側が受け取るのは `ReadStream`（`:304` の別の型）で、書く側の API は持たない —
単方向であることが型に出ている。

### 1.7 再送を止める手段が MsQuic にはあり、`msquic-async` には出ていない

`QUIC_SEND_FLAG_CANCEL_ON_LOSS`（`src/inc/msquic.h:257`、
`Indicates that a stream is to be cancelled when packet loss is detected`）。
**§3.1 のために期限を自分で決める必要は無い。**

意味論はコードで確かめた:

| | |
| --- | --- |
| 付き方 | **ストリーム単位で不可逆**。どれか 1 つの送信要求に付けば、そのストリームの以後の送信すべてが対象になる（`stream_send.c:620`、`If a send has the 'cancel on loss' flag set, we irreversibly switch the associated stream over to that behavior`）|
| 損失時 | `QUIC_STREAM_EVENT_CANCEL_ON_LOSS` を上げ、アプリが入れた error code で**両方向を即 abort** し、`return FALSE; // Don't resend any data.`（`stream_send.c:1384-1399`）|
| 相手側 | `PEER_SEND_ABORTED` を受け、`msquic-async` では `ReadError::Reset(code)`（`stream.rs:1674`、`handle_event_peer_send_aborted` が `:1194`）|

**不可逆であることが、ここでは欠点にならない。** 長命なストリームにとっては罠だが、
この計画のストリームの寿命は**データグラム 1 個**なので、「ストリーム単位」が
そのまま「データグラム単位」である。

**Rust バインディングには既にある。** `SendFlags::CANCEL_ON_LOSS`
（`seera-msquic/src/rs/types.rs:626`）と `StreamEvent::CancelOnLoss`
（`:376`、復号は `:454`）。

**無いのは `msquic-async` の配線だけ。** 送信フラグを決める場所は
`poll_write_generic`（`msquic-async/src/stream.rs:690`）1 箇所で、そこは
`WriteStatus` から `NONE` か `FIN` を選ぶだけで、呼び出し側からフラグを渡す道が無い。
`CancelOnLoss` イベントは `_ => { trace!("Other callback"); Ok(()) }` に落ちる
（`:1428`）ので**今日も壊れてはいない**が、error code を選ぶ機会も無い。

### 1.8 ストリームの先頭フォーマットには既に版と種別がある

`frame.rs`:

```text
 client → server   [ 2 ][ kind ][ len ][ service name ]           kind 0, TCP
 client → server   [ 2 ][ kind ][ len ][ service name ][ u32 ]    kind 1, UDP
 server → client   [ status ]
```

`VERSION = 2`、`KIND_TCP = 0`、`KIND_UDP = 1`。新しい種別を足す形は用意されている。
ただしこの交換は**双方向ストリーム**の上で行われ、`[ status ]` の返信がある。
単方向ストリームでは返信ができない — それでよい理由は §2.2。

## 2. 設計

### 2.1 ワイヤフォーマット

単方向ストリーム 1 本が、データグラム 1 個である。

```text
 送信側 → 受信側   [ VERSION ][ KIND_BIG_DATAGRAM ][ session u32 ][ payload ... ] FIN
```

- `[ VERSION ]` は `frame::VERSION` **の値をそのまま**。リテラルで `2` と書かない —
  当初ここは `[ 2 ]` と書いてあり、同じ計画の S1 が版を 3 に上げると書いていたので、
  **文字どおり実装すると受信側の版検査で全部落ちる**ところだった。版の扱いは §5 で
  変わり、いまは 2 のままだが、**書くのは定数であって数字ではない**。
- `[ KIND_BIG_DATAGRAM ]` が「これは 1 個の大きいデータグラムである」。
- `[ session u32 ]` は `datagram.rs` のヘッダと同じ意味・同じ幅のセッション id。
  **データグラム側と同じものを同じ幅で置く**ので、受信側は組み立て終わったバイト列を
  既存の `deliver` と同じ経路に入れられる。
- 長さは書かない。**FIN が長さである。** ストリームは終端を持つので、長さを書くと
  2 つが食い違う余地を作るだけになる — `frame.rs` の冒頭が TCP について言っているのと
  同じ理由である。

`session` をデータグラム側と同じ 4 バイトにするのは、**ここでは倹約の理由が無い**
にもかかわらずそうする。データグラムのヘッダが id だけなのは 1 バイトがペイロードの
1 バイトだからで、ストリームにはその圧力が無い。それでも揃えるのは、2 つの経路が
同じ id 空間を指していることをコードの形で示すためである。

### 2.2 なぜ単方向か

返すものが無い。既存の UDP セッション開設ストリーム（kind 1）が `[ status ]` を
返すのは、**拒否されたサービスが「受け入れて即切った相手」と区別できないと、
ローカルのアプリが空の成功を見てしまう**からである。データグラム 1 個にその問題は
無い — 宛先セッションは既に開設済みで、id が未知なら受信側が
`unknown_session` に数えるだけで、送信側が知って何かできることは無い。

双方向にすれば受信側の受領を待てるが、それは UDP に無い意味を足すことになる。

### 2.3 送信経路

`Sessions::send` の `encode` が `None` を返す枝（= `MAX_PAYLOAD` 超過）を、
`oversize` に数える代わりに**ストリーム送出へ渡す**。

`send` は同期なので、ここでストリームを開くことはできない。`Sessions` が
**専用の送出タスクと有界チャネル**を持ち、`send` は `try_send` するだけにする。

```text
  send() ──try_send──▶ [ 有界チャネル ] ──▶ 送出タスク
                           │ 満杯なら                    │ 1 データグラムごとに
                           └─ oversize_dropped に数える   └─ open → write_chunks(fin)
                                                            → poll_finish_write → 終了
```

> **`poll_finish_write` を省くとデータグラムは届かない。** ここは当初
> `open → write_chunks(fin) → 終了` と書いてあり、それは**ほぼ全部の大きい
> データグラムを捨てる**実装になる。
>
> `write_chunks` は MsQuic が送信要求を受け取った時点で解決する — `poll_write_generic`
> は `send()` に渡して `Poll::Ready(Ok(..))` を返すだけで、送信も ack も待たない
> （`msquic-async/src/stream.rs:690-755`）。そこでタスクを終えると `Stream` が drop
> され、ハンドルが閉じられ、**`QuicStreamClose` は `ShutdownComplete` でなければ
> `ABORT_SEND | ABORT_RECEIVE | IMMEDIATE` を実行する** — コメントがそのまま
> `Abort any pending operations.` と書いてある（`seera-msquic/src/core/stream.c:413-420`、
> 入口の `if (!Stream->Flags.ShutdownComplete)` が `:403`）。
> 受信側は `ReadError::Reset` を見る。
>
> **このリポジトリは既にこれを 2 箇所で知っていた。** 単方向の送出は
> `camera_core::video::push_one`（`rust/camera-core/src/video.rs:314`）が
> `write_all` のあとに `poll_finish_write` を待っており、`portal_core::server::refuse`
> の doc は status バイトについて同じことを言っている — 「**`write_status` が返っても
> byte が出たことにはならない。** finish していないストリームを閉じると両方向が
> abort されるので、status が reset で消えて…」（`server.rs:197`）。
>
> **値段も変わる。** 送出タスクは ack まで生きるので、§2.3 の「1 データグラムごとに
> 1 タスク」は見かけより長命である。**そしてそれが §1.4 の 100 本という枠を
> 実際に効かせている** — 即座に閉じていれば枠は決して埋まらず、何も絞られない。

- **満杯で落とすのは、待たないため。** `send` が待てば、その呼び出し元は
  `udp.rs:502` / `:755` のソケット読み出しループで、待つとローカルのソケットの
  読み出しが止まり、カーネルのバッファが溢れて**小さいデータグラムまで落ちる**。
  大きいものを運ぶ機能が小さいものを壊すのは筋が通らない。
- 送出タスクは**ストリームごとに `tokio::spawn`**。1 本の遅いストリームが後続を
  止めないため。これが「1 データグラム 1 ストリーム」の値段を払う場所である。

### 2.4 なぜ 1 データグラム 1 ストリームか

`datagram.rs` の冒頭は、**ストリームを使わない理由としてヘッドオブラインを挙げて
いる**:

> Datagrams rather than an unreliable stream because UDP's own semantics are
> datagram semantics — losing one is allowed, reordering is allowed, and a
> stream would add head-of-line blocking the application does not expect.

**1 本に相乗りさせるならその指摘は正しく、1 データグラム 1 本ならあたらない。**
ストリーム間に順序関係は無いので、データグラム N の再送はデータグラム M を待たせない。
ブロッキングは 1 個のデータグラムの内側に閉じ、そこは**元々 1 個の不可分な
データグラム**だったのだから、アプリが失うものは無い。

この計画が成立するかどうかはこの 1 点にかかっている。だから相乗りは選択肢に入れない
（§7）。

### 2.5 受信経路

`Sessions` が `pump` の隣に**2 本目のループ**を持つ。

```text
  accept_inbound_uni_stream() ──▶ ストリームごとに spawn
                                     読み切る（上限まで）→ 先頭を解析 → 既存のキューへ
```

- `ReadStream`（`poll_accept_inbound_uni_stream` が返す型、`connection.rs:245`）を
  FIN まで読み、**組み立て終えてから**セッションのキューに入れる。途中で渡せるもの
  ではない — データグラムは不可分である。
- 入れる先は `deliver` が使うのと同じキュー（`table` の `Queue`）。**その先の経路は
  1 行も変わらない**。満杯なら既存どおり最古を落として `overflow` に数える。
- `MAX_SESSIONS` は触らない。**`QUEUE_DEPTH` は触らないでは済まない** — 次項。

#### キューの上限は個数ではなくバイト数でなければならない

`QUEUE_DEPTH = 64`（`datagram.rs:128`）は**個数**で、**キューに入るものが
最大 1163 バイトだった前提で決められている**。1 セッション 74 KB である。

そこに 65507 バイトを混ぜると:

```
  64 × 65507                    = 4.19 MB   1 セッション
  × MAX_SESSIONS (1024)         = 4.3 GB    1 接続の表の上限
```

**当初この計画は「`QUEUE_DEPTH` もも触らない」と書いていた。** 個数の上限はバイト数を
縛らないので、ローカルのアプリが数セッション分読むのを止めただけで、§2.5 が
頼っている「満杯なら最古を落とす」が**バイト数については何も保証しない**。

**セッションあたりのバイト上限を足す**（個数と併用し、どちらかに当たれば最古を
落とす）。値は §8-3。

#### 同時に読むストリーム数の上限は、accept しないことでは作れない

§1.4 の 100 はトランスポート側（`PeerUnidiStreamCount`）の上限で、全部が 65507
バイトなら 1 接続 6.4 MB。**この 6.4 MB を portal 側の定数で下げることはできない。**

accept しないという選択は、§1.3 のとおり**上限なしの `VecDeque` に積む**だけで、
しかも MsQuic はストリームを既に作って受信窓を与えているので、`handle_event_receive`
は `recv_buffers` にバッファを積んで `QUIC_STATUS_PENDING` を返し続ける
（`stream.rs:1153` と `:1158`、関数は `:1129`）。`StreamMultiReceiveEnabled` は両側で有効
（`isekai-p2p/src/peer.rs:209`、`utils/src/lib.rs:69`）なので、**accept していない
ストリームの分も溜まる。**

下げたいなら手段は 2 つしかない: **accept してから `abort_read` する**か、
**`PeerUnidiStreamCount` を下げる**か。前者は「受け取れないと伝える」ことになり、
後者は接続全体に効く。§8-1。

### 2.6 サイズ上限

`MAX_STREAM_PAYLOAD = 65507`（UDP ペイロードの上限そのもの）。

**portal が独自の上限を作らない。** ここで 8 KB なり 16 KB なりに切ると、
「portal は 1163 までしか運ばない」を「portal は 16384 までしか運ばない」に
置き換えるだけで、同じ説明を 2 度することになる。メモリはキューのバイト上限
（§2.5）で縛るほうが、運べるサイズを下げるより素直である。

受信側は**先頭を見た時点では長さを知らない**（§2.1 で長さを書かないので）ので、
上限は「読んだ量がこれを超えたらストリームを捨てる」という形で効かせる。

**そのとき比べる相手はヘッダを含んだ長さである。** ストリームは §2.1 の
`[ VERSION ][ kind ][ session u32 ]` の 6 バイトを前に持つので、最大サイズの
データグラムは **65513 バイト**読まれる。`MAX_STREAM_PAYLOAD` とそのまま
比べると**合法な最大サイズが落ちる** — §9 の「最大: 65507 が往復する」が
落ちるテストになる。ヘッダを読み終えてから数え始めるか、
`MAX_STREAM_PAYLOAD + HEADER` と比べる。

## 3. 何が変わり、何は変わらないか

**この節が計画の本体である。** サイズの話に見えて、実際には配送意味論を
サイズで二分する変更だからである。

| | ≤ 1163（DATAGRAM） | > 1163（ストリーム） |
| --- | --- | --- |
| 損失 | **あり得る。** 再送しない | **無い。** QUIC が再送する |
| 遅延 | 1 RTT | 損失時は再送分だけ伸びる |
| 順序 | 保証しない | **データグラム間では保証しない**（ストリーム間に順序は無い）|
| 流量の制御 | 無い。キューが最古を落とす | **ストリーム数の受け入れ制御。** 枠が尽きれば送信側で落とす |
| 不可分性 | ある | ある（FIN が境界）|

### 3.1 大きいものだけが信頼できる、という非対称

**同じセッションの中で、サイズによって損失の有無が変わる。** これはアプリから
観測できる。

多くの用途では改善である（DNS の大きな応答は、落ちるより再送されるほうが良い）。
**改善でない用途もある**: リアルタイムのメディアのように「古いデータは要らない」
ものにとって、再送は帯域と遅延の無駄である。

**そのための手段は MsQuic にある**（§1.7）。`CANCEL_ON_LOSS` を付けて送れば、
損失が検知された時点でストリームは再送されずに abort され、受信側は
`ReadError::Reset` を見て組み立て中のものを捨てる。**つまり UDP の意味論に
正確に戻る** — 失われたデータグラムは、遅れるのではなく失われる。

**期限を決める必要が無いのが要点である。** 当初この節は「一定時間で諦める」
仕組みを素描していたが、期限は portal が知らない値で、既定を置けば必ず誰かに
対して間違っていた。`CANCEL_ON_LOSS` の引き金は**損失検知そのもの**で、それは
まさに正しい引き金である。数字を選ぶ問題が消える。

### 3.1.1 三択になる

| | 損失 | 遅延 | 誰のための挙動か |
| --- | --- | --- | --- |
| DATAGRAM（≤1163）| あり | 1 RTT 固定 | 今まで通り |
| ストリーム、フラグなし | **無い** | 損失時に伸びる | 大きな DNS 応答。届くことが大事なもの |
| ストリーム + `CANCEL_ON_LOSS` | あり | **再送による伸びが無い**（下記）| 古いデータが要らないもの |

**「1 RTT 相当」とは書けない。** 当初この表はそう書いていたが、この経路が
存在する理由からして**データグラムは必ず 1 パケットを超える**（1164 バイト以上、
65507 なら約 45 パケット）。損失が無くても最後のバイトが着くまでに 1 RTT では
済まないし、`CANCEL_ON_LOSS` は**そのストリームのどこかで損失が検知されれば**
abort する — 下段で触れる N パケット分の露出がそのまま効く。1 RTT に近いのは
DATAGRAM の境界すぐ上のサイズだけである。**この行は §8-2 の既定の判断の
根拠になるので、盛ると判断を誤らせる。**

**既定をどちらにするかは製品の判断で、§8-2 に置いた。** この計画が動機にしている
のは DNS なので**フラグなしを既定として推す**が、ひとつ数字を添えておく値打ちが
ある: **N パケットに跨るデータグラムを再送なしで送ると、損失確率はおよそ
パケット 1 個の N 倍になる。** 4 KB の応答は 4 パケット強で、これは IP
フラグメンテーションが昔からしていたことと同じ脆さである。意味論としては忠実でも、
実用上はそこが効く。

### 3.2 2 つの運び方の間には順序が無い

セッションの通信が 2 つの経路に分かれるので、**大きいデータグラムが、後から
送られた小さいものより後に着く**ことがある。再送が挟まればほぼ必ずそうなる。

UDP は順序を保証しないので契約違反ではない。**ただし「保証しない」と「実際に
入れ替わる」は別のことで**、今まで入れ替わらなかったものが入れ替わるようになる。
id で突き合わせる DNS のようなものは無害で、暗黙に順序を頼っているものは影響を受ける。
`docs/portal.md` に書く。

### 3.3 分割はしない、が変わらない

`portal_plan.md` §4.1 の「黙って分割するデータグラムサービスは、黙って落とす
ものより悪い」はそのまま立っている。**この計画は分割の反対である** — 境界を
保ったまま運ぶ手段を足すのであって、境界を壊して既存の手段に押し込むのではない。

## 5. 互換性 — 交渉は必須である

§1.3 の `VecDeque` に上限が無いという事実が、ここを「できれば」から「必ず」に
変える。

**0.6.0 の peer に単方向ストリームを開くと、相手は accept しないのでストリームは
キューに積まれ続け、データは届かず、メモリは解放されない。** 送信側には何も
返らないので、落ちたことすら分からない。交渉せずに出すとこうなる。

交渉する場所は既にある。**UDP セッションを開設する双方向ストリーム（kind 1）が
版と `[ status ]` を交換している**ので、そこに「この端は大きいデータグラムを
単方向ストリームで受け取る」を載せる。

### 5.1 版を上げる案は捨てた

当初ここは **`VERSION` を 3 に上げる**と書いていた。`frame.rs` が 2 にした理由
（「同じ先頭 2 バイトが違う意味を持つのが、番号を 1 つ使って大声にする価値のある
唯一の食い違い」）がそのまま当てはまる、という理屈だった。**成り立たない。**

`read_open` は `head[0] == VERSION` を `anyhow::ensure!` で検査して
`unsupported portal protocol version {}` で抜ける（`frame.rs:159`）。
返信は status 1 バイトだけで、版を言う場所が無い（`write_status`、`frame.rs:195`）。
つまり:

- **版 3 の `Open` は、status が 1 バイトも書かれる前に拒否される。** 送った側が
  見るのは「版が違う」ではなく**死んだストリーム**で、§5 が書いていた
  「2 の挙動に落ちる」という退避路は**どこにも実装されていない**。
- **そして落ちるのは大きいデータグラムだけではない。** 版は `KIND_TCP` の
  `Open` にも乗っているので、**この計画と無関係な TCP フォワードごと
  0.6.0 相手に通らなくなる。** flag day である。

### 5.2 種別で交渉する

版ではなく**開設の種別**で交渉する。`VERSION` は 2 のまま。

```text
  client → server   [ 2 ][ KIND_UDP_BIG ][ len ][ name ][ u32 ]
                      = 「UDP セッション。かつ私は大きいデータグラムを受け取れる」
  server → client   [ Ready ]        → 相手も受け取れる
                    （ストリームが死ぬ）→ 相手は知らない。**このセッションは
                                          諦め**、次のデータグラムが新しい id で
                                          平の種別を使う
```

**同じセッションの中で開き直さない。** 開設フレームは id を運び、答える側は
status を書く**前に** id を取る（`serve`）。同じ id で 2 度目を試すと
`Accept::InUse` に当たって `Status::Refused` が返り、「このサービスを提供して
いない」と**権威をもって誤報される**。失ったセッション 1 本より、断定された
誤りのほうが高い。代償は**接続あたり 1 セッション**で、相手が機能を持たない
初回だけである。

**これが成り立つのは `read_open` がそう作られているからである。** 種別の検査は
名前を読んだ**後**に置かれているので、未知の種別は
`unknown open kind {other} for service` で拒否され、しかも拒否は `forward_one`
の中（`server.rs:213`）なので**その 1 本で終わり**、接続も他のフォワードも
巻き込まない。

**ただし「フレーム境界に残る」は誤りだった。** 種別の検査は名前の後・session id
の**前**なので、UDP 系の種別が拒否されるとストリームには 4 バイト残る —
`read_open` のコメントが言う境界は名前の末尾で、フレーム境界であるのは
`KIND_TCP` のときだけである。依存している箇所は無い（開き直しは新しい
ストリームを開く）が、将来の読者に「再利用できる」と読ませないようコードと
ここの両方を直した。

| | 版を 3 に上げる | 種別を足す |
| --- | --- | --- |
| 0.6.0 相手の TCP フォワード | **壊れる** | 無事 |
| 0.6.0 相手の UDP フォワード | **壊れる** | 開き直して無事 |
| 失敗の波及 | 接続のフォワード全部 | **開設 1 回** |
| 退避の仕組み | **無い** | `KIND_UDP` で再試行（1 往復） |

代償は、**知らない相手に対して開設が 1 往復余計にかかる**ことと、能力が
「種別が受け入れられたか」という間接的な形で伝わること。前者は接続ごとに
一度で、後者は §5.1 が心配していた「読まないバイト」よりは強い — **読まない
実装は種別を拒否するので、黙って間違うのではなく失敗する。**

**相手が知らなかったと分かったら、今までどおり落として数える。** 機能が無いのでは
なく相手に無いので、`oversize` の警告文はそれが分かる形にする。

## 6. フェーズ

### S0 — `msquic-async` に送信フラグの道を作る（別リポジトリ）— **完了**

**ここが先行する。** `msquic-async` は別リポジトリ
（`masa-koz/msquic-async-rs`、サブモジュール）なので、上流への変更が要る。

**msquic-async-rs#102 で入った**（`311ddba`、サブモジュールは `35d6eb0`）。
計画した 12 本がそのまま生えている。**計画に無かった発見が 1 つあり、
それが §2.3 と §8-4 を変える** — 下の「ローカル側は abort を知る必要がある」。

`poll_write_generic`（`stream.rs:690`）に追加のフラグを渡す引数を足し、既存の
入口はすべて `SendFlags::NONE` を渡す。その上で `_no_retrans` を付けた入口を
並べる:

| 既存 | 追加 |
| --- | --- |
| `poll_write` | `poll_write_no_retrans` |
| `poll_write_chunk` / `write_chunk` | `poll_write_chunk_no_retrans` / `write_chunk_no_retrans` |
| `poll_write_chunks` / `write_chunks` | `poll_write_chunks_no_retrans` / `write_chunks_no_retrans` |

`Stream` と `WriteStream` の両方に生える（`stream.rs:227-262` と `:367-402`）。

**`_no_retrans` という名前が、フラグ名より意味を言っている。** `CANCEL_ON_LOSS`
は MsQuic 側の名前で、呼ぶ側にとって重要なのは「再送されない」ことである。
ただしドキュメントには**不可逆性を書く必要がある**（§1.7）— 一度でもこれで書いた
ストリームは、以後 `write_chunk` で書いても再送されない。名前が per-call に
見えるので、そこは明記しないと誤解される。

`StreamEvent::CancelOnLoss` の扱いも決める。いま `_` に落ちているので動作は
壊れていないが、**error code を選べない**。相手に伝わる値なので、既定 0 のまま
にするか、ストリームに設定できるようにするか。portal の用途では 0 で足りる。

**→ 0 のままになった。** イベントの `error_code` は MsQuic が 0 に初期化する
out パラメータで、ハンドラは複写で受けて書き戻さないので、abort は常に 0 を運び、
相手は `ReadError::Reset(0)` を見る。setter は必要が出てからでよい。

#### ローカル側は abort を知る必要がある（計画に無かった）

**`CANCEL_ON_LOSS` の abort は自分のスタックが起こすので、放っておくと
「自分で `fin` した」と区別できない。** `send_error_code` も `recv_error_code` も
立たず、write は `WriteError::Finished`、`poll_finish_write` は `Ok(())` を返して
しまう — つまり **§2.3 の送出タスクは、捨てられたデータグラムを成功と読む。**

#102 はハンドラで teardown を記録し、**`ReadError::CancelledOnLoss` と
`WriteError::CancelledOnLoss`** として出すようにした（どちらも
`io::ErrorKind::ConnectionAborted`）。双方向ストリームなら読み側が
clean EOF を返して未読データを捨てるという別の害もあった。

**計画側への影響は 2 つ。**

1. §2.3 の送出タスクは、`poll_finish_write`（レビューで足した段）が
   `WriteError::CancelledOnLoss` を返したら**落ちたものとして数える**。
   `fin` 済みの成功と区別がつく。
2. §8-4 のカウンタに「再送を諦めて捨てた」が**自前の推測ではなく観測として**
   入る。受信側の `ReadError::Reset` と対になる。

`ReadError` / `WriteError` に変種が増えたので、**網羅 match を持つ利用側は
影響を受ける**。このワークスペースは受けない（`cargo check --workspace` が
通る）が、`h3-msquic-async` は 2 箇所に腕を足している。

### S1 — 枠組みと交渉（運ばない）— **完了**

- `KIND_UDP_BIG = 2` と `KIND_BIG_DATAGRAM = 3` を定義。**種別の番号空間は
  双方向・単方向で共通**とした（`frame.rs`）— 到達した経路で意味が変わるバイトは
  `VERSION` が防いでいる類のものだからである
- `Open::Udp` に `oversize_on_stream: bool`。**両 UDP 種別は 1 バイトしか違わず、
  `protocol()` も `service()` も同じ** — カタログから見て区別がつかないことが、
  「別の訊き方で 2 つ目の経路が開く」ことを防いでいる
- 開設は `open_session` / `try_open` に分かれ、**status バイトが届いたかどうか**で
  失敗を 2 つに分けた（`OpenFailed::NoStatus` / `Answered`）。**status が届いたなら
  種別は読まれた**ので、`Refused` に再試行はしない — そこで再試行すると設定の
  間違いを 2 度目の試行で隠してしまう
- 相手の能力は `PeerOversize`（3 状態）として `Sessions` が接続単位で持つ
- 答える側（`server.rs`）が種別から相手の半分を学ぶ。**1 回の交換で両方向が
  決まる**: 答える側は訊かれた種別から、訊いた側は答えが返ったことから
- `oversize` の警告が**どちらの限界かを言う**ようになった

#### 機能は S1 では名乗らない（計画の訂正）

計画は「S1 で開設にまずこれを使う」と書いていた。**そのままにはできない。**

`oversize_on_stream` は **「私はこれを受け取れる」** という意味である。S1 だけを
含むビルドがそう言うと、**0.6.0 に対してではなく、S3 の送信側を持つ後のリリースに
対して**嘘になる。その相手は誰も accept しない単方向ストリームを開き、accept
されないストリームは受信窓を与えられたまま上限なしのキューに積まれる（§1.3）。
**自分の将来のリリースに罠を置くことになる。**

**そして訊かないだけでは足りなかった。** 最初の実装は opener として訊くのを
やめておいて、**answerer としては `KIND_UDP_BIG` に `Ready` を返していた** —
相手は「答えが返ったこと」から能力を記録するので、同じ罠を裏側から踏んでいる。
コードレビューが見つけた。

**訊くことと与えることは同じ主張なので、1 つの定数が両方を決める形にした** —
`frame::RECEIVES_OVERSIZE_ON_STREAM`。false の間は `read_open` が種別を
（未知の種別と同じ形で）拒否し、opener は訊かない。**S2 が受信ループと一緒に
これを立てる。** 種別・フィールド・答える側の学習・`Sessions` の記憶はすべて
生きている。

#### 相手の能力の覚え方は 4 状態（レビューで直した）

最初は 3 状態で、`yes` を `no` で上書きしないことだけを守っていた。**守る向きが
片方しかなかった**: 接続の最初のセッションの probe が、種別とは無関係な理由
（一瞬のリセット、ストリーム上限、停滞）で無応答に終わると、**その接続では
二度と訊かなくなる**。

そこで「一度は覚え、二度目で決める」にした。1 回の無応答では結論が動かず
（まだ unknown なので次が訊く）、2 回で latch する。訊かないままにすると、
機能を持たない相手に対して毎セッション 1 本を失うので、latch は必要である。

> **実装の 1 段を書き間違え、テストが捕まえた。** `compare_exchange` を 2 つ
> 続けると 1 回の呼び出しで `UNKNOWN → REFUSED_ONCE → NO` まで進んでしまい、
> 初回で latch して追加した状態が無意味になる。「覚えるが信じない」のテストが
> 落ちたので分かった。

**S1 単独の値打ちは変わらない** — 境界と番号と交渉の形が固まり、互換性の判断が
乗る場所ができた。テストは `frame.rs` に 2 本（1 バイトしか違わないこと、未知の
種別がフレーム境界で止まること）、`udp.rs` に 4 本（3 状態の遷移、とくに
**証明済みの `yes` が死んだストリームで `no` に落ちない**こと）。

### S2 — 受信側 — **完了**

- `Sessions::pump_streams` が `accept_inbound_uni_stream` のループ、
  `read_big_datagram` がストリーム 1 本を読む。**`pump` の arm ではなく 2 本目の
  ループ**にしたのは、1 本の 64 KB が接続上の全データグラムを待たせないため —
  §2.4 が却下した相乗りのヘッドオブラインを、一番効く場所で再現してしまう
- 組み立て終えてから `deliver_payload` へ。**2 つの運び方が合流するのはここだけ**で、
  以降はキューも上限もカウンタも 1 組である
- `QUEUE_BYTES = 128 KB`（§8-3 の決着）。`MAX_STREAM_PAYLOAD = 65507`
- カウンタ 3 本: `stream_malformed` / `stream_too_big` / `stream_lost`
- **`RECEIVES_OVERSIZE_ON_STREAM` を `true` に。** 受け取れるようになったので
  名乗って良い。送るのは S3 で、まだ無い

#### キューのバイト上限は 128 KB

| | |
| --- | --- |
| 現状の最悪値 | 64 × 1163 ≈ **74 KB**/セッション。128 KB はその 1.7 倍で、**今動いているものが落ち始めることはない** |
| 1 接続の表の上限 | 128 KB × 1024 = **131 MB**（個数だけなら 4.3 GB だった）|
| 最大サイズでの実効深さ | 65507 × 2 = 131014 < 131072 なので **2 発**。大きいものを溜め込ませない形で、このキューは「遅い読み手を burst が越える」ためのものである |
| DNS 級（4 KB）| 32 発 |

**`Push::Evicted` が個数を運ぶようになった。** 1 つの到着が複数を押し出せる
（100 KB が 8 KB を 5 本どかす）ので、push ごとに 1 を数えると**まさに効く分だけ
過少申告**する。

`MAX_STREAM_PAYLOAD <= QUEUE_BYTES` は `const _: () = assert!(..)` で**コンパイル
時に**縛った。空のキューに 1 発入らないと、`push` が全部捨ててなお上限を超える。

#### ストリーム 1 本の読み出しには 2 つの歯止めが要る

**どちらも最初は無かった。** 読み出しは相手が finish するか reset するか接続が
死ぬまで park し、**そのどれも `shutdown` ではない**。

- **`shutdown`**: このタスクは `Arc<Sessions>` を持つので `Connection` の clone を
  持ち、それは `RegistrationClose` が待つハンドルである — `start_with_idle` と
  `session::Connected::close` が両方書いている罠そのもの。頭の 6 バイトだけ書いて
  止まる相手が 1 人いれば、`close` は cancel して handle を落として、
  **5 秒の drain を諦める**。
- **期限**: 接続が健全なまま相手がストリームを握ることはできて、トランスポートは
  それを 100 本許す。期限が無ければ、全部を停滞させた相手が接続上の大きい
  データグラムを全部止め、しかも理由がどこにも出ない。`Sessions` の `idle` を
  使う — 実在する回線なら十分に緩く（65507 バイトは動いている回線なら 1 秒未満）、
  既にパラメータなのでテストが 1 分待たなくて済む。

#### 送れないものは入口で断る

`forward` はローカルのソケットから `RECV_BUFFER`（65536）まで読んでキューに入れ、
送れないと分かるのは `Sessions::send` である。**バイト上限がこれを変えた**: 
`SENDABLE_PAYLOAD` を超えるものは必ず落ちるのに、以前は深さの 64 分の 1 しか
使わなかったのが、いまは 64 KB 1 発で**セッションの予算の半分**を取り、後ろの
小さいものを追い出す。

そこで入口で断る。カウンタは `Sessions::send` が数えていたものと同じで、
変わるのは**予算が「出て行けるトラフィック」のために残る**ことである。
`SENDABLE_PAYLOAD` は S3 で `MAX_STREAM_PAYLOAD` になる 1 箇所である。

#### 同時実行数は portal からは下げられない

§2.5 の結論どおり、accept しないことはメモリを減らさない。**受け入れたものは
全部読む**。上限はトランスポートの `PeerUnidiStreamCount`（100）で、
`MAX_STREAM_PAYLOAD` と掛けて 1 接続 6.4 MB。下げたいなら `abort_read` か
トランスポート設定で、このループの仕事ではない。

#### テスト

ループバックで**端から端まで**: 4 KB のペイロードが単方向ストリームで渡り、
サービスに届く（`MAX_PAYLOAD` を超えるものが初めてフォワードを通った）。
`MAX_STREAM_PAYLOAD + 1` は届かない。ヘッダは `frame::big_datagram_head`
——**本物の writer**——で書く。手書きのバイト列は、形式が動いた瞬間に形式を
テストしなくなる。

> **送信側が無いので、応答は確かめられない。** 既存の
> `shouting_datagram_service` は往復を測る道具で、返ってくる 4 KB は
> `MAX_PAYLOAD` を超えて落ちるため、この経路には使えない。到着を記録する
> `recording_datagram_service` を足した。
>
> **テストの `drain` が 1 つ教えてくれた。** finish したストリームも
> registration が待つハンドルで、落とさないと `drain` が 5 秒で諦める。
> アサーションは全部通っていたのにテストは落ちていた。
>
> **そして「上限を守るテスト」が何も守っていなかった。** 最初の版は
> `udp_status` でセッションを開けていて、それは戻るときに lifetime ストリームを
> 落とすので、サーバはストリームを読む前にセッションを畳む — つまり
> 「サービスに何も届かない」は**上限チェックを消しても通る**（`unknown_session`
> に落ちるだけ）。セッションを握ったまま、**後から正常な大きいデータグラムを
> 送って届くこと**まで確かめる形に直した。
>
> どちらの歯止めも、**外すとテストが落ちることを実際に確かめた**（上限チェックを
> `false &&` で潰す、期限を 1 時間にする）。守っているものが守られていることの
> 確認は、テストが通ることではなく、壊すと落ちることである。
>
> **期限は client 側で測っている。** サーバの `Sessions` はテストから届かない
> ので、ハーネスに `Halves::peer_side`（サーバ側接続の clone）を 1 本通し、
> **サーバがまだ開かない向き**の単方向ストリームをそこから開いている。
> 最初は client 側から開いて `drain` で測ろうとしたが、テスト自身が持つ
> ストリームハンドルが同じ registration を塞ぐので**切り分けられなかった**。

### S3 — 送信側

- 有界チャネルと送出タスク
- `send` の `oversize` 枝を分岐させる
- `fail_on_blocked: true` で開き、落ちたものを数える

### S4 — `CANCEL_ON_LOSS` を使えるようにする

S0 で生えた API を、フォワード単位の選択として portal から使えるようにする
（§3.1.1 の三択目）。**既定にするかは §8-2。**

## 8. 未決事項

1. **同時に読んでよいストリーム数**。トランスポートの上限は 100（§1.4）で、
   全部が最大サイズなら 1 接続 6.4 MB。**「portal 側の定数で下げる」は
   選択肢ではない**（§2.5）— accept しないことはメモリを減らさない。下げるなら
   accept してから `abort_read` するか、`PeerUnidiStreamCount` 自体を下げる。
   **セッション数（1024）とは独立であることに注意** — 上限は接続単位なので、
   セッションが増えても増えない。
2. **`CANCEL_ON_LOSS` を既定にするか、opt-in にするか**（§3.1.1、S4）。
   **期限をいくつにするかという問いは消えた**（引き金が損失検知なので）が、
   どちらを既定にするかは残る。動機が DNS なのでフラグなしを推すが、
   「portal の UDP フォワードは UDP と同じ意味論である」を優先するなら逆になる。
   `--map` のオプションにするのが素直。**フォワード単位で足りるかは分からない** —
   1 本のフォワードに大小・緩急の違う通信が混ざる場合がある。
3. ~~**キューのバイト上限をいくつにするか**~~ → **128 KB**（S2、§6）。
   混ぜるか分けるかは**混ぜたまま**で、大きいものの洪水が小さいものを追い出す
   形は残っている（キューは最古を落とす）。**分ける判断は観測してからでよい** —
   バイト上限が入ったので、少なくとも「上限が無い」という状態ではなくなった。
4. **カウンタの切り方**。いまの `oversize` は「アプリが大きすぎるものを送った」で、
   これからは「相手が受け取れない」「枠が尽きた」「上限を超えた」「ストリームが
   途中で死んだ（受信側は `ReadError::Reset`、送信側は
   `WriteError::CancelledOnLoss`）」が別の事象になる。**最後のものは S0 の
   おかげで観測であって推測ではない**（§6 の S0）。`refused_too_big` と `oversize` を分けた
   判断（`datagram.rs:168`、「数えて一緒にすると区別できず、2 つは違う場所へ
   導く」）と同じ基準で分ける。
5. **契約 C を `docs/portal.md` でどう言うか**。「上限が無くなった」とだけ書くと
   §3.1 を隠す。サイズで損失の有無が変わることを、約束として書ける文にする必要が
   ある。
6. ~~**知らない相手に対する開設の 1 往復を省けるか**~~ → S1 で決めた。
   `Sessions`（接続単位）が `PeerOversize` を持ち、**最初の 1 セッションだけが
   払う**。`Some(false)` を覚えた後は probe しない。
7. ~~**`RECEIVES_OVERSIZE_ON_STREAM` を S2 で立てるとき、受信側が「ある」ことを
   どう担保するか**~~ → **S2 で立てた**（受信ループと同じコミット）。以下は、
   次に S3 を足すときに同じ形で効く注意として残す。**訊く側と与える側が同じ定数を読むようになったので、
   2 つが食い違う形の失敗は無くなった**（レビューが見つけたのはまさにそれ）。
   残るのは「受信ループが無いのに定数が立っている」1 通りで、いまはそれを
   「S2 が同じコミットで立てる」という規律で防いでいる。**規律であって仕組みでは
   ない** — 受信ループの存在にコンパイル時に結び付ける手があるなら、そのほうが
   良い。
8. **probe の「無応答 → 学習 → 次は訊かない」一巡がまだテストで走らない**。
   S2 で定数が立ったので probe は実行されるようになり、ループバックが
   **`KIND_UDP_BIG` が受理される側**を押さえている。残っているのは**拒否される
   側**で、それには「この機能を持たない相手」が要る — いまのループバックは
   両端が同じビルドなので作れない。`read_open` を通さない偽の answerer を立てる
   のが素直。判断そのもの（`should_probe` と 4 状態）は単体で押さえてある。

## 9. テスト

| 対象 | 内容 |
| --- | --- |
| 境界 | 1163 がデータグラムで通り、**1164 がストリームで通る**。どちらも届く |
| 最大 | 65507 が往復する。両方向で |
| 版 | 版 2 の相手に対して、1164 が落ちて数えられる（S1 の交渉が効いている）|
| 枠 | 同時実行の上限を超えたとき、落ちて数えられ、**小さいデータグラムは通り続ける** |
| 混在 | 大小を混ぜて送り、全部届く。順序は問わない（§3.2）|
| 経路移行 | リレー経路と直接経路の両方で、および移行をまたいで |
| セッション終了 | ストリームが飛んでいる途中でセッションが閉じたとき、受信側が
  組み立て中のものを捨て、`unknown_session` に数える |
| ローカル側 | 65507 をローカルのソケットに送る側（`socket.send`）が、
  ローカル経路の MTU でどう振る舞うか。**portal の責任の外だが、
  測って書いておく** |

「枠」と「混在」が中心である。**この計画の危険は、大きいものを運べるようにした
ことで小さいものが悪化することで**、それが起きる場所は送信側のチャネルと
受信側のキューの 2 箇所に絞れている（§2.3、§2.5）。
