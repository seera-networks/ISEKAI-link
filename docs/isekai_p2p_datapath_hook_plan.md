# isekai-p2p — データパスに割り込む仕組み

実装計画。対象は `channel-masque` / `isekai-p2p-core` と、それを使う
`portal-core` / `camera-core` のテスト。

`docs/portal_oversize_udp_plan.md` の未確認 8・10・11 が同じ壁で止まっている
ことから始まった。**調べたら、損失で解けるのは 10 だけだった**（§1.5）—
それでも作る理由は §1.5 の後半と §7 にある。

---

## 0. 何を決めたか

**内側 QUIC のパケットに、コードから割り込める継ぎ目を 1 つ作る。** 落とす、
遅らせる、見る。msquic が自分のテストに持っているもの
（`QUIC_TEST_DATAPATH_HOOKS`）と同じ役割を、**この workspace の抽象の側に**
置く。

| | |
| --- | --- |
| **置く場所** | トレイトは `channel-masque`（`run_bridge` が呼ぶので層としてそこ）、公開と道具立ては `isekai-p2p-core` |
| **運び手は 2 つ** | ①本物のリレー脚（`run_bridge`）②テスト用の素の UDP 中継 |
| **本番から到達できない** | 設定・CLI・環境変数からは作れない。コードだけ |
| **見えるのはリレー脚だけ** | 直接経路は継ぎ目を通らない。§3.2 |
| **`run_bridge` の継ぎ目は片側だけ** | 掛ける側の脚にしかない。§1.1 |
| **損失で閉じる問いは 1 つ** | 8 と 11 は偽の answerer 待ち。§1.5 |

**portal 専用にしない。** 落としたいのは内側 QUIC のパケットで、それは portal の
ものではなく `isekai-p2p` のものである。camera も同じ内側接続を使う。

## 1. 前提として確定していること

### 1.1 継ぎ目は 1 つしかなく、既にある

`channel_masque::masque::connect_udp::run_bridge(socket, tx, inbound, shutdown)`
（`connect_udp.rs:78`）。**内側 QUIC のパケットは、リレー経路では全部が両方向
ともここを `Bytes` で通る。**

```text
  上り  socket.recv_from  ──▶  tx.send(framed)
  下り  inbound.recv()    ──▶  socket.send_to(.., last_src)
```

本番のログがそれを裏付ける: リレー経路は
`local=127.0.0.1:37604 remote=127.0.0.1:42098` で、内側 QUIC はこの
ローカルソケット宛に送っている。

**ただし継ぎ目があるのは掛ける側の脚だけである。** `run_bridge` の本番の
呼び出し元は 1 つ（`channel-masque/src/lib.rs:855`、`start_connect_udp` の中、
`bind.rs:812` が組む connect leg）で、**待ち受ける側のリレー脚は
`MasqueClientMode::Forward`**（`bind.rs:586`）で、送信元ごとに転送する別の
経路を通り `run_bridge` を呼ばない。

リレー経路のパケットは全部が掛ける側の脚を通るので**損失注入は効く**が、
**「サーバが送るものを、サーバの送信として落とす」は表現できない。**
§2.4 の「フックを持てるのは `bind`」も connect leg についてだけ真である。

### 1.2 送信側はもうトレイトである

`pub trait DatagramTx { fn send(&mut self, datagram: Bytes) -> anyhow::Result<()>; }`
（`connect_udp.rs:29`）。`run_bridge` は `impl DatagramTx` を取るので、
**上りの差し替え口は既に空いている。**

### 1.3 H3 もリレーも無しで bridge を立てられる

`channel-masque` 自身のテストがもうやっている
（`bridge_records_source_and_replies_to_it`、`connect_udp.rs:164`）:
ソケット 1 つとチャネル裏打ちの `DatagramTx` で bridge が動く。
**トンネルを模すのに H3 は要らない。**

### 1.4 全部を継ぎ目に通すには、両端を黙らせる必要がある

直接経路は継ぎ目を通らない（§3.2）ので、テストは直接経路を作らせない。
`--relay-only`（`portal-client/src/main.rs:219`、`portal-server/src/main.rs:215`、
機構は `initiator.rs:637` の「`candidates` may be empty for relay-only use」）。

**片側では足りない。** `session.rs:249` がそれを測って書いている:

> **Both ends have to stay quiet for a session to really be relay-only.** A
> client that offers no candidate still gets a direct path if this side
> advertises one, because the advertisement is what makes the *peer* probe —
> measured: withholding the client's candidate alone left a path validated
> anyway.

**そして足りないときの失敗が黙っている。** クライアント側だけ黙らせたテストは
直接経路に移り、注入した `Drop` は 1 つも効かず、**「損失を扱えている」という
テストが損失を 1 度も注入せずに通る。** この数日に 3 回直したのと同じ形
（`portal_oversize_udp_plan.md` の上限テスト、stall テスト、空疎な
アサーション）なので、ハーネスが**両端の relay-only を要求する**こと自体を
H1 の仕事に入れる。

### 1.5 損失で解けるのは 1 つだけだった

**当初この節は「8・10・11 はどれも損失を注入できれば解ける」と書いていた。
2 つは解けない。**

| | 損失で解けるか |
| --- | --- |
| **10** `no-retrans` が損失で諦める | **解ける**（ただし §3.3 の段取りが要る）|
| **8** probe の無応答 → 学習 → 以後訊かない | **解けない**。下記 |
| **11** 「相手が受け取らない」ので落とす経路 | **解けない**。8 と同じ理由 |

#### なぜ 8 と 11 が解けないか

status は**信頼配送のストリーム**に乗る。パケットを落とせば再送されるので、
`read_status` が答を得ないのは `STATUS_DEADLINE` に当たったときだけである —
**20 秒**（`client.rs:23`）。つまり probe を無応答にするには、
**20 秒間すべてのパケットを落とす**必要がある。

ところが内側接続の `DisconnectTimeoutMs` は msquic 既定の **16 秒**で、
peer connection では上書きしていない（上書きは外側のリレー脚だけ、
`transport.rs:506`）。**接続のほうが先に死ぬ。**

そして `PeerOversize::NO` には**同じ接続で 2 回**の無応答が要る
（`udp.rs` の `learn_unanswered`、「一度は覚え、二度目で決める」）。1 回目で
接続が死ぬので、**2 回目は永遠に来ない。** `send_on_stream` の `Some(false)`
枝 — 11 がまさに走らせたいもの — は到達しないままである。

**8 と 11 には偽の answerer が要る**（元の計画がそう書いていた）。
ストリームをリセットさせる手があれば別だが、落とすことでは作れない。

**そして損失で解けるものは 10 だけ、では話が終わらない。** `docs/relay_repath_plan.md` の調査は、リレーを
**再起動して**損失と経路断を作っていた（§7.11 の窓、§5-7 の A/B）。あれは
「リレーが死ぬ」しか作れない道具で、**パケット 1 つを落とすことはできなかった**。
§5-11 が「1 回の走行から結論して 2 度撤回した」のは、作れる事象が粗すぎて
再現が運任せだったからでもある。

### 1.6 msquic 自身のフックは使える。使わない理由がある

`QUIC_TEST_DATAPATH_HOOKS`（`msquicp.h:64`）を
`QUIC_PARAM_GLOBAL_TEST_DATAPATH_HOOKS` で差し込める。**debug ビルドなら
実在する** — `#if DEBUG` でしか定義されない（`msquicp.h:77`）が、この
workspace の debug ビルドで `DEBUG` が立っていることは**既に観測済み**である
（`CLOG_FRAME_C` のフレームログが出た、`relay_repath_plan.md` §7.13）。

| | |
| --- | --- |
| **利点** | **直接経路も見える。** 継ぎ目は msquic のデータパスの中なので、リレーだろうが直接だろうが通る |
| 欠点 1 | **プロセス単位のグローバル**（`QUIC_PARAM_GLOBAL_`）。cargo のテストは 1 プロセスのスレッドで並列に走るので、**ある 1 本の損失注入が他の全テストに掛かる** |
| 欠点 2 | debug のみ。release の挙動はテストできない |
| 欠点 3 | private ヘッダの C API。msquic-async に面を足し、C の関数ポインタを `unsafe` で渡す |

**欠点 1 が決定的である。** テストが欲しいのは「この脚のこのパケット」で、
プロセス全体ではない。だから自前の継ぎ目を作る。**ただし利点は本物なので、
直接経路に割り込む必要が出たときの道はここだと §6 に残す。**

## 2. 設計

### 2.1 トレイト

```rust
/// 内側 QUIC のパケット 1 つに対する判断。
pub enum Verdict {
    /// そのまま通す。
    Pass,
    /// 落とす。送った側には何も返らない — それが損失である。
    Drop,
    /// この時間だけ遅らせて通す。
    Delay(Duration),
}

pub trait DatapathHook: Send + Sync {
    /// この端から出ていくパケット。
    fn outbound(&self, datagram: &Bytes) -> Verdict { Verdict::Pass }
    /// この端に入ってくるパケット。
    fn inbound(&self, datagram: &Bytes) -> Verdict { Verdict::Pass }
}
```

**`&Bytes` で、書き換えさせない。** msquic のフックは `_Inout_` で中身を
いじれるが、内側 QUIC のパケットは暗号化されていて、**書き換えて意味のある
ものは 1 バイトも無い**。落とす・遅らせる・数えるだけで、この計画の目的は
全部足りる。できることを増やすと、できることの説明が要る。

**両方向に既定実装を置く。** 片方だけ見たいフックがほとんどで、空実装 2 つを
毎回書かせる意味が無い。

**呼ぶ位置を決めないと、両方向が別のものを見る。** 上りの素直な位置では
バイト列は HTTP Datagram に framing された後で（`tx.send(frame_context0(..))`、
`connect_udp.rs:110`）context id の varint が頭に付く。下りの `inbound` から
来るものは**既に context を剥がされている**（`:64`）。サイズを見るフックは
1 バイトずれ、方向で構造が違う — §2.1 の「内側 QUIC のパケット 1 つ」と
食い違う。**framing の前で呼ぶ**のが筋だが、そこはデータグラムごとの
コピーが 1 回増える（§5 の費用の行がそれを測る）。

### 2.2 運び手 ①本物のリレー脚

`run_bridge` が `Option<Arc<dyn DatapathHook>>` を取り、上りと下りで 1 回ずつ
相談する。

- **`None` が既定で、見るのは `Option` の分岐 1 つ。** リレー脚はもともと
  データグラムごとに `recv_from` と `send` をしているので、ここに分岐 1 つが
  増えても測れる差にはならない（§7 で確かめる）。
- `Verdict::Delay` は後送りする。**順序は保証しない** — UDP は保証しないので、
  遅らせたものが追い越されるのは正しい。
- **上りの `Delay` は `run_bridge` の署名を変えないと書けない。**
  `tx: impl DatagramTx` は値で取られ、`'static` 境界が無く、`DatagramTx` は
  `Send` だけで `Sync` でも `Clone` でもない（`connect_udp.rs:29`, `:78`）。
  spawn した先に `tx` を借りることも持ち出すこともできない。
  `impl DatagramTx + 'static` にして `Arc<Mutex<_>>` にするか、転送チャネルを
  挟むことになる — **「上りの差し替え口は既に空いている」（§1.2）は
  `Drop` までで、`Delay` には当てはまらない。** 下りは `socket` が
  もう `Arc` なので問題ない。

**これは本物のリレー相手でも効く。** §1.5 の後半がそこで、`relay_repath_plan`
の調査が持っていなかった道具がこれである。

### 2.3 運び手 ②テスト用の素の UDP 中継

`isekai-p2p-core` に、**内側 QUIC 2 つの間に挟まるだけのもの**を置く。

```text
  内側 QUIC (client) ──▶ [ hop ] ──▶ 内側 QUIC (server)
                          │
                          └─ DatapathHook に相談
```

H3 も MASQUE もリレーも無い。ソケット 2 つと `DatapathHook` だけ。

**当初ここには「hop は両端のアドレスを与えられるので `last_src` の問いが
無い」と書いていた。違う。** クライアントの送信元ポートは一時的で、
`ConnectOptions`（`portal-core/src/transport.rs:88`）にローカル bind を
指定する口が無いので、**hop も最初の上りを見るまでサーバ→クライアント方向の
宛先を知らない** — bridge と同じである。

**どちらも無害で、理由は同じ**: QUIC はクライアントが先に喋る。それが
§6-1 の答でもある。

hop を選ぶ本当の理由は別である:

| | |
| --- | --- |
| **両端に継ぎ目がある** | `run_bridge` は掛ける側の脚にしか無い（§1.1）。hop は両方向を 1 箇所で見る |
| **H3 も MASQUE も要らない** | ループバックのテストは MASQUE を使っていないので、`run_bridge` を通すには偽のトンネルを立てる必要がある |

**トレイトは共通で、運び手が 2 つである。** それが「portal ではなく
isekai-p2p の仕組みにする」の具体形で、テストは hop を使い、実機の調査は
リレー脚を使う。

### 2.4 本番から到達できないこと

- **設定・CLI・環境変数からは作れない。** `Option<Arc<dyn DatapathHook>>` を
  渡す経路はコードだけで、`portal-server.toml` にも `--map` にも出さない。
- フックを**持てる**のは `run_bridge` を組む側（`isekai-p2p-core::bind`）と
  hop である。
- **feature の門は既にあり、しかも効いている。** `channel-masque` は
  `isekai-p2p-core` の**任意依存**で `msquic` feature の下にあり
  （`isekai-p2p-core/Cargo.toml:16`）、`bind`/`transport` も
  `#[cfg(feature = "msquic")]` である（`isekai-p2p-core/src/lib.rs:33` 以下）。つまりトレイトを
  `channel-masque` に置くと、**「ソケット 2 つとフックだけ」の hop が
  native msquic スタック込みでしか存在しない**ことになる。§6-2 はこれを
  踏まえて書き直した。
- **再公開は 2 段ではなく 3 段である。** `portal-core` が依存しているのは
  `isekai-p2p` で `isekai-p2p-core` ではなく（`portal-core/Cargo.toml:20`）、
  `isekai-p2p` は項目ごとに再公開している（`isekai-p2p/src/lib.rs:65` 以下）。H1 はそこにも
  面を足す。

---

### 3.3 「どのパケットか」はフックには分からない

§2.1 がフックを不透明にした（`&Bytes`、書き換えない）ことの裏側として、
**フックは目の前のパケットがどのストリームを運んでいるか分からない。**
暗号化されているので当然である。落とせるのは**数・位置・時刻**でしかない。

つまり 10 の「`no-retrans` のストリームを運ぶパケットを 1 つ落とす」は、
そのままでは表現できない。盲目に落とすと、ハンドシェイクや ACK や別の
ストリームに当たって意図しないものを壊すか、何も入っていないパケットに
当たって何も起きない。

**段取りが要る**: 接続を静める → 大きいデータグラムだけを送る → その直後の
上り N パケットを落とす。**H2 の仕事はフックを呼ぶことではなく、この段取りを
組むことである。**

## 3. やらないこと

| | 理由 |
| --- | --- |
| **パケットの書き換え** | 暗号化されていて、書き換えて意味のあるものが無い（§2.1）|
| **直接経路への割り込み** | 継ぎ目を通らない（§3.2）。必要になったら msquic のフック（§1.6）|
| **msquic のフックを今使う** | プロセス単位なので並列テストと両立しない（§1.6）|
| **設定から有効にできるようにする** | 本番で損失を注入できる設定は、あってよいものではない |
| **順序の保証** | `Delay` が追い越されるのは UDP として正しい |

### 3.2 見えるのはリレー脚だけ、を正確に

継ぎ目はリレー脚の上にある。**直接経路のパケットは msquic が自分のソケットで
送受信するので、1 バイトも通らない。** テストでは §1.4 のとおり候補を
広告しないことで全部を通すが、**本番のフックは「リレー脚のフック」である**。
それを「データパスのフック」と呼ぶと、いつか誰かが直接経路で試して困る。

## 4. フェーズ

### H0 — トレイトと `run_bridge` の分岐（運び手①）— **完了**

実装して分かったこと 3 つ:

- **`Verdict::Delay` は入れなかった。** §2.2 が言うとおり `run_bridge` の
  署名を変えないと書けず、**H2 も H3 も `Drop` しか要らない**。壊れたまま
  並べるより、要るときに足す（`Verdict` は 2 値）。
- **`&Bytes` ではなく `&[u8]` にしたら、F8 の非対称が消えてコピーも増えない。**
  上りの `&buf[..n]` は `frame_context0` の**前**の生のパケットで、下りの
  `payload` は context を**剥がした後**である。両方向が同じものを見る位置に、
  追加の確保なしで置けた。
- **カウンタは `hook_dropped` を新設した**（§6-4 の決着）。`up_dropped` は
  「トンネルが運ぶのを拒んだ — 普通は大きすぎるデータグラム」と文書化されて
  いるので、そこに入れると実機で oversize の診断が偽陽性になる。
  **0 のときは行の形も変えない**ので、普通の脚のログは 1 文字も変わらない。

`last_src` は**フックより先に記録する**。落とすのは「線の上で失われた」の
模擬で、パケットはこの端を出てこの bridge が見たのだから、送信元まで隠すのは
別のものを模擬することになる。

再公開は計画どおり 3 段（`channel-masque` → `isekai-p2p-core::bind` →
`isekai-p2p::agent`）。渡し口は `RelayOptions::datapath_hook` で、
**「脚をどう組むか」の構造体にあるのが筋**である。`RelayOptions` の構築箇所
6 つには `datapath_hook: None` を明示的に書いた — `..Default::default()` に
すると、次にフィールドが増えたときコンパイルエラーで気づけない。

テストは `channel-masque` に 3 本: 上りで落とせること（**offer されたのは
framed の 5 バイトではなく内側の 4 バイト**だとアサート）、下りで落とせること、
そして**全部通すフックが `None` と区別できない**こと — 分岐は本番の経路に
入っているので。



- `DatapathHook` / `Verdict` を `channel-masque` に定義し、
  `isekai-p2p-core` が再公開する（`bind.rs` が
  `pub use channel_masque::{InboundActivity, MasqueClientEvent}` で既にやって
  いる形）
- `run_bridge` が `Option<Arc<dyn DatapathHook>>` を取る。既定 `None`
- `bind.rs` が脚を組むときに渡せるようにする
- **テストはこの段では `channel-masque` の中だけ**（bridge の単体テストが既に
  あるので、そこに落とす・遅らせるを足す）

H0 単独で意味がある: 実機のリレー相手に損失を注入できるようになり、
`relay_repath_plan` の調査がリレー再起動以外の手段を持つ。

### H1 — hop（運び手②）

- `isekai-p2p-core` に hop を置く。2 つのアドレスとフックを取る
- `portal-core` のループバックハーネスが hop を張れるようにする
- **まだ既存のテストは変えない**

### H2 — 10 を閉じる（8 と 11 は閉じない）

`portal_oversize_udp_plan.md` の **10 だけ**を hop で書く。§1.5 のとおり
8 と 11 は損失では作れない。

- §3.3 の段取り（静める → 大きいのを 1 つ送る → 直後の上りを落とす）
- ハーネスが**両端の relay-only を要求する**こと（§1.4）。片側では
  注入が 1 つも効かないまま通る

**これが H0/H1 が正しいことの試験でもある** — 道具を作ったが使えなかった、が
一番ありそうな失敗である。

### H2' — 偽の answerer（8 と 11 のため、別物）

フックとは別の道具で、`read_open` を通さずに status を書く答える側。

## 5. テスト

| 対象 | 内容 |
| --- | --- |
| 通す | フックが `Pass` を返すとき、何も変わらない（既存の bridge テストが通る）|
| 落とす | 上り・下りそれぞれで、落としたパケットが相手に届かない |
| 遅らせる | `Delay` が指定の時間後に届く。追い越しが起きても失敗しない |
| 既定 | `None` のとき分岐が増えただけで挙動が同じ |
| 費用 | データグラムごとの `Option` 分岐、および §2.1 が framing 前で呼ぶならコピー 1 回に、測れる差が無いこと。**測ってから「無い」と書く**（`relay_repath_plan.md` §0.1.1）|
| hop | 2 つの内側 QUIC が hop 越しにハンドシェイクでき、フックが両方向を見る |

## 6. 未決事項

1. **bridge の下りは `last_src` を最初の上りから学ぶ**
   （`connect_udp.rs:105` で覚え、`:128` で使う）。
   運び手②を hop にしたのはこの依存を避けるためだが、**運び手①を
   テストで使いたくなったときには向き合うことになる**。本番では
   どちらが先に喋るかが決まっているのか、読んで確かめていない。
2. **トレイトをどこに置くか**、feature の門をどう扱うか。`run_bridge` が
   呼ぶので `channel-masque` が素直だが、そこは `msquic` feature の下にあり
   （§2.4）、hop までその門の内側に入る。候補は 3 つで、どれも決めていない:
   トレイトだけ門の外の小さなクレート（または `isekai-p2p-core` の
   feature 外のモジュール）に出す／hop を `channel-masque` に同居させて
   門を受け入れる／`run_bridge` 側はトレイトを使わず関数ポインタで受ける。
   **「本番バイナリがフックを持ち得ない」ことを門で保証したいかどうか**も
   同じ判断に乗る。
3. **`Verdict::Delay` の実装**。`tokio::spawn` で後送りすると、脚が畳まれた
   後に起きる送信が残る。`run_bridge` の `shutdown` に乗せるのが素直だが、
   遅延中のものを落とすか送るかは決めていない。
4. **フックが落としたものを `run_bridge` のどのカウンタに入れるか。**
   いまのカウンタには意味が書かれている（`connect_udp.rs:71`）: 
   `up_dropped` は「トンネルが運ぶのを拒んだ — 普通は大きすぎるデータグラム」、
   「上りがあって下りが無い」は「向こうが答えていない」。**フックの `Drop` を
   `up_dropped` に入れると、実機のリレー脚で oversize の診断が偽陽性になる**
   （§2.2 はこれを実機で使うと言っている）。`up` に入れても、数えなくても、
   「下りが無い」の読みが狂う。**別のカウンタを足すのが素直**だが、決めていない。
   テストが見たい「落とした数」はフックの実装側で数えればよく、それとは別の話
   である。
5. **hop をどこまで本物に寄せるか。** MTU を小さくする、片方向だけ詰まらせる、
   といったものは「損失を落とす」の先にあるが、**要るまで作らない**。

## 7. これが閉じるもの、開けるもの

**閉じる**（`portal_oversize_udp_plan.md`）:

- **10** `no-retrans` が損失で諦めること。**これだけである**（§1.5）

**閉じない**:

  到達できない（status は信頼配送で、20 秒の遮断が要るのに接続は 16 秒で
  死ぬ）

**開ける**:

- `relay_repath_plan.md` の調査に、**リレー再起動より細かい道具**が渡る（H3）
- 貼り直しの検証が損失に 1 回で死ぬ件（§7.13 で上流が直した）を、
  **こちら側から回帰テストにできる**
- 「窓」のような、作れる事象が粗くて再現が運任せだった調査の形が変わる

**開けないまま**: 直接経路。§3.2 と §1.6。
