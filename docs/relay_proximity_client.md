# 近い DP を選ぶ — 測る側

`relay_proximity_plan.md`（サーバ側の設計書）が決めているのは**形式と意味**であり、
§10.3 が「どう測るか — QUIC ハンドシェイクか軽量な UDP エコーか、何回測って何を取るか
（中央値か最小か）は**クライアント側の設計**である」と明示的に委ねている。本書はその
委ねられた部分の答えと、それを選んだ理由である。

CP 側（`GET /v1/peer/relays`、`PUT /v1/peer-listeners/{id}/relay-rtt`、
`endpoint_relay_rtt`、§6 の A/B/C 段）は ISEKAI-link-server に実装済みで、
本書は触れない。

## 1. なぜ端点が測るのか

CP は経路上に居ない。DP も相手側の経路を知らない。**実際のパスの上に立っているのは
端点だけ**である。だから当事者が測り、CP が選ぶ。

測定値はクライアント由来＝攻撃者制御下の入力だが、**候補集合は測定を読む前に第 1 段
（テナント境界）で確定している**ので、嘘は既にある候補の順序を入れ替えるだけで、
プールを広げない。嘘の被害は自分のセッションが遅くなること。設計書 §3.2 が受け入れた
例外は「相手も同じ DP を使うことになる」で、相手は既にその接続を認可しており、
`relay_base_url` で経由先を読める。

## 2. 何を測るか — H3 `GET /health`

relay の origin に対する HTTP/3 の `GET /health`。**脚が実際に張られるのと同じホストへ、
同じ QUIC スタックで**投げる。`/health` は relay の `serve.rs` で認証層の外側に
登録されていて、資格情報を要らない。

### 2.1 ハンドシェイクは数えない — 実測が根拠

最初の交換は QUIC ハンドシェイク・証明書検証・冷えた輻輳ウィンドウの代金を払う。
長命なリレー脚はそれを二度と払わない。**測りたいのは経路を「使う」費用であって
「張る」費用ではない。**

配備済みホストへの実測（`tokyo.link.isekai.tools:8443`）:

```text
#0  200 OK  56 ms   ← ハンドシェイク込み
#1  200 OK  13 ms
#2  200 OK  13 ms
#3  200 OK  13 ms
```

**ハンドシェイクが 43 ms、往復の 4 倍以上である。** これを数えれば、順位は経路の
近さではなく接続確立の重さで決まっていた。だから 1 回目は捨てる。

### 2.2 最小を採る

平均でも中央値でもなく**最小**。欲しいのは経路の下限であって、それを超える分は
キューイング・スケジューラ遅延・relay の混み具合であり、経路に属さない雑音である。
上の実測が 13/13/13 と揃っているのは、雑音が乗っていないときは何を採っても同じ、
という当たり前のことを言っているにすぎない。効いてくるのは揃わないときである。

## 3. 「測っていない」と「測ったが届かない」を混ぜない

設計書 §5 の中心。`rtt_ms: null` は**測ったが届かない**で、CP はその DP を
**そのセッションの候補から外す**。エントリを省くのは**測っていない**で、候補に残る。

実装では 2 つの制限時間がこの区別を担う。

| 制限 | 切れたら | なぜ |
| --- | --- | --- |
| `per_relay` | `rtt_ms: null` | その relay に公平な機会を与えて答えなかった。relay についての**判定**である |
| `budget`（ラウンド全体） | **報告に載せない** | ラウンドが打ち切られただけで、その relay について何も分かっていない |

**この 2 つを同じ扱いにすると、自分のネットワークが一瞬悪かっただけで relay を
黒穴と申告することになる。** 逆に、両方を「省略」にすると、落ちたノードをいつまでも
降ろせない。

### 3.1 打ち切りは、既に測れた分を捨ててはならない

**最初の実装はここを間違えた。** `per_relay` の打ち切りがプローブ全体を包んでいたので、
**答えたのに打ち切られた relay が `null`（＝不到達）として報告されていた。**
`null` はセッションの候補からその relay を外す唯一の判定である。

数字で言うと悪い。ハンドシェイクが約 3.3 RTT、プローブ 2 回で合計およそ 6.3 RTT。
initiator の `per_relay` は 1.2 秒なので、**RTT がおよそ 190 ms を超える relay は
すべて「不到達」にされていた** — 大陸をまたぐノード、つまり近接選択が存在する理由
そのものである。プール全体がそこより遠ければ、候補は空になる。

**遠いことは、無いことではない。** 直したのは、実測を確定するたびに共有セルへ
書き出す形にしたこと。打ち切りは進行中のプローブを切るが、**既に着地した測定は残る**。
セルが最後まで空のままだったときだけ `null` になる — それが `per_relay` の本来の意味
（公平な機会を与えて何も答えなかった）である。

### 3.2 全部 `null` なら、それは自分の話

1 ラウンドの結果が全て `null` なら報告しない。**「どの relay にも届かない」は
この端末についての言明であって、プールについてではない。** 数秒の回線の乱れで
簡単に起きるし、報告すれば良好な集合が「全ノード除外」に置き換わり、CP はこの
テナントのプールを 30 分ものあいだ丸ごと飛ばす（接続が失敗するわけではない —
サーバは運用者プール、次いで CP 自身へ落ちる — が、遠回りにはなる）。
短い間隔で測り直す方が正しい。プールが本当に消えたのなら、保存された行は
自分の窓で失効する。

プローブは並列で、**届かない 1 台がラウンド全体の予算を食い潰さない**。プールは
一様に健全ではないので、これが無いと壊れた relay を 1 台足しただけで全ての測定が
未完了になり、選択はどこでもプール順に戻る。

## 4. いつ測るか

| 当事者 | どこで | 周期 |
| --- | --- | --- |
| **target**（Listener） | `PUT /v1/peer-listeners/{id}/relay-rtt` | 30 分 |
| **initiator** | `connect` 要求本文 | その 1 回、`connect` の直前 |

**target が先に居ることが、この機能の成立条件である。** relay が決まるのは
initiator の `connect` の 1 回きりで、そのとき target は居ない。Listener は接続より
前から存在するので、先に測っておける。

Listener のリースに相乗りはできない（設計書 §4.1）。`/events` を開いたままの
Listener は作成後に Listener 経路を呼ばないので、載せる先が無い。だから
`RelayRttReporter` は自分のタスクと自分の周期を持つ。

### 4.1 30 分 — 鮮度窓の半分

サーバの `RELAY_RTT_RETAIN_SECS` は 1 時間。**窓ちょうどで報告すると隙間が保証される**:
行が失効するのと入れ替えを測っているのが同じ瞬間になり、その間に来た接続は
「一度も報告が無かった」のと同じに扱われる。だから半分。このコードベースの他の更新が
すべて何かの半分であるのと同じ理由である。

> **これはサーバの定数を写したもので、教えてもらっているのではない。**
> `GET /v1/peer/relays` は窓の長さを言わない。サーバ側が窓を縮めたらここも追随が要る。
> 追随し損ねると、報告は届いた時点で既に陳腐化していて、**選択は黙ってプール順に
> 戻る** — 壊れ方が静かなので、書いておく。

**失敗したラウンドは 30 分待たない。** 60 秒で試し直す。半分という周期は
「前回がまだ生きているうちに次を届ける」ための余裕であり、**失敗のあとにその余裕を
丸ごと使ってしまっては意味が無い。** 特に最初のラウンドが失敗した Listener は、
それでは 30 分ものあいだ何も公表しないことになる。

### 4.2 initiator は待たせない

`connect` の直前に入るので、ここは人が待っている。プローブ 2 回・relay あたり 1.2 秒・
ラウンド全体 1.5 秒。**間に合わなかったものは省略される**ので、予算が厳しいときの
劣化は「target の測定だけで決まる」（設計書 §6 の B 段）であって、誤った答えではない。

**予算は候補一覧の取得も含む。** 制御プレーンのトランスポートは要求ごとの
制限時間を持たないので、応答が返らなければ QUIC の 30 秒アイドルタイムアウトまで
待つ — この経路が約束している遅延の 20 倍である。予算の半分を一覧に、残りを計測に割く。

測定に失敗しても接続は続く。測定は「どの relay になるか」の最適化であって、
接続の前提条件ではない。

## 5. 古い proxy に当たったとき

`GET /v1/peer/relays` が **404** を返す proxy — この機能より前の配備すべて — では
`list_relays` が `Ok(None)` を返す。**これは異常ではなく配備についての事実**である。
エラーにすると、Listener はプロセスの生涯にわたり 30 分ごとに失敗を記録し続ける。

`Some(vec![])`（空）は別の、後の状態である: proxy は relay を選ぶが、登録が 1 台も無い。

実配備で確認済み — `portal-client --relays` が
`This proxy does not choose relays by proximity.` と答える。

## 6. どのアドレスファミリーで繋ぐか

**近さとは別の問いが 1 つ乗っている。** リレーをどれにするかは RTT が決めるが、
**両端がそのリレーに繋ぐアドレスファミリーが揃っていないと direct path は成立
しない**。レグ 1 本は未接続ソケット 1 つで、それはファミリー 1 つ、つまり候補 1 つ
だからである（詳細は `relay_address_family_plan.md`）。

片端が IPv6 で、相手が IPv4 で同じリレーに繋いだセッションは、リレー経由では
成立するのに direct path に一度も移らない。

### 6.1 レグと同じ叩き方で測る — ここを間違えていた

RTT のプローブ（§2）は `MasqueH3Transport::connect`、つまり**接続済み**ソケットで
動く。レグは**未接続**ソケットを使う。そして **CLAT/464XLAT のホストでは
この二つが違う** — 接続済みソケットは変換器を通り、未接続ソケットは通らない
（isekai-link#213）。

接続済みで測れば「v4 は使える」と答え、レグは同じ v4 で**使えない**。
したがってファミリーの測定は**未接続ソケットで別に行う**。叩く先は `/health` の
ままで、変わるのは叩き方である。

### 6.2 要求したファミリーではなく、着地したアドレスを読む

指定は**優先**であって制約ではない。`AAAA` を持たない名前に v6 を指定しても、
v4 で繋がって 200 が返る。要求したファミリーを信じると**A のみのリレーを
`[v4, v6]` と報告**し、制御プレーンが v6 を共通ファミリーに選び、レグはどこにも
行けなくなる。

> **これは実配備で現に起きた。** 2026-11-01 の測定で、v6 を要求したプローブは
> 両リレーで **v4 のアドレス**を返した。着地を読んでいなければ誤報告していた。

接続済みソケットに差し替わった場合も同じで、コネクタが報告する
`Binding::Connected`（CLAT スタブ／routable 無し／QMUX フォールバック）は
**どれも「レグの未接続バインドでは再現できない」**ので、ファミリーを主張しない。

### 6.3 申告は肯定のみ

```json
"relay_reach": [
  { "dp_id": "dp_1", "families": ["v6", "v4"] },
  { "dp_id": "dp_2", "families": ["v6"] }
]
```

**列挙されたファミリーは「測って使えた」の意味だけを持つ。** 「使えない」は
送れない — initiator の収集期限（予算の半分）では、`per_relay` で初めて確定する
「到達不能」が捨てられて**省略**になるからで、省略は「未測定」である。
§3 の「混ぜない」と同じ規律が、ここでは否定的証拠を**出さない**形になる。

- **送るリストは本質的に部分的である。** 測れなかったリレーは列から落ちるので、
  3 リレーのうち 1 本だけ間に合わなかったラウンドでは 2 本だけが届く。RTT は
  接続済みソケットで QMUX フォールバックも通るのに、ファミリーは未接続バインドで
  しか数えないので、**「RTT は良好・ファミリーは空」は普通に起こる** — 部分的な
  リストは例外ではない
- だから制御プレーンは **`dp_id` 単位でマージ**する（集合全体の置き換えではない）。
  含まれない `dp_id` は触らない。置き換えだと、間に合わなかったリレーの以前の
  申告が毎ラウンド消える
- **1 つも測れなかったラウンドはフィールドを省く。** マージなら空配列も無害なので
  これは**保険**で、置き換えで実装された相手に当たっても壊れないための用心である

### 6.4 訊くのは選ぶ余地があるときだけ

**名前が解決しないファミリーは訊かない。** 解決結果にそのファミリーのアドレスが
無ければ `first_routable` はハンドシェイク前の route test で落ちるので、訊く
コストはほぼゼロ — 実測でも v6 を要求したプローブは v4 を要求したものより速かった。
それでも訊かないのは、**安い方を消しても高い方が残る**からである。

残る高コストは「解決できるが UDP が黒穴」で、これは `per_relay` を丸ごと使う。
**DNS はこれを予言しない** — 解決できると分かることは、むしろ「訊く対象になる」
という意味である。これを縛っているのは解決ではなく**期限**で、観測全体が予算で、
1 リレーが `per_relay` で切られる。

| | プローブ本数 |
| --- | --- |
| シングルスタックのリレー | 1 本（listener）／**0 本**（initiator — 選ぶ余地が無い） |
| デュアルスタックのリレー | 2 本、並行 |
| **名前が解決できなかったとき** | **2 本**（両方訊く） |

最後の行が「0 本」でないのは意図したものである。URI が parse できない、
リゾルバがエラーを返す、1 件も解決しない — いずれも**両方訊く**。DNS の一時障害で
観測が黙って止まるより、訊いてプローブ側で失敗する方がよい。ただし
**その間 initiator は 1 リレーあたり 2 本引く**ので、安いのは通常時だけである。

initiator が 0 本なのは、片方のファミリーしか持たないリレーには**選ぶ余地が無く**、
報告しても制御プレーンが自分のプールから分かること以上を与えないからである。
**現配備のリレーは A レコードのみ**なので、これは特殊ケースではなく通常の経路である。

### 6.5 答えは 2 箇所で読む

```json
{
  "relay": { "masque_uri": "https://…", "family": "v6" },
  "relay_base_url": "https://…",
  "relay_family": "v6"
}
```

**listener は `relay` を読まない**（`relay_base_url` を直下から取る）ので、
同じ値が 2 箇所に乗る。そして**両端が両フィールドから計算する** — 制御プレーンが
片方だけ埋めた段階的ロールアウトで、片端だけが制約されるのを防ぐためである。
**片端だけが選ぶのは誰も選ばないより悪い**: 揃わなければならないのは組だからで、
initiator が v6 に固定され listener が v4 を選べば、不揃いのまま片方が制約される。

| `relay.family` | `relay_family` | 結果 |
| --- | --- | --- |
| 無 | 無 | 無制約 |
| `"v6"` | 無 | v6（片方でも明確な指示） |
| `"v6"` | `"v6"` | v6（通常） |
| `"v4"` | `"v6"` | **無制約**（矛盾。相手がどちらに従うか分からない） |

知らない綴りは「無」と同じに扱い、`warn!` を出す。**制御プレーンが新しいことは
接続を失う理由ではない。**

### 6.6 要件ではなく優先 — これは退行防止の条件である

名指されたファミリーに routable なものが無ければ、**無制約に戻して続ける**。
報告した時点では使えたのだから、ここに来るのは経路が変わった後である。

**これを硬い要件として実装してはならない。** `relay_reach` は肯定のみで撤回する
手段が無いので、制御プレーンは古い証拠からファミリーを選び得る。硬い要件だと、
以前は「省略 = 無制約」で繋がっていた端が**繋がらなくなる** — 失うのは direct path
ではなく**セッションそのもの**である。

> 固定しているテストは `h3-util/tests/prefer_family.rs` の
> `an_unroutable_preferred_family_falls_through`。**別実装がこの仕組みに乗るとき
> 最初に確認すべき 1 本。**

フォールバックした端は繋がるが、その場合 direct path は再び揃わない。

**そしてこの指定が効くのは未接続のレグだけである。** アドレスを選ぶのは
コネクタの未接続モードの中だけで、接続済みソケットでは msquic が `start` で
自前に解決し、優先は参照されない。`RelayOptions { unconnected: false }` で
開いたレグ — migration を切った `isekai-client-ffi` — は、**相手が従っていても
合意したファミリーを落とす**。そのレグには direct path が無いので害は無いが、
「合意された」と「適用された」は別の事実で、応答から見えるのは前者だけである
（該当時は `debug!` が出る）。

### 6.7 リレー選択との関係

ファミリーは**同点の決め手**であって、ハードフィルタではない。共通ファミリーを
持たないリレーを候補から外すことはしない — 共通が無いならリレー継続が正しい答えで
あって、選ばないことではないからである。

RTT より優先もしない。`relay_reach` は肯定のみで「共通が無い」は取りこぼしでも
起こるのに対し、RTT はそのラウンドで測った数字であり、**弱い証拠で強い証拠を
覆すのは順序が逆**である。リレー経由は常に動き、direct path は成立しない場合が
ある（NAT、CLAT、msquic の単一候補）。

## 7. 見るための口

```sh
portal-client --relays
```

```
rtt            families probe              dp_id                        base_url
12 ms          v4       v4=85              dp12619d3abf75e16b138        https://…
115 ms         v4       v4=397             dp19145ad90467ce86d86        https://…
not measured   ?        -                  dp_frankfurt_1               https://…
```

> 上の `probe` は **§6.4 が効いた後**の実行のもので、A のみのリレーなので 1 本
> しか引いていない。`relay_address_family_plan.md` §8.1 が記録している
> v4 107–135ms / v6 82–115ms は、**両方訊いていた頃**の同じリレーの値である。
> 片方しか出ていない行は「もう片方が遅い」ではなく「訊いていない」。

候補と実測を出す。3 状態を潰さずに表示する（`12 ms` / `unreachable` /
`not measured`）。**「なぜ自分の接続はあの relay を通ったのか」は運用で必ず訊かれる**
ので、選択が乗っている数字そのものを見せる。

`families` は §6 の未接続プローブが答えたファミリー、`probe` はそれに掛かった時間
（ファミリーごと、ミリ秒）。**`families` が `none` は「どちらも駄目」ではない** —
無応答・接続済みへのフォールバック・アドレス読み取り失敗がすべてここに来るので、
`probe` と並べて初めてどれなのかが分かる。

> **この列があるので、リスナーを配備して 30 分待つ必要がない。** 同じ観測を
> オンデマンドで走らせるため、`relay_address_family_plan.md` §8.1 の実測は
> このコマンド 1 本で採った。

## 8. 測っていないもの

1. **デュアルスタックのリレーが本当に両方の未接続ソケットで応答するか。**
   §6 の仕組みは全部入っているが、**現配備のリレーは A レコードのみ**で、
   検証する対象が存在しない（`relay_address_family_plan.md` §8.1）。
   リレーが片方のファミリーしか持たないなら揃えるべき不一致も無い。
   今日 IPv6 で繋ぎに行く先は制御プレーン自身のデータパスで、それは別の持ち場である
2. **relay の健全性。** 到達不能の申告はそのセッションに閉じてあり（設計書 §5.1）、
   他のセッションの選択には影響しない。死んだノードは新規セッションに選ばれ続ける
3. **セッション途中の乗り換え。** 選択は `connect` の 1 回きり。ファミリーも
   同じで、途中で使えなくなっても再交渉しない — §6.6 のフォールバックがあるので
   「繋がらない」にはならないが、**その場合 direct path は再び揃わない**
4. **`spki_sha256` の照合。** 候補は pin を運んでくるが、プローブは使っていない。
   `/health` は資格情報を運ばず 1 語を読むだけなので、経路上の攻撃者にできるのは
   relay を速く/遅く見せることだけ — それは報告側が手で書けることそのもので、
   **設計書** §3.1 の枠内に収まる。**照合するなら、それは pin の配布を信頼する
   別の話になる**
