# camera-server / camera-client 仕様

対象コミット時点の実装を記述したものであり、計画ではなく**現状**である。挙動を
変えたときは、この文書も一緒に変えること。

- 実装: `rust/camera-server`（配信側）、`rust/camera-client`（視聴側）
- 共有部分: `rust/camera-core`（映像トランスポートと P2P の配線）、
  `rust/camera-ui`（両アプリが出す画面）
- ビルド手順: [`Build.md`](Build.md)。この 2 つだけが OpenCV と libclang を必要とする
- 関連: [`p2p_mode_migration_plan.md`](p2p_mode_migration_plan.md)（直接経路への移行）、
  ISEKAI-link-server の `docs/p2p_connect_spec.md`（プロキシ側の規定。以下 §
  番号はこれを指す）

---

## 1. 全体像

どちらも eframe/egui のデスクトップアプリで、**カメラ映像を MJPEG で 1 対多に
配信する**ことだけを行う。認証・接続の仲介・リレーは ISEKAI link のサービス側が
持ち、アプリはその利用者である。

```
camera-server                                          camera-client / iOS
 ├ カメラ捕捉 (OpenCV)                                   ├ 受信・デコード (OpenCV)
 ├ 映像 QUIC リスナ  ◀────── リレー or 直接経路 ──────▶  ├ 映像 QUIC 接続
 └ Peer Listener ─┐                              ┌─ Peer Connection
                  └──── ISEKAI link Proxy ───────┘
                                │
                         Identity API (Auth0)
```

### 1.1 2 つのモード

両アプリとも起動時に選ぶ。

| | Direct | P2P |
| --- | --- | --- |
| 到達方法 | プロキシが払い出した公開アドレスへ直接 | プロキシ経由（公開アドレス不要） |
| 認可 | JWT を手で渡す | Endpoint 登録 + Grant / Capability |
| 位置づけ | 旧方式。残置 | **現行**。以下は特記なき限り P2P を指す |

Direct は `camera-server` が MASQUE で公開アドレスと証明書を受け取り、
`camera-client` がそこへ直接 QUIC で繋ぐ。P2P はプロキシが接続を仲介し、
リレー経由で始まり、可能なら直接経路へ移る（§1.4）。

### 1.2 映像トランスポート（共通・`camera-core/src/video.rs`）

| | |
| --- | --- |
| プロトコル | QUIC、ALPN `sample` |
| 単位 | **1 フレーム = 1 本の単方向ストリーム**。JPEG をそのまま載せる |
| 順序 | ストリーム ID を連番として扱う。**最新のみ表示**し、遅れたフレームは捨てる |
| MTU | `MaximumMtu` 1248（msquic の下限。CONNECT-UDP 化して外側に収まる大きさ） |
| アイドル | 30 秒。ハンドシェイクのみ 60 秒 |

**最新が勝つ。** 追いつけない視聴者にはキューを積まず、次に受け取れるときの
最新フレームを渡す。ライブ映像では貯めたフレームは遅延でしかなく、遅い視聴者が
他の視聴者や accept ループを止めてはならない。

### 1.3 認証（両アプリ共通）

1. **Auth0 サインイン** — デバイス認可グラント（RFC 8628）。短いコードを画面に
   出し、操作者が任意のブラウザで入力する。得た refresh token で以後は自動更新
2. **Endpoint 登録** — 端末ごとの ECDSA P-256 鍵。公開鍵から Endpoint ID を導出
3. **Endpoint Token** — Identity API が発行。**数分で失効する**ため、セッション中
   自動で再発行する（§5.3 が発行のたびに Auth0 認証状態を要求するので、1 の
   自動更新が前提になる）

手貼りの Auth0 アクセストークン欄も残っているが、期限切れ後は更新できない。

### 1.4 経路（P2P モード）

リレー経由で始まり、双方が相手の観測アドレスを広告して直接経路を試みる。
**multipath を使い、両経路をアクティブに保つ**（`p2p_mode_migration_plan.md`
リスク #24）。

- 直接経路が検証されると `PathAdded` が上がり、**まず backup として保持**される
  （宣言するまで通信は流れない）
- 視聴者が切り替えを要求すると、relay を backup、direct を available と宣言する。
  **リレー経路は破棄されず**、経路ごとの keepalive で温存される
- 直接経路が確立した後の映像はリレーを通らない。確立可否は双方のネットワーク次第
- multipath 非対応の相手には従来の切り替え（`activate_path`）にフォールバックする

経路ごとの keepalive（10 秒、両端が設定する）は、経路を腐らせないためのものだが、
**カメラが視聴者の生存を知る唯一の手段でもある**。直接経路へ移った後にリレーレグを
まだ通っているのはこの PING だけで、§2.5 の判定がそれに乗っている。

広告するアドレスは**その視聴者のレグのもの**でなければならない。レグは視聴者ごとに
あり、それぞれ別のバインディングを持つので、他人のレグを渡すと相手が到達できない経路を
広告することになる（症状は「その視聴者だけリレーのまま」で、何も言わない）。どのレグから
来た接続かは、**接続元アドレス**で分かる — レグは受け取ったものを自分のソケットから
映像リスナへ転送するので、そのソケットのアドレスがレグを名指しする（`LegDirectory`）。

## 2. camera-server（配信側）

### 2.1 やること

1. カメラから捕捉し JPEG に符号化する
2. 映像 QUIC リスナを localhost に立てる
3. Peer Listener をプロキシに作り、リレーのバインドレグを張る
4. 接続してきた視聴者へフレームを配る

### 2.2 捕捉

| | |
| --- | --- |
| 取得 | OpenCV `VideoCapture`。**どの端末を使うかは選べる**（下記） |
| 解像度 | 640×480。選べない |
| 間隔 | 約 33 ms（≒30 fps）。取得失敗時も同間隔で待って再試行する |
| 符号化 | JPEG、品質 80 |

捕捉は専用スレッドで回り、配信中でなければ送信しない。

**カメラの選択**（`camera-server/src/capture.rs`）。内蔵カメラの隣に USB カメラを
挿した端末で、どちらを配信するかを決められる。

| | |
| --- | --- |
| 一覧 | ドロップダウンを開いたとき、および Scan ボタンで走査する。**装置を実際に開いて確かめる**ため時間がかかるので、ワーカースレッドで行う |
| 候補 | Linux は `/sys/class/video4linux` が挙げるものだけ（名前も取れる）。他は index 0〜4 |
| 手入力 | 一覧に出ない装置のために index を直接指定できる。確定は入力を終えたときで、途中の値では切り替わらない |
| 切替 | 配信中でも可。捕捉スレッドが次の周回で開き直す |

走査は**操作者が一覧を求めるまで行わない**。装置を開くことが答えである以上、起動しただけで
開くと、カメラに許可が要るプラットフォームでは誰も何もしていない時点で許可を求め、
インジケータが点くことになる。

**一覧は目安であり、選択できる範囲ではない。** 何が繋がっているかを移植性のある形で
問い合わせる方法は無いので、装置が使えるかどうかを決めるのは開いてみることであり、
その結果は画面に出る（開けない／別のアプリが掴んでいる、は普通に起きる）。開けない間は
0.5 秒ごとに試み続けるので、挿し直せば操作なしで復帰する。

### 2.3 視聴者の受け入れ（AcceptPolicy）

| | |
| --- | --- |
| `Auto` | プロキシが Grant を確認済みなので、そのまま束ねる |
| `AutoNotify` | 同上、かつ操作者に見えるよう通知する。**GUI が使う既定** |
| `Manual` | 自動では何も束ねない。操作者が接続 ID を受け取って束ねる |

同時に serve する視聴者数の上限は **8**（`MAX_CONCURRENT_PEERS`）。超えた相手は
待機として報告され、レグが空き次第束ねられる。

### 2.4 Listener のリースを保つ

Peer Listener には期限があり（作成時の `ttl`、既定 3600 秒）、過ぎると制御プレーン
から消える（§8.2.4）。**このアプリは延長を明示的に要求しない。** 延長は owner 自身が
その Listener を読むたびに起きる（§8.2.5）ためで、配信中のカメラは次を叩いている。

| | |
| --- | --- |
| 接続一覧の poll | ストリームが無いとき 3 秒ごと、あるとき 60 秒ごとの控え |
| イベント購読 | 購読時、および保持中もリースの半分ごと |

つまり**配信していれば勝手に延びる**。ここに手当てが要るのは §4 の `Manual` の
場合だけである。

> 以前はこの延長が存在せず、配信中のカメラが 1 時間で Listener を失い、接続と
> リレーエッジを道連れにして映像が止まっていた
> （[ISEKAI-link-server#215](https://github.com/seera-networks/ISEKAI-link-server/issues/215)、
> [#216](https://github.com/seera-networks/ISEKAI-link-server/pull/216) で解決）。

### 2.5 接続のリースを更新する — 運んでいるレグだけ

Peer Connection にも別の期限がある（プロキシの connect TTL、既定 300 秒）。
Listener のリースと違い、これは**明示的に更新しなければ切れる**（§8.5.4）。
リレーエッジも同じ期限を共有するので、切れれば映像も止まる。

カメラは 60 秒ごとに更新するが、**その時点でレグに何か届いているものだけ**を更新
する（`ListenerSession::renew_connections`）。レグを抱えていること自体は相手が
まだ居る証拠にならない — レグが落ちるのは相手が `closed` を報告したときで、
Ctrl+C で殺された相手は何も報告しないからである。

| 判定 | 根拠 |
| --- | --- |
| 何か届いている | 更新する。相手が居る |
| 前回のパスから何も届いていない | **更新しない。** TTL で失効させる |

判定は「レグごとの受信データグラム数が前回のパスから増えたか」だけで、時計も
「何秒無音なら死」という閾値も使わない。

リレー経由の間は映像そのものが届く。**直接経路へ移った後も届く** — リレー経路は
破棄されず backup として残り（§1.4）、経路ごとの keepalive が 10 秒ごとに PING を
流すためである。両端が `PathKeepAliveIntervalMs` を持っており、視聴側は
`camera-core` の `DIRECT_PATH_KEEPALIVE`、カメラ側は `isekai-link-utils` の
`PATH_KEEP_ALIVE_INTERVAL_MS`（どちらか一方でも落とすと、視聴中の相手が TTL 後に
切られる）。multipath 非対応の相手は PING を出さないが、その相手はリレーを離れて
いないので映像そのものが届いている。

相手が消えれば keepalive 間隔のうちに届かなくなり、更新が止まり、接続は自分の
TTL で失効する。`state=relay` の一覧から消えるので、カメラはレグを落として枠を返す。
**Ctrl+C も `kill -9` もクラッシュも回線断も、プロキシから見れば同じ「誰も更新
しなかった」**であり、区別する仕組みは要らない。

> 以前は抱えているレグを全部無条件に更新していたため、TTL が発火せず、消えた
> 視聴者のレグが永久に残った。8 本溜まると `MAX_CONCURRENT_PEERS` に達し、次の
> 視聴者は待機のまま繋がらなくなる（#105、[#106](https://github.com/seera-networks/ISEKAI-link/pull/106) で解決）。

視聴側も同じ接続を自分で更新する（§3.4）。**両側から更新される**が、押し出す先が
同じ期限なので二重に効いても害は無い。

### 2.6 映像 TLS の鍵と証明書

映像 QUIC が提示する証明書のための鍵は、**この端末で生成し、外へ出さない**。

| | |
| --- | --- |
| 鍵 | 初回起動時に生成（P-256）、`0600` で保存、以後**使い回す** |
| 送るもの | 証明書要求（CSR）だけ。公開鍵と名前であって、鍵ではない |
| 名前 | `GET /v1/peer/certificate/parameters` が返す `hostname` を**そのまま**使う。ドメインはプロキシの設定であり、こちらでは導出できない |
| 確認 | 発行された証明書の `spki_sha256` が手元の鍵のものと一致することを確かめてから使う |

**なぜ鍵を渡さないか。** リレーは映像 QUIC の暗号文をそのまま中継する。その鍵を
プロキシが生成して配る限り、プロキシは同じ区間の暗号文と鍵の両方を持つ — つまり
リレー区間の暗号化は、プロキシに対しては保護になっていない。

鍵を使い回すのは、新しい鍵が**発行枠を 1 つ消費する**ため（7 日あたり 5 回）。同じ鍵で
要求すればプロキシはキャッシュした証明書を返し、CA に問い合わせない。再起動しても
証明書を取り直さないのはこのためである。

Endpoint 鍵とは**別の鍵**にしている。あちらは署名専用の識別鍵で、QUIC スタックに
渡す必要がなく、用途の違う鍵を使い回すこと自体が事故のもとであるため。

> **移行中の挙動。** CSR 経路を持たない古いプロキシに対しては、旧
> `GET /v1/peer/certificate`（プロキシが鍵を生成して配る）に落ちる。そのとき鍵は
> プロキシも持つことになるので、警告を毎回出す。証明書が一切無いより良い、という
> 判断である — 証明書が無ければ相手は検証を省くしかなく、第三者でも成りすませる。

## 3. camera-client（デスクトップ視聴側）

### 3.1 やること

1. 接続できるカメラを一覧する
2. 選んで接続し、映像 QUIC を張る
3. フレームを復号して表示する
4. 経路（リレー／直接）を選ぶ

### 3.2 カメラの一覧

プロキシに問い合わせ、**カメラ 1 台につき 1 行**を出す。Grant は Endpoint に
対するものなので、プロキシは同じ Endpoint の Listener を全部返す。落ちた
camera-server はリースが切れるまで繋がらない Listener を残すため、**同じ owner
では `expires_at` が後のものを採る**（`camera-core/src/cameras.rs`。前提と限界は
そこに書いてある）。この判断は iOS ビューアと共有しており、2 つ書いて食い違うのを
避けるために `camera-core` に置いてある。

一覧に出ないカメラのために、Listener ID と Capability の手入力も残してある。

### 3.3 ペアリング

カメラが表示したコードを入力すると Grant ができ、以後は一覧に出る。
Grant はカメラの Listener ではなく owner に属するので、カメラ側が Listener を
作り直しても有効なままである（§8.8）。

### 3.4 自分の接続のリースを更新する

視聴側は、自分が張った Peer Connection のリースを自分で更新する
（`InitiatorSession`）。§2.5 と同じ期限を押し出す作業だが、こちらは**主張できる
側がしている**という位置づけである — 「まだ使っている」と言えるのは使っている
本人だけで、カメラからは相手がまだ見ているかどうか分からない。

更新間隔は**サーバの応答から測る**。応答に載る `expires_at` と `updated_at` の差が
リースの長さなので、その 1/3 を空けて次を打つ（10〜60 秒にクランプ）。どちらも
サーバ側の時刻なので、**端末の時計がずれていても間隔は変わらない**。プロキシの
`--p2p-connect-ttl-secs` を写した定数はこちらに置かない。

重要なのは**止まり方**である。更新はセッションが持つタスクで、セッションが落ちれば
中断される。つまり切断でも、Ctrl+C でも、`kill -9` でも、クラッシュでも、回線断でも
更新は止まり、接続は TTL で失効する。**報告は要らない。**

> 以前はカメラ側だけが更新しており、視聴者が消えてもリースが押し出され続けていた
> （§2.5 の注記、[#104](https://github.com/seera-networks/ISEKAI-link/pull/104)）。

`closed` の報告前に更新を止める。終端状態への報告は拒否されるので、後ろから届いた
更新は失敗として記録されるが、それは順序の問題でしかない。

### 3.5 画面

| 区画 | 内容 |
| --- | --- |
| プライバシーポリシー | 初回起動時のみ（§5） |
| 接続設定 | Identity URL / Proxy URL / Auth0 サインイン / 鍵のパス / プロトコル |
| Cameras | 接続できるカメラ、ペアリング、更新 |
| 経路 | リレー／直接それぞれのアドレスと、現在どちらを使っているか、切替 |
| RTT | 1 秒ごとの往復時間を折れ線で表示 |
| 映像 | 受信中のフレーム |

サインイン済み、または Auth0 トークンが入力済みになった時点で、一覧を自動で
取得する。押さないと "none" のままになるのを避けるため。

### 3.6 端末に置くもの

`camera-client-endpoint.pem` と `camera-client-auth0.json`。役割と扱いは §2.8 と
同じ。

## 4. 既知の制約

実装が意図してそうなっている、または直っていない事項。

- **`AcceptPolicy::Manual` では Listener のリースも接続のリースも切れる。** 前者は
  owner 自身の読み取りで延びる（§8.2.5）が、`Manual` では poll もイベント購読も
  走らないため、それを叩くものが無い。後者も同じ理由で、§2.5 の更新は poll が
  記録した接続を辿るので、**手で bind した接続は一度も更新されない**。既定の
  `AutoNotify` ではどちらも起きない。`Manual` を使うのは試験用の例だけなので
  実害は無いが、常駐させるなら手当てが要る
- **動いているが送っていない視聴者は切られる。** §2.5 の判定はトラフィックなので、
  プロセスが生きていても送信が止まれば TTL で失効し、レグと枠が返る。§8.5.4 が
  数えているのは「まだ使われているか」であって「まだ居るか」ではない、という
  読みに沿った挙動である。**iOS がバックグラウンドでサスペンドされた場合が
  これに当たり**、視聴側の更新（§3.4）もアプリのタスクなので同時に止まるため、
  更新の有無で差は付かない。復帰後の挙動は未確認
  （[#108](https://github.com/seera-networks/ISEKAI-link/issues/108)）
- **リレー運営者による能動的な傍受は、まだ防げていない。** TLS 鍵は端末から出なく
  なった（§2.6）ので、リレーが持つのは暗号文だけになった。ただし FQDN を導出するのも
  ACME アカウントを持つのもプロキシなので、**同じ名前で自分の証明書を取って中間者に
  なることは依然として可能**である。塞ぐには相手の Endpoint 鍵で裏づけた SPKI の
  ピン留め（サーバ側仕様 §8.6.4）が要り、それには鍵がクライアント側にあることが前提
  だった。プライバシーポリシー §5 の記述は、鍵の配布を前提に書かれているので**要更新**
- **証明書の更新は再起動でしか起きない。** 発行された証明書は約 90 日有効だが、
  稼働中に期限が近づいても取り直さない。msquic のリスナは資格情報を差し替える形に
  なっていないため（§2.6）
- **Direct モードは旧方式**で、P2P のような自動的な仲介は無い
- **解像度は 640×480 固定**で、選択も設定もできない。装置そのものは選べる（§2.2）
- **カメラの選択は保存されない。** 起動するたびに既定（index 0）に戻るので、内蔵
  カメラ以外を使う端末では毎回選び直すことになる

## 5. プライバシーポリシーの同意

利用にはアカウント登録が必要で個人情報を取得するため、両アプリとも**初回起動時に
全文を表示し、同意するまで他を操作できない**。

- 本文は `docs/privacy-policy.{ja,en}.md` の 1 か所。`camera_core::privacy` に
  コンパイル時に取り込まれ、iOS も FFI 経由で同じものを表示する
- **同意はバージョンに対して**記録する（`VERSION` + 日時 + 表示していた言語）。
  改定して定数を上げると、次回起動時に再度確認する
- 日英を同梱し切り替えられる。egui は CJK フォントを持たないため、システムから
  日本語フォントを借りる。見つからない場合は英語のみを表示し、その旨を出す
- 記録は**利用者ごとの設定ディレクトリ**に置く。起動ディレクトリで同意の有無が
  変わっては記録にならないため
