# portal-server を Gateway として動かす

`agent_access_spec_draft.md` の**段階 2**:

> **Gateway：NDJSON 購読 + 操作カタログ（§3.5）+ 属性スキーマ（§3.1.0）+ PEP +
> Grant 作成（順序規則つき）**

Gateway に相当するのは `portal-server` である。本書はそこに **Gateway モード**を
足す計画で、**PEP の強制は後回し**とする（§0.3）。

> 以下、`§n` は本書の節。設計書を指すときは「**draft §n**」、Identity の仕様を
> 指すときは「**identity §n**」、Proxy の仕様は「**proxy §n**」と書く。

---

## 0. 結論を先に

### 0.1 上流は揃っている。こちらが唯一の欠けている部品である

段階 1（Identity にエンタイトルメント・`decision_id`・配布ストリーム）は
**実装済み**である。identity §8.9 と §8.10、`/v1/policies` と
`/v1/policies/stream` のハンドラが入っている。

**つまり段階 2 は「上流を待つ」話ではない。** 配る側は既に配っており、
**受け取る側が居ない**。

### 0.2 仕様が受け取る側に課している義務は、素直に書くと必ず破る

identity §8.10.3 / §8.10.4 は Gateway の責務を明示的に列挙している。
そのうち 5 つは「言われなければそう書かない」種類である。

| 義務 | 素直に書くとどうなるか |
| --- | --- |
| **知らない `window` ラベルの行は適用しない** | 「知らないラベルは無視」と書く。**窓を付けたつもりが 24 時間アクセスになる**（§0.4） |
| **空の一覧は「全部落とせ」という指示**。「読めなかった」をそれで代用しない | エラー時に空を返す実装にすると、**一時的な失敗で全 Grant を消す** |
| **期限切れはストリームに流れない。** 沈黙は「まだ有効」ではない | ストリームだけ見ていると、**切れたリースを永久に保持する** |
| **ストリームはトークンの期限で必ず終わる**（サーバが切る） | 「切れた＝異常」と扱い、**15 分ごとに異常ログが出る** |
| 照合が正しさの担保。ストリームは速い経路 | ストリームを信頼し、取りこぼしが恒久化する |

**これらは設計ではなく仕様である。** 実装の自由はそこに無い。

### 0.3 PEP を後回しにしても、順序規則は先に要る

identity §8.10.4 が処理順を固定している。

1. 属性を検証し、**`window` ラベルを検証する**（どちらも外れれば**その行は適用しない** = fail-closed）
2. **強制点の表に書く**
3. Grant を作る

> 逆にすると、**届くけれど scope が無い窓**が開く。

**PEP の強制が後回しでも、この順序は今決める。** あとから 2 を差し込むとき、
「Grant を先に作る」実装になっていれば**順序を直す改修**になる。
表は作って保持し、**強制だけをしない。**

### 0.4 `window` は「後回しの PEP」に含まれない

**これが本計画でいちばん間違えやすい一点である。** identity §8.10.4 が名指しで
警告している:

> **知らない `window` ラベルを受け取ったら、その行を適用しない**（fail-closed、
> 属性の値域と同じ）。**いちばん素直な実装は「知らないラベルは無視」で、それは
> 24 時間アクセスになる。** 窓を付けたつもりが外れる形なので、明示しておく。

`window` の**強制**（いま窓の中か）は PEP であり、後回しでよい。しかし
**「知らないラベルなら行を適用しない」は段階 2 の義務**である — 適用するかどうかを
決めるのは Grant を作る前だからである。

**したがって Gateway は、自分が知っている窓ラベルの一覧を設定に持つ。**
属性スキーマと同じ場所に置く（§4）。

> **窓を Grant の TTL で表現してはならない**（identity §8.10.4）。窓が閉じるのは
> セッションの途中であり、Grant の失効は「次の connect から」しか効かない。
> TTL にすると「**窓が閉じたのに動き続けるセッション**」ができる — 窓で止めたいのは
> まさにそれである。多層防御として TTL を切り詰めるのは可、強制点ではない。

## 1. 上流の形（実装から読んだ）

**仕様書とハンドラの両方を読んだ。** ISEKAI-identity#35 の教訓である。

### 1.1 2 つの口

| 口 | 役割 |
| --- | --- |
| `GET /v1/policies` | いま有効なもの**全件**と `cursor`。**再接続時の照合** |
| `GET /v1/policies/stream?after=<cursor>` | NDJSON。変化を流し続ける |

認証は **Endpoint Token + PoP**。**permission は要らない** — 名乗った Endpoint に
紐づくものだけが流れるので、名乗り以外に認可することが無い。

### 1.2 流れてくるもの

```jsonc
{"type":"policy.granted","access_lease_id":"al_7f2c9d1b","decision_id":"dec_9f1e2d3c",
 "version":4,"allowed_endpoint":"ep:1197c4…","protocol":"pg-sales-ro-v1",
 "ttl":1800,"expires_at":"2026-09-17T09:30:00Z","attributes":{"region":"kanto"},
 "constraints":{"grant_ttl":3600,"max_concurrent":2,"window":"business_hours"}}

{"type":"policy.revoked","access_lease_id":"al_7f2c9d1b","decision_id":"dec_9f1e2d3c",
 "version":5,"allowed_endpoint":"ep:1197c4…","protocol":"pg-sales-ro-v1",
 "reason":"entitlement-removed"}

{"type":"keepalive"}
```

- `reason` は `policy.revoked` に**必ず載る**（`lease-expired` /
  `entitlement-removed` / `endpoint-revoked`）
- `keepalive` は 15 秒ごと。**接続直後に必ず 1 行**流れる
- 超過は `503 policy-stream-capacity`

### 1.3 ストリームはトークンの期限で終わる

> **ストリームは、名乗りに使ったトークンの期限で必ず終わる。**

**サーバ側の仕様**である。Gateway は 1 トークン寿命（≤15 分）ごとに戻って照合し、
取りこぼしの上限がそこで決まる。PoP はストリームを開く 1 要求にしか掛からないので、
**認証の再検査もこれで満たされる。「切れた」を異常として扱わないこと。**

> `relay_lease.rs` でトークンセルを共有することにしたのと**裏表**である。
> あちらは長生きするループが新しいトークンを**見る**必要があり、こちらは
> 長生きするストリームが新しいトークンで**張り直される**必要がある。
> そして今回は、サーバがそれを強制してくれる。

### 1.4 巻き戻し防止のキーは `access_lease_id`

`version` が既知より古ければ捨てる。**最後に見た `version` は
`access_lease_id` ごとに持つ。**

> draft §5.4.3 は「`(decision_id, version)` で判定する」と書いているが、
> **実装では `version` はリースごとの連番である**（Identity の `domain/lease.rs`:
> 「`version` は**リースごと**の連番」）。`decision_id` をキーにすると、決定が
> 変わったときに基準が無くなる。**`access_lease_id` で持つ。**

## 2. 期限切れは自分の時計で落とす

identity §8.10.4 の、いちばん見落としやすい一行。

> **そして、期限切れはストリームに流れない。**（中略）
> **「ストリームに何も来ない」は「まだ有効だ」を意味しない。**

`policy.granted` は `ttl` と `expires_at` を持っているので、**Gateway は自分の時計で
落とせる。それが期限切れの唯一の検出手段**であり、取りこぼしは照合が拾う。

**内容の変更と明示的な失効は必ず流れる**（デバウンスの対象外）。つまり
「流れてこない」で判断してよいのは期限だけである。

### 2.1 TTL は 2 段で、別の規則である

初版はこの 2 つを 1 つに潰していた。**別々に書く。**

| 規則 | 出典 | 内容 |
| --- | --- | --- |
| **Grant の TTL < ポリシーの `ttl`** | identity §8.10.3 | ポリシーの行が消える前に Grant が切れる |
| **強制点の表の TTL < Grant の TTL** | identity §8.10.4 | **強制が先に落ちる。** fail-closed 側へ倒す |

**下の規則が段階 2 でこそ効く。** 表を持って強制しない段階では忘れやすいが、
強制が入った瞬間に「Grant は消えたのに表に残る」が「消したはずの認可が効き続ける」
になる。

### 2.2 最小リースでは 1 段目が成立しない

Identity の `LEASE_TTL_MIN_SECS = 60`、proxy §8.8.1 の `ttl` は **60〜86,400 に
クランプ**される。**`ttl` が 60 秒の行に対して、60 未満の Grant は作れない** —
クランプで 60 に戻され、Grant がポリシーより長生きする。fail-closed の向きが反転する。

**床を明示する。** 取りうるのは 2 つ。

- **短すぎる行を受け付けない**（例: `ttl < 120` は適用しない）。fail-closed で素直
- **等しくなることを受け入れ、照合に頼る**。照合は 15 分に 1 回以上走るが、
  **その間ずれる**

**前者を採る。** 後者は「仕様の向きが反転した状態を許容する」ことであり、
それを既定にはできない。

## 3. Gateway モードとは何か

```
portal-server --gateway
  ├─ 操作カタログ・属性スキーマ・窓ラベルを読む（draft §3.5 / §3.1.0、§0.4）
  └─ /v1/policies を照合 → /v1/policies/stream を購読
       → 属性と窓を検証 → 強制点の表に書く → Grant を作る
```

**既存の動作を置き換えない。** `--gateway` を渡さなければ今までどおりで、手で作った
Grant もそのまま効く。増えるのは**「Grant を自動で作る主体」**である。

### 3.1 自分が作った Grant を、label で識別することはできない

初版は「`label` に `access_lease_id` を入れて印にする」と書いた。**成立しない。**

proxy §8.8.1 の Grant は **`(owner_endpoint, allowed_endpoint, protocol)` がキー**で、
**同じ組への再作成はエラーにならず `200 OK` で `label` が要求の値に更新される。**

破れ方が 2 つある。

1. **運用者の Grant を奪う。** 手で作った `(ep:A7, pg-sales-ro-v1)` の Grant に
   リースが重なると、Gateway の作成が `label` を上書きする。リースが終われば
   照合がそれを消す — **§3.1 が防ごうとした事故そのもの**
2. **1 つの組に複数のリース。** draft §3.4 は「同じ Endpoint・同じ protocol で
   タスクが 2 つ」を普通としており、§3.4.2 は
   **`access_lease_id` を Grant のキーに入れるには Proxy の変更が要る**（段階 6）と
   書いている。いまは**2 つのリースが 1 つの Grant を共有**し、片方が終わると
   もう片方が要る Grant を消す

**したがって Gateway は自分の帳簿を持つ。**

- `(allowed_endpoint, protocol)` ごとに、**それを要求しているリースの集合**を持つ
- Grant を消すのは**集合が空になったとき**だけ
- **起動時にその組の Grant が既に在り、自分の帳簿に無ければ、触らない**
  （運用者のものとみなす）

`origin` も助けにならない — Gateway が作る Grant も運用者のものも `manual` である。

> `--revoke-endpoint` の `by_us` と同じ問題だが、**答えが違う。** あちらは
> 「自分が登録したか」をプロセス内の事実として持てた。こちらは**再起動をまたぐ**ので、
> 帳簿を永続化するか、「知らない Grant には触らない」で通すかを選ぶ必要がある。
> **後者を既定にする** — 消しすぎより消し忘れのほうが安全である。

### 3.2 Grant の上限に当たる

proxy §8.8.1: 上限は **Endpoint あたり `--p2p-grant-quota`（既定 64）**、超過は
`429 grant-quota-exceeded` で既存の行は変わらない。

**64 を超えるリースを配られた Gateway は、残りを黙って作れない。** 失敗は行ごとなので
**ポリシーが半分だけ適用された状態**になる。

- `429` を**成功として扱わない**。表に書いたのに Grant が無い行を記録する
- **運用者に見えるようにする**。上限は配備の設定であり、Gateway が直せるものではない

## 4. 操作カタログ・属性スキーマ・窓ラベル

どれも**顧客側の設定ファイル**であり、中央には出ない（draft §3.1）。

```toml
[protocols."pg-sales-ro-v1"]
# 知っている窓ラベル（§0.4）。ここに無いラベルの行は適用しない
windows = ["business_hours", "always"]

# 属性スキーマ — 中央から来る値の受け入れ範囲（draft §3.1.0）
[protocols."pg-sales-ro-v1".attributes]
region = { type = "enum", allowed = ["kanto", "kansai", "kyushu"] }

# 操作カタログ — 許す操作（draft §3.5）
[[protocols."pg-sales-ro-v1".operations]]
name     = "query_sales"
sql      = "SELECT id, region, amount FROM sales WHERE region = $1 AND month = $2"
bind     = ["{{region}}", "$month"]
max_rows = 1000
[protocols."pg-sales-ro-v1".operations.params]
month = { type = "string", pattern = '^\d{4}-\d{2}$' }
```

**段階 2 では読んで検証するところまで作る。操作は実行しない**（PEP 後回し）。
それでも価値がある理由は 2 つ。

1. **属性スキーマと窓ラベルの検証は段階 2 で効く。** どちらも Grant 作成の前段で
   あり、PEP とは独立に動く。**「中央を侵害されても envelope を超えられない」**という
   draft §3.1.0 の主張は、ここが動いて初めて成り立つ。段階 2 の**安全上の中身はこれ**
2. カタログの構文エラーを起動時に見つけられる

### 4.1 自由 SQL を受け取る口は、作らない

draft §3.5 は「任意 SQL を検査して通す形にしてはならない」と書いている。
**段階 2 で作らないだけでなく、後から足せる形にもしない。** `operations` は名前で引く
表であって、テンプレートの外から SQL が入る経路を持たない。

## 5. 照合が正しさの担保である

```
起動 / 再接続
  → GET /v1/policies                （全件 + cursor）
  → 各行を検証（属性・窓。ストリームと同じ検証、§5.3）
  → 表を「ここに無いものは落とす」で作り直す
  → 帳簿と突き合わせ、要らなくなった Grant を消す（§3.1）
  → GET /v1/policies/stream?after=<cursor>
```

### 5.1 「読めなかった」を「空」と書いてはならない

identity §8.10.3 が名指しで警告している。

> **空の一覧は「手元の行を全部落とせ」という指示**なので、「読めなかった」をそれで
> 代用してはならない。

実装上は、照合の結果を `Result<Vec<Policy>>` のまま扱い、**`Err` で表に触らない**。
**`unwrap_or_default()` はこの一点で禁止**である。

> `--revoke-endpoint` で `duplicate_key` の読み取りを `Result` のまま持ったのと
> 同じ形である。**読めなかったことと、無かったことは違う。**

### 5.2 巻き戻し防止

§1.4 のとおり `access_lease_id` ごとに `version` を持ち、古ければ捨てる。
**再接続後の再送でも要る。**

### 5.3 照合路とストリーム路で、検証を共有する

**初版は照合路に検証を書いていなかった。** 照合は起動時と 15 分に 1 回以上走る
——**ストリームより頻度が高い**。そこを素通りさせると、値域外の属性や知らない窓が
**いちばん通りやすい経路から入る**。

**行を受け取ってから表に書くまでを 1 つの関数にし、両方がそれを呼ぶ。**

## 6. 接続を知る — 既にストリームは張られている

**初版は「portal-server はまだ §8.11 の購読をしていない」と書いた。誤りである。**

`portal-server` は `AcceptPolicy::AutoNotify` を渡しており、`listener::run` は
`policy != Manual` のとき `session.subscribe()` する。**ストリームは既に張られていて、
`poll_signaling` は 2 段階のバックストップとして併用されている。**

> これは §8 の「どちらを主にするか」という問いへの答えでもある。**コードで既に
> 決まっている** — ストリームが引き金、ポーリングが記録。proxy §8.11 の
> 「ポーリングは廃止しない」がそのまま実装されている。

### 6.1 では何が足りないのか

`listener::run` は**中身を捨てている** — イベントが来たことだけを使って
ポーリングを早めている。`initiator_endpoint` は誰にも届かない。

段階 2 でやるのは**購読を足すことではなく、payload を通すこと**である。
Gateway が自分で購読すると、**同じ Listener に 2 本目の
`GET /v1/peer-listeners/{id}/events` が開く。**

### 6.2 記録するだけ

- `initiator_endpoint` が表にあるか（**記録するだけ、落とさない**）
- `max_concurrent` を超えていないか（**記録するだけ**）

**「照合して、落とさなかった」を必ずログに残す。** 強制を入れる前に、
**本番の配備で何件落ちることになるかが分かる**ようにしておく。

### 6.3 `initiator_endpoint` は省略されうる

`ListenerEvent::ConnectCreated.initiator_endpoint` は `Option<String>` である。
**3 つ目の答えを持つ。**

- 記録では「不明」として**別に数える**。「表に無い」に混ぜると数が膨らみ、
  「検査を飛ばす」に混ぜると数が減る。**P5 の目的は件数を知ることなので、どちらも困る**
- **強制を入れるときは `None` を fail-closed** にする

## 7. 段取り

| # | やること | 出口 |
| --- | --- | --- |
| **P0** | 操作カタログ・属性スキーマ・**窓ラベル**の型とパーサ。起動時に検証 | 設定が壊れていれば起動時に分かる |
| **P1** | `GET /v1/policies` の型とクライアント。**検証して表を作るだけ**、Grant は作らない | **上流と繋がる。** 何が配られているかが見える。配備に影響しない |
| **P2** | ストリーム購読（`after` 付き）。**トークン期限での終了を正常系に**（§1.3）。期限切れは自分の時計で（§2） | 変化に追随する |
| **P3** | Grant 作成（§0.3 の順序、§2.1 の TTL、§2.2 の床）と**帳簿**（§3.1）。`429` を成功にしない（§3.2） | Gateway が Grant を配る |
| **P4** | `policy.revoked`（PEP 先、draft §7.2）と、照合での消しすぎ防止 | 消し忘れと消しすぎの両方が起きない |
| **P5** | `listener::run` の payload を通し、記録する（§6） | 強制を入れる前に影響が見える |
| **P6** | PEP の強制（別計画） | — |

**P1 で一度、上流と繋がったことが確認できる。** Grant を作らないので、
**間違っていても配備に影響しない** — 何が配られているかを先に見る。

## 8. 確かめていないこと

1. **Identity のストリームを読む transport が無い。** `EventStreamTransport` の
   実装は **`MasqueH3Transport` だけ**で、`HttpsTransport` には無い。
   `issue_endpoint_token` は `cfg.identity_http3` で実行時に選ぶので、
   **Identity を TCP+TLS で動かす配備には流せる transport が存在しない。**
   P2 はこの実装を足すところから始まる
2. **PoP の path 束縛とベース URL。** 形は揃っていても、`ProxyClient` 用の実装を
   そのまま Identity に向けられるとは限らない
3. **`503 policy-stream-capacity` の後退の仕方。** 仕様は「後で通る」としか
   言っていない
4. **エンタイトルメントと Gateway の登録を運用でどう回すか。** identity §8.9 に
