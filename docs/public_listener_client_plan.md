# Public UDP Listener に繋ぐ

サーバ側のフェーズ 5（`dataplane_separation_phase5_plan.md`）で、パブリック
アドレスは **CP の資源から DP の資源になった**。台帳は `(dp_id, port, sub)` で、
IP は持たない。したがって、

> そのアドレスでバウンド UDP セッションを張れるのは**その DP だけ**である。

いまクライアントは CP にダイヤルしている。本書はその差を埋める計画である。

---

## 0. 結論を先に

### 0.1 これは「新しい接続方式」ではない

必要なものは**すでに全部ある**。リレーのレグ（§8.14）が、チケットを取り、名指された
DP へ CONNECT-UDP を出し、バウンドしたソケットの上でデータグラムを運ぶ、という形を
作った。パブリックアドレスはその**同じ形の、相手のいない版**である。

| | リレーのレグ | パブリックアドレス |
| --- | --- | --- |
| 何を bind するか | DP のループバック（30000 番台） | **利用者の公開 `ip:port`** |
| 誰が認可するか | CP 署名のチケット | **同じチケット**（`role: public`） |
| ランデブー | ある（2 本が出会う） | **無い**（1 本きり） |
| セッション ID ヘッダ | 送る | **送ってはならない**（§2.2） |
| リースの効き方 | パケットごとに関門がある | **次のチケットを出すかどうかだけ**（§4.2） |

**だから新しい寿命管理も新しい資格情報も作らない。** 作ると、単回使用も失効も
もう一度正しく実装することになる。

### 0.2 いちばん危ないのは「ヘッダを 1 つ足す」こと

DP の振り分けは**要求の形**で決まる（`serve.rs`、phase-5 §4.2）。

```
Seera-Signaling-Session-Id あり → レグとして扱う（role は initiator / target のみ）
        同ヘッダ無し＋チケットあり → パブリックアドレスとして扱う（role は public のみ）
                          どちらも無し → この DP のものではない
```

既存の `open_bind_session` は `seera-signaling-session-id` を**必ず付ける**
（`bind.rs:365`）。これを流用して `role: public` のチケットを持ち込むと、**レグの
経路に入って拒否される**。サーバ側が意図してそう作っている（攻撃者がヘッダを添えて
公開アドレスをエッジプールへ入れるのを防ぐため）ので、**こちらが合わせる**。

### 0.3 「相手がいない」が 2 つのことを壊す

リレーのレグには相手がいて、**届かなければ気づく**（`InboundActivity`）。
パブリックアドレスの相手は不特定多数で、**一度も誰も来ないことが正常**である。

**1 つめ：到達性を能動的に確かめられない。** 判定材料は「CONNECT-UDP が確立した」
だけで、それは「bind できた」しか言っていない。**ヘルスチェックを発明しない** —
無音を異常と読む仕組みは、この経路では必ず誤報する。

> **初版は判定材料を 2 つ挙げ、2 つめを間違えていた。** 「CP が言った広告アドレスと
> DP が報告したそれが一致すること」と書いたが、**その 2 つは同じ 1 回の台帳読み出しの
> 写しである**（§3.3）。一致して当然で、何も検証していない。

**2 つめ：転送先のソケットが無制限に増える。** `MasqueClientMode::Forward` は
**受信元アドレスごとに新しい UDP ソケットを bind する**
（`from_quic_to_udp.rs:343-367`、キーは `(stream_id, 送信元)`）。レグの送信元は 1 つ
だが、公開アドレスの送信元はインターネット全体である。**新しい送信ポートから 1 発
送るだけで、こちら側にソケットとコンテキスト ID が 1 つ増える。** 上限も追い出しも
無い（§3.6）。

## 1. サーバが提供している口（実装済みの事実）

計画書ではなく実装から取る。

### 1.1 作成 — `POST /v1/public-listeners`

```jsonc
{ "listener_id": "ul_…", "owner_endpoint": "ep:C", "visibility": "public",
  "public_address": { "hostname": "…", "ip": "203.0.113.9", "port": 10042 },
  "region": "ap-northeast-1",          // 決まった region。要求の echo ではない
  "relay": { "masque_uri": "https://dp1…:8443/…", "dp_id": "dp1…",
             "spki_sha256": ["…"] },   // 登録済み DP のときだけ
  "status": "active", "created_at": "…", "expires_at": "…" }
```

- **`ticket` は入らない。** 作成は冪等で、`Idempotency-Key` の応答キャッシュは 24 時間
  残る。単回使用・寿命 45 秒のチケットを再送に返すわけにいかない、という判断が
  サーバ側で下されている（実装のコメントが明言）。計画書 §4.3 の「同梱は最適化」は
  **採られなかった**
- **`relay` が無いのは「CP 自身のデータパス」という意味**である。その bind は
  セッション自身の Endpoint Token で認可され、チケットは要らない。**ただし
  そこに着けば自分のポートに bind される、ではない** — §3.7
- **仕様 §7.7.4 はまだ「作成応答が `relay` と `ticket` を伴う」と書いている。**
  実装に追随していない。仕様を先に読んだ実装者は同梱チケットを待つコードを書く
  ので、ここで明示しておく（§3.5 の `target` と同じ種類の食い違い）

### 1.2 チケット — `POST /v1/public-listeners/{id}/ticket`

**これが主経路である。** `relay` と `ticket` を返す。応答の形は作成と同じなので、
クライアントは 1 つの型で読める。

```jsonc
{ …, "relay": { … }, "ticket": { "ticket": "<JWT>", "role": "public",
                                  "expires_at": "…", "lease_expires_at": "…" } }
```

**新しい認可判断はここで行われない。** Listener を持っていることが資格で、それは
作成時に決まっている。ここで足されるのは**鮮度・単回使用・DP の名前**である。

> **台帳を引き直している。** サーバはこのとき「行が憶えている値」ではなく
> **いまその利用者が保有しているポート**を読む。解放・再割当が起きていれば、
> 返るアドレスは作成時と違う。§3.3 と §5 はこの事実の上に立つ。

### 1.3 削除 — `DELETE /v1/public-listeners/{id}`

`204`。owner 以外は `404 listener-not-found`。

### 1.4 bind — CONNECT-UDP

| | 値 |
| --- | --- |
| 宛先 | `relay.masque_uri` のホスト（無ければ設定された proxy） |
| パス | ワイルドカードの bind パス（`/.well-known/masque/udp/*/*/`） |
| 認証 | Endpoint Token + PoP（レグと同じ） |
| `Seera-Relay-Ticket` | **`relay` があるとき必須** |
| `Seera-Signaling-Session-Id` | **付けない**（§0.2） |
| `Seera-Prefer-Temporary-Public-Address` | **付けない**（§3.7）。いまの `open_bind_session` は無条件で付ける |

DP は**ポート番号だけ**をチケットから取り、自分の `--public-bind-ip` に bind する。
そして**広告アドレス**（bind したものではない）を `proxy-public-address` として
返す。クライアントには `MasqueClientEvent::PublicAddresses` として届く。

**これは `Vec<SocketAddr>` である。** ヘッダはカンマ区切りで、読めない要素は
`filter_map` で黙って落ちる（`channel-masque/src/lib.rs:941-963`）。`[0]` を見て
比較する実装は、複数広告する DP に対して誤検知する。そして `SocketAddr` に
`hostname` に当たるものは無い — **名前は CP の応答からしか来ない。**

## 2. クライアント側に足すもの

### 2.1 `isekai-p2p-core` — ワイヤ

| # | もの | 置き場所 |
| --- | --- | --- |
| 1 | `PublicListener` / `PublicAddress` の DTO、`RelayRole::Public`、**`RelayInfo.session_id` を `Option<String>` に** | `proxy.rs` |
| 2 | `create_public_listener` / `delete_public_listener` / `issue_public_listener_ticket` | `proxy.rs` |
| 3 | `open_public_bind_session` — セッション ID ヘッダを**付けない**バウンド UDP | `bind.rs` |

**非互換の変更が 2 つある。どちらも「読めない」で終わる。**

1. **`RelayRole::Public`。** いまの列挙は `initiator` / `target` の 2 つで、未知の
   値は serde が拒否する。足さなければ `role: "public"` のチケットを**読むことすら
   できない**
2. **`RelayInfo.session_id` が必須の `String` である**（`proxy.rs:253`）。公開
   アドレスの `relay` に `session_id` は無く、サーバは `skip_serializing_if` で
   **フィールドごと落とす**。いまの型で `/ticket` の応答を読むと
   `missing field 'session_id'` で失敗する

2 つめは既存のレグの呼び出し側すべてに波及する（`Option` になるので）。**P0 の出口
「チケットが読める」はこれを含む** — 初版はこれを数えておらず、P0 は完了しえなかった。

> **実際に波及したのは 1 箇所だった**（P0 実施時）。initiator はレグを開くのに
> `masque_uri` と `dp_id` しか読まず、`session_id` は CONNECT-UDP のヘッダに
> `connection_id` を使っていて、`RelayInfo` のほうは**誰も読んでいなかった**。
> 直ったのはテスト 1 本である。

### 2.2 `open_bind_session` を分けるか、引数で分けるか

**分ける。** 引数 1 つの違いに見えるが、意味が違う。

| | 一緒にする | 分ける（本案） |
| --- | --- | --- |
| セッション ID | `Option<&str>` | 型に現れない |
| 間違えたとき | **レグの経路に入り拒否される**。原因はヘッダ 1 つで、エラーには出ない | そもそも渡せない |
| `forward_to` | 同じ | 同じ |
| 共有 | コネクタ・PoP・チケット層は共通の下請けに | 同上 |

§0.2 の落とし穴は「うっかり付ける」ではなく「**既存の関数を流用すると必ず付く**」
形をしている。型で防げるものを実行時のエラーに任せる理由がない。

### 2.3 `isekai-p2p` — 寿命

`PublicEndpoint`（仮称）が持つのは 3 つだけ：

```
create（1 度）→ ticket（毎回）→ bind（セッションのあいだ）
```

- **チケットは bind の試行ごとに取り直す。** 「再接続のたび」では足りない：
  単回使用で寿命 45 秒、しかも DP は **bind が成功してから**使用済みにする
  （`serve.rs:385-390`）。bind を再試行で包むと、2 回目は 45 秒を過ぎているか
  使用済みかで `403` になり、**「DP に拒まれた」と読める形で失敗する**
- **リースの更新ループは作らない**（§4.2）
- **Listener の TTL は延ばせない。** 最大 86,400 秒で、切れたら作り直し
  （`/ticket` は期限切れの Listener に `404` を返す）
- **作り直しには `Idempotency-Key` が要る。** 無いと `POST /v1/public-listeners` は
  毎回新しい行を作り、**Endpoint あたりの上限は既定 8**（`p2p_public_listener_quota`）。
  再起動のたびに作り直す常駐プロセスは 8 回で `429 listener-quota-exceeded` に当たり、
  以後**二度と公開できない**（期限切れの行は掃引まで残る）
- **`listener_id` はプロセスをまたいで保持する。** 保持しないなら、上の
  `Idempotency-Key` が唯一の身元になる

## 3. 落とし穴

### 3.1 `relay` が無いときに DP を推測しない

`RelayInfo.dp_id` について `bind.rs` が既に書いていることが、そのまま当てはまる：

> **URI の形ではなく、明示の signal を見る。** 登録済み relay が無いとき CP は
> `--p2p-relay-base-url` から URI を組み立てるので、その既定はハードコードされた
> 本番ホストである。「authority があるから行く」と読むと、開発用クライアントの
> Endpoint Token と PoP が誰も設定していない origin へ飛ぶ。

パブリックアドレスでも同じ規則にする。**`relay` が無ければ、設定された proxy —
すなわち CP — にダイヤルし、チケットは付けない。**

**「設定された proxy」と書くと足りない。** チケット無しの公開 bind を受けるのは
**CP 同居のデータパスだけ**である。単体の `isekai-link-relay` は §0.2 の
「どちらも無し」に落ち、MASQUE 層がソケットを見つけられず**本文の無い 500** を返す。
`relay` が無いときの行き先は CP であって「設定されたどこか」ではない。

### 3.2 チケットの `role` を検査する

CP が `role: public` を返すはずの場所で `initiator` が返ってきたら、それは
**こちらの要求が意図と違う口に届いている**。黙って bind に進むと、DP 側の
振り分け（§0.2）で拒否され、原因はヘッダとロールの組み合わせという**こちらから
いちばん見えにくい形**で現れる。取り出した時点で確かめる。

### 3.3 突き合わせる相手は「時間をまたいだ自分」である

**初版はここを間違えた。** 「CP の `public_address` と DP の報告を突き合わせる」と
書いたが、**その 2 つは同じ 1 回の台帳読み出しから出ている** — サーバは `alloc` を
一度読み、それを応答の `public_address` にもチケットの `advertised` にも入れ、DP は
`bind.advertised` を**そのまま** `proxy-public-address` として返す
（`handlers.rs:4460-4495`、`serve.rs:400-411`）。**構造上一致する。**

DP が報告するのは**bind したアドレスではない**（NAT の内側やワイルドカードでは
自分のアドレスを配ることになるので、意図してそうなっている）。つまり
**「DP が実際にどのポートを取ったか」はクライアントからは観測できない。**

実在する比較は 1 つだけである。

| 比較 | 分かること |
| --- | --- |
| **前回公開したアドレス** vs **今回のチケットが言うアドレス** | 割当が動いた（§5）。サーバは `/ticket` のたびに台帳を引き直す |

再チケットは「紙を新しくする」だけでなく、**割当が変わっていないかを訊く唯一の
手段**である。§2.3 が「bind の試行ごとに取り直す」と言っているのは寿命の話だが、
**変化を知る経路でもある。**

- **保持する**: 最後に外へ配ったアドレスを、プロセスをまたいで憶えておく
- **黙って進まない**: 変わっていたら `warn`。この経路の利用者は「外の誰かに
  アドレスを配った人」なので、変わったことを知らせないのは最も高くつく

> **ただし `relay` が無い経路では、DP の報告に意味がある**（§3.7）。そこだけは
> 報告されたポートが割当と食い違いうる。

### 3.4 権限

`udp-listen:public:create` / `:delete` が Endpoint Token に要る。足りなければ
`403 insufficient-permission`。

**`/ticket` と bind は権限を要求しない**（`handlers.rs:374` に `require_permission`
が無く、bind はチケットと PoP だけ）。**作れないトークンで、作ってあるものを
bind し直せる。** 権限の絞りは「新しく公開する」を止めるものであって、「すでに
公開してあるものを使い続ける」は止めない — 絞りで停止させようとする運用が、
ここで期待と食い違う。

### 3.5 転送先ソケットに上限が要る

`MasqueClientMode::Forward` は `(stream_id, 送信元アドレス)` ごとに
**新しい UDP ソケットを bind して `forward_to` に connect する**
（`from_quic_to_udp.rs:343-367`）。レグではこれでよい — 送信元は 1 つである。

**公開アドレスでは送信元がインターネット全体になる。** 新しい送信ポートから 1 発
送るだけでソケットが 1 つ増え、上限も追い出しも無い。誰でも、何の資格も無しに。

> これは §0.3 の「相手がいない」のもう半分である。無音が正常な経路は、**騒音も
> 正常に見える**経路でもある。

**P2 より前に決める。** 決め方は 3 つあり、どれを採るかはこの計画では決めない
（実装時に測る）が、**何も決めないという選択肢は無い**。

| 案 | 費用 |
| --- | --- |
| 同時ソケット数の上限＋LRU 追い出し | 正当な送信元が追い出されうる |
| アイドルのソケットを閉じる（既存の blackhole 機構に寄せる） | 生きている無音の相手を切る |
| `Forward` ではなく単一ソケットのモードを足す | `channel-masque` の変更。レグの識別（`local_addr`）に影響しないか要確認 |

> **P1b では上 2 つを両方採った。** 片方では足りない — アイドル解放は
> 「送るのをやめて戻らない」通常の相手を回収するが、**1 秒に 1000 の送信元**には
> 何もしない。上限はそれを抑えるが、追い出す相手は最も静かだった者であり、**生きて
> いるかもしれない**。3 つめは採れない：**返信の宛先が分からなくなる**からである
> （ローカルのサービスからの応答は、どのソケットに来たかでしか送信元に結び付かない）。
>
> **既存の blackhole をそのまま使うと誤る。** 死んだソケット（ローカルが ICMP で
> 拒否した）を 60 秒作り直さないのは正しいが、**こちらが決めた上限のために追い出した
> 相手**を 60 秒締め出すのは、こちらの都合で相手を罰することになる。追い出しは
> blackhole を立てない。

### 3.6 `target` は送るが、Proxy は解釈しない

仕様 §7.7.3 が「未実装」から「**実装しない**」に書き直された。`target` は
owner 自身が転送する宛先のメタデータである。クライアントは、

- 作成要求には載せる（宣言・可視化のため）
- **実際の転送は自分でやる** — バウンド UDP セッションの `forward_to` がそれ

の 2 つを別のものとして扱う。片方だけ設定して繋がらない、が起きやすい場所である。

---

### 3.7 `relay` が無いとき、CP は「あなたのポート」に bind するとは限らない

`relay` が無い経路には、サーバ側に**もう 2 つの分岐**がある
（`main.rs:1928-1990`）。

1. **共用リスナが先に見られる。** 利用者の `udp_mode` が `"dedicated"` でなく、
   サーバに共用リスナが設定されていれば、**共用ポートに bind される**。公開した
   `ip:port` には何も来ない
2. **`Seera-Prefer-Temporary-Public-Address: ?1` があると、割当を飛ばして
   一時ポートを取る。** いまの `open_bind_session` はこのヘッダを**無条件で付ける**
   （`bind.rs:359-362`）

**2 は §2.2 の「共通の下請けに寄せる」が素直に踏む地雷である。** レイヤの積み方を
共有すると、このヘッダも一緒に付いてくる。すると bind は成功し、
`proxy-public-address` は一時ポートを報告し、**外に配ったアドレスは死んでいるのに
こちらは健全に見える。**

- **公開 bind はこのヘッダを付けない**（§1.4）
- **ここだけは DP の報告が意味を持つ**（§3.3）。報告されたポートが `public_address`
  と違えば、上の 1 か 2 が起きている
- 単体の `isekai-link-relay` はこのヘッダを見ないので、**問題が出るのは計画が
  いちばん単純だと思っていた経路だけ**である

## 4. 寿命

### 4.1 3 つの時計が別々に動く

| | 長さ | 切れたら |
| --- | --- | --- |
| チケット | 45 秒 | 取り直す。**保持する価値が無い** |
| リース | 数十分 | **セッションは切れない**（§4.3） |
| Listener | 最大 86,400 秒 | **作り直し**。`/ticket` が `404` |

### 4.2 更新ループを作らない

リレーのレグは `RelayLegLease` がリースを押し出し続ける。**パブリックアドレスには
要らない。** サーバ側計画 §12.8 が明言している：

> パブリックアドレスにその関門は無い — 台帳に入れてはならないからである。
> したがってソケットは CONNECT-UDP セッションと同じだけ生き、リースは**次の
> チケットを出すかどうかの条件**としてしか効かない。

**押しても何も動かないレバーを付けない。** 付ければ「リースを更新しているのだから
生きている」という誤った安心が生まれる。

### 4.3 では何が切るのか

- **CONNECT-UDP セッションが切れたとき**（QUIC が切れた、DP が落ちた、プロセスが
  終わった）
- **Endpoint が失効したとき** — 失効ストリームに乗るので、次のチケットは出ない。
  ただし**動いているセッションはその場では切れない**（サーバ側 §12.8）

再接続は「チケットを取り直して bind し直す」であり、それが同時に**割当が変わって
いないかの確認**になる（§1.2 の「台帳を引き直す」）。

---

## 5. DP の退役はアドレスを変える

サーバ側計画 §5 が正直に書いているとおり、**パブリックアドレスは移せない**。
リレーのレグは移せるが、これは文字通りその DP の IP である。

クライアントにできるのは 2 つだけ：

1. **気づく** — **再チケットしたときだけ**。サーバはそのたびに台帳を引き直すので、
   前回公開したアドレスと比べれば分かる（§3.3）。bind しているあいだは分からない
2. **言う** — 古いアドレスは死んだ、と利用者に伝える

**自動で吸収しようとしない。** 外に配ったアドレスは、こちらの知らないところで
DNS や設定ファイルに書かれている。黙って新しいアドレスに移ると、「繋がらない」が
**どこにも記録されないまま**利用者の外側で起きる。

## 6. 段取り

| # | やること | 出口 |
| --- | --- | --- |
| **P0** ✅ | DTO と 3 つの API 呼び出し、`RelayRole::Public`、`session_id` を `Option` に（§2.1） | **チケットが読める** |
| **P1** ✅ | `open_public_bind_session`（§2.2）。セッション ID と `Prefer-Temporary` を**付けない** bind（§3.7） | **名指された DP に bind できる** |
| **P1b** ✅ | 転送先ソケットの上限（§3.5） | **公開しても増え続けない** |
| **P2** ✅ | `PublicEndpoint`：create → ticket → bind、`Idempotency-Key`、bind 試行ごとの再チケット（§2.3） | 公開したサービスが外から届く |
| **P3** ✅ | 前回公開したアドレスとの比較（§3.3）、`role` の検査（§3.2）、退役の見え方（§5） | **アドレスが変わったことが分かる** |
| **P4** ✅ | `isekai-p2p/examples/` にサンプルを置く（§6.1） | **外から誰かが来るところまで見える** |

**P1b は P2 の前に要る。** §3.5 は「公開した瞬間から、誰でもこちらのソケットを
増やせる」であって、後回しにできる種類の不足ではない。初版は P1 で止めてよいと
書いたが、**bind できた時点で外から届く**以上、上限の無いまま止めるのは
「動くが晒されている」状態で止めることになる。

### 6.1 P4 — `channel-masque/examples/masque-h3-server.rs` を下敷きにする

**置き場所は `isekai-p2p/examples/`**（このクレートに `examples/` はまだ無い。
`camera-core/examples/` が先例）。

下敷きにするのは `channel-masque` のこの例が、**この計画でいちばん確かめにくい
ところをすでに実演しているから**である。

```text
外の QUIC/H3 クライアント          ← 不特定多数。これが「相手」
     ↕ QUIC（公開アドレス宛）
DP がその ip:port で bind したソケット
     ↕ CONNECT-UDP（MASQUE）
このプロセス（MasqueClient）
     ↕ ローカル UDP（ループバック）
このプロセスが動かす quinn の H3 サーバ
```

`masque-h3-server` との違いは**上端だけ**である。あちらは MASQUE proxy に
ダイヤルして一時アドレスをもらう。こちらは **Listener を作り、チケットを取り、
名指された DP にダイヤルして、自分のポートをもらう** — つまり §1 と §2 が足すもの
だけが差し替わり、下半分（ローカル UDP への転送、`events` の読み方）はそのまま
使える。

**サンプルにする理由は 2 つある。**

1. **`portal-server` に先に入れると、確かめたいものが確かめられない。** portal は
   TCP / UDP の転送を持つが、外から来る不特定多数に晒す口ではない。P4 で見たいのは
   「公開アドレス宛のパケットが本当にこのプロセスまで来るか」で、それには**外から
   叩けるサーバ**がいる。H3 サーバはそれ自身がクライアントを持っている
2. **§3.5 が見えるのはここだけである。** 送信元が増えるとソケットが増える、は
   相手が 1 つの経路では再現しない。サンプルは `NewRemoteHost` を出すので、
   **上限（P1b）が効いているかを目で確かめられる**

既存の例と同じく、引数は `--target`（Listener の宛先）と proxy の指定にする。
**`--jwt` に当たるものは Endpoint Token で、これは `isekai-p2p` が持っている** —
サンプルが手で組み立てるものではない。

> **実装では H3 ではなく UDP echo にした。** `masque-h3-server` の下半分は
> **マネージド証明書**（`isekai-link-utils`、サーバ側のクレート）に依存しており、
> `isekai-p2p` の example がそこへ手を伸ばすのは筋が違う。P4 が見たいのは
> 「**外から誰でも叩ける**」ことで、`nc -u` で叩ける echo はその性質を満たし、
> 証明書の段取りを一切持ち込まない。**§3.5 の可視化も echo のほうが直接的**で、
> 送信元ポートを変えて送るだけでソケットが増えるのが見える。
>
> **実配備で通した（2026-09-21）。** `link.isekai.tools` に対して公開し、外から叩いた。
>
> ```text
> address : 161.33.189.228:19556
> sender=42.125.235.37:52821 → forwarding_socket=127.0.0.1:50502
> sender=42.125.235.37:56755 → forwarding_socket=127.0.0.1:58833
> ```
>
> 後者がこの段の本題である。**送信元 1 つにつきソケット 1 つ**——相手が 1 人の
> レグでは決して現れない振る舞いが、送信元と対にして観測できた。P1b が上限を
> かけているのはこれである。
>
> **サンプルが見つけたものが 2 つある。** どちらも「動かしてみるまで分からない」
> 種類で、P4 を置いた理由そのものだった。
>
> - **転送先のサービスには送信元が見えない。** 見えるのは転送ソケットの
>   ループバックアドレスだけで、誰が送ってきたかは `NewRemoteHost` にしか無い。
>   対応を出すのはこの経路だけである
> - **`main` から return するのは終了ではない。** msquic の `RegistrationClose`
>   が残ったハンドルを待って止まらない——最初は core dump、次は Ctrl-C 後の
>   ハング。`drain_msquic` のあと `_exit` する、というワークスペースの
>   バイナリと同じ形が要る

> **`portal-server` への統合はこの計画の外に出す。** サンプルが通れば口は
> 固まるので、そのあとで足すほうが順序として正しい。

## 7. テスト

**ヘッダは実装の内部ではなく、サーバとの契約である**（§0.2、§3.7）。要求を見て
確かめる：

- `Seera-Signaling-Session-Id` を**送らない**
- `Seera-Prefer-Temporary-Public-Address` を**送らない**
- `relay` があるときだけ `Seera-Relay-Ticket` を送る

残り：

- `relay` が無ければ CP にダイヤルする（§3.1）。`relay` があればそのホストへ
- `session_id` の無い `relay` が読める（§2.1）。**これが読めないと何も始まらない**
- `role` が `public` でないチケットは bind に進まない（§3.2）
- **前回公開したアドレスと違うチケットが返ったら、呼び出し側に見える**（§3.3、§5）
- 送信元アドレスが N 個を超えたとき、ソケットが N を超えない（§3.5）。
  **サンプルがこれを目で見られる形にする**（§6.1）
- 期限切れ Listener の `/ticket` が `404` を返したとき、「作り直せ」と言う
- 作り直しが `Idempotency-Key` を送る。**送らなければ 8 回で `429` に当たる**（§2.3）
- `403 insufficient-permission` が、足りない権限の名前とともに出る（§3.4）

## 8. この計画で解かないもの

1. **`portal-server` からの利用**（§6.1）。サンプルで口が固まってからにする
2. **アドレスの移行**（§5）。サーバ側が「破壊的」と決めたものを、クライアントが
   無停止にすることはできない
3. **緊急ブロック**（サーバ側 §8）。DP に届いていない。クライアント側の話ではないが、
   **この経路のトラフィックは止まらない**ことは知っておく必要がある
4. **マネージド証明書の名前**（サーバ側 §6）。`hostname` は応答が言うとおりに使う
5. **到達性の能動確認**。§0.3 のとおり、無音が正常な経路では作れない
6. **DP が実際に取ったポートの確認**（§3.3）。DP は広告アドレスを返すので、
   bind したポートはクライアントから見えない。CP 同居経路だけは例外（§3.7）
7. **複数 region への同時公開**。割当は `sub` ごとに 1 つで永続（§7.7.1）という
   サーバ側の約束がそれを許さない
