# Public UDP Listener に繋ぐ

サーバ側のフェーズ 5（`dataplane_separation_phase5_plan.md`）で、パブリック
アドレスは **CP の資源から DP の資源になった**。台帳は `(dp_id, port, sub)` で、
IP は持たない。したがって、

> そのアドレスでバウンド UDP セッションを張れるのは**その DP だけ**である。

いまクライアントは CP にダイヤルしている。本書はその差を埋める計画である。

---

## 0. 結論を先に

### 0.1 これは「新しい接続方式」ではない

必要なものは**すでに全部ある**。リレーのレグ（§8.14）が、チケットを取り、名指された
DP へ CONNECT-UDP を出し、バウンドしたソケットの上でデータグラムを運ぶ、という形を
作った。パブリックアドレスはその**同じ形の、相手のいない版**である。

| | リレーのレグ | パブリックアドレス |
| --- | --- | --- |
| 何を bind するか | DP のループバック（30000 番台） | **利用者の公開 `ip:port`** |
| 誰が認可するか | CP 署名のチケット | **同じチケット**（`role: public`） |
| ランデブー | ある（2 本が出会う） | **無い**（1 本きり） |
| セッション ID ヘッダ | 送る | **送ってはならない**（§2.2） |
| リースの効き方 | パケットごとに関門がある | **次のチケットを出すかどうかだけ**（§4.3） |

**だから新しい寿命管理も新しい資格情報も作らない。** 作ると、単回使用も失効も
もう一度正しく実装することになる。

### 0.2 いちばん危ないのは「ヘッダを 1 つ足す」こと

DP の振り分けは**要求の形**で決まる（`serve.rs`、phase-5 §4.2）。

```
Seera-Signaling-Session-Id あり → レグとして扱う（role は initiator / target のみ）
        同ヘッダ無し＋チケットあり → パブリックアドレスとして扱う（role は public のみ）
                          どちらも無し → この DP のものではない
```

既存の `open_bind_session` は `seera-signaling-session-id` を**必ず付ける**
（`bind.rs:365`）。これを流用して `role: public` のチケットを持ち込むと、**レグの
経路に入って拒否される**。サーバ側が意図してそう作っている（攻撃者がヘッダを添えて
公開アドレスをエッジプールへ入れるのを防ぐため）ので、**こちらが合わせる**。

### 0.3 クライアントから見た「相手がいない」の意味

リレーのレグには相手がいて、**届かなければ気づく**（`InboundActivity`）。
パブリックアドレスの相手は不特定多数で、**一度も誰も来ないことが正常**である。

したがって「動いているか」をこちら側の観測で判定できない。判定材料は 2 つだけ：

1. **CONNECT-UDP が確立したこと**（bind が成功した）
2. **DP が報告してきた広告アドレス**が、CP が言ったものと一致すること（§3.3）

**ヘルスチェックを発明しない。** 無音を異常と読む仕組みは、この経路では必ず誤報する。

## 1. サーバが提供している口（実装済みの事実）

計画書ではなく実装から取る。

### 1.1 作成 — `POST /v1/public-listeners`

```jsonc
{ "listener_id": "ul_…", "owner_endpoint": "ep:C", "visibility": "public",
  "public_address": { "hostname": "…", "ip": "203.0.113.9", "port": 10042 },
  "region": "ap-northeast-1",          // 決まった region。要求の echo ではない
  "relay": { "masque_uri": "https://dp1…:8443/…", "dp_id": "dp1…",
             "spki_sha256": ["…"] },   // 登録済み DP のときだけ
  "status": "active", "created_at": "…", "expires_at": "…" }
```

- **`ticket` は入らない。** 作成は冪等で、`Idempotency-Key` の応答キャッシュは 24 時間
  残る。単回使用・寿命 45 秒のチケットを再送に返すわけにいかない、という判断が
  サーバ側で下されている（実装のコメントが明言）。計画書 §4.3 の「同梱は最適化」は
  **採られなかった**
- **`relay` が無いのは「CP 自身のデータパス」という意味**である。その bind は
  セッション自身の Endpoint Token で認可され、チケットは要らない

### 1.2 チケット — `POST /v1/public-listeners/{id}/ticket`

**これが主経路である。** `relay` と `ticket` を返す。応答の形は作成と同じなので、
クライアントは 1 つの型で読める。

```jsonc
{ …, "relay": { … }, "ticket": { "ticket": "<JWT>", "role": "public",
                                  "expires_at": "…", "lease_expires_at": "…" } }
```

**新しい認可判断はここで行われない。** Listener を持っていることが資格で、それは
作成時に決まっている。ここで足されるのは**鮮度・単回使用・DP の名前**である。

> **台帳を引き直している。** サーバはこのとき「行が憶えている値」ではなく
> **いまその利用者が保有しているポート**を読む。解放・再割当が起きていれば、
> 返るアドレスは作成時と違う。§3.3 と §5 はこの事実の上に立つ。

### 1.3 削除 — `DELETE /v1/public-listeners/{id}`

`204`。owner 以外は `404 listener-not-found`。

### 1.4 bind — CONNECT-UDP

| | 値 |
| --- | --- |
| 宛先 | `relay.masque_uri` のホスト（無ければ設定された proxy） |
| パス | ワイルドカードの bind パス（`/.well-known/masque/udp/*/*/`） |
| 認証 | Endpoint Token + PoP（レグと同じ） |
| `Seera-Relay-Ticket` | **`relay` があるとき必須** |
| `Seera-Signaling-Session-Id` | **付けない**（§0.2） |

DP は**ポート番号だけ**をチケットから取り、自分の `--public-bind-ip` に bind する。
そして**広告アドレス**（bind したものではない）を `proxy-public-address` として
返す。クライアントには `MasqueClientEvent::PublicAddresses` として届く。

## 2. クライアント側に足すもの

### 2.1 `isekai-p2p-core` — ワイヤ

| # | もの | 置き場所 |
| --- | --- | --- |
| 1 | `PublicListener` / `PublicAddress` の DTO、`RelayRole::Public` | `proxy.rs` |
| 2 | `create_public_listener` / `delete_public_listener` / `issue_public_listener_ticket` | `proxy.rs` |
| 3 | `open_public_bind_session` — セッション ID ヘッダを**付けない**バウンド UDP | `bind.rs` |

**`RelayRole` に `Public` を足すのは非互換の変更である。** いまの列挙は
`initiator` / `target` の 2 つで、未知の値は serde が拒否する。足さなければ
`role: "public"` のチケットを**読むことすらできない**。

### 2.2 `open_bind_session` を分けるか、引数で分けるか

**分ける。** 引数 1 つの違いに見えるが、意味が違う。

| | 一緒にする | 分ける（本案） |
| --- | --- | --- |
| セッション ID | `Option<&str>` | 型に現れない |
| 間違えたとき | **レグの経路に入り拒否される**。原因はヘッダ 1 つで、エラーには出ない | そもそも渡せない |
| `forward_to` | 同じ | 同じ |
| 共有 | コネクタ・PoP・チケット層は共通の下請けに | 同上 |

§0.2 の落とし穴は「うっかり付ける」ではなく「**既存の関数を流用すると必ず付く**」
形をしている。型で防げるものを実行時のエラーに任せる理由がない。

### 2.3 `isekai-p2p` — 寿命

`PublicEndpoint`（仮称）が持つのは 3 つだけ：

```
create（1 度）→ ticket（毎回）→ bind（セッションのあいだ）
```

- **再接続のたびにチケットを取り直す。** 45 秒の紙を保持しても意味がない
- **リースの更新ループは作らない**（§4.3）
- **Listener の TTL は延ばせない。** 最大 86,400 秒で、切れたら作り直し
  （`/ticket` は期限切れの Listener に `404` を返す）

## 3. 落とし穴

### 3.1 `relay` が無いときに DP を推測しない

`RelayInfo.dp_id` について `bind.rs` が既に書いていることが、そのまま当てはまる：

> **URI の形ではなく、明示の signal を見る。** 登録済み relay が無いとき CP は
> `--p2p-relay-base-url` から URI を組み立てるので、その既定はハードコードされた
> 本番ホストである。「authority があるから行く」と読むと、開発用クライアントの
> Endpoint Token と PoP が誰も設定していない origin へ飛ぶ。

パブリックアドレスでも同じ規則にする。**`relay` が無ければ、設定された proxy に
ダイヤルし、チケットは付けない。**

### 3.2 チケットの `role` を検査する

CP が `role: public` を返すはずの場所で `initiator` が返ってきたら、それは
**こちらの要求が意図と違う口に届いている**。黙って bind に進むと、DP 側の
振り分け（§0.2）で拒否され、原因はヘッダとロールの組み合わせという**こちらから
いちばん見えにくい形**で現れる。取り出した時点で確かめる。

### 3.3 広告アドレスは 2 か所から来る。突き合わせる

| 出どころ | 何を言っているか |
| --- | --- |
| `public_address`（CP の応答） | 台帳が「あなたのポート」と言っている値 |
| `PublicAddresses`（DP の報告） | **実際に bind した DP が広告する値** |

一致するのが正常である。**食い違ったら、それは DP がアドレスを変えたか、割当が
移ったかのどちらか**で、外に配ってある `ip:port` が死んでいる（§5）。

- **どちらを信じるか**: DP の報告。実際にパケットを受けるのはその DP である
- **黙って進まない**: `warn` で両方を出す。この経路の利用者は「外の誰かに
  アドレスを配った人」なので、変わったことを知らせないのは最も高くつく

### 3.4 権限

`udp-listen:public:create` / `:delete` が Endpoint Token に要る。足りなければ
`403 insufficient-permission`。agent モードのように `Narrowing` で権限を絞る
呼び出し側は、**この 2 つを落とすと Listener が作れない**。

### 3.5 `target` は送るが、Proxy は解釈しない

仕様 §7.7.3 が「未実装」から「**実装しない**」に書き直された。`target` は
owner 自身が転送する宛先のメタデータである。クライアントは、

- 作成要求には載せる（宣言・可視化のため）
- **実際の転送は自分でやる** — バウンド UDP セッションの `forward_to` がそれ

の 2 つを別のものとして扱う。片方だけ設定して繋がらない、が起きやすい場所である。

## 4. 寿命

### 4.1 3 つの時計が別々に動く

| | 長さ | 切れたら |
| --- | --- | --- |
| チケット | 45 秒 | 取り直す。**保持する価値が無い** |
| リース | 数十分 | **セッションは切れない**（§4.3） |
| Listener | 最大 86,400 秒 | **作り直し**。`/ticket` が `404` |

### 4.2 更新ループを作らない

リレーのレグは `RelayLegLease` がリースを押し出し続ける。**パブリックアドレスには
要らない。** サーバ側計画 §12.8 が明言している：

> パブリックアドレスにその関門は無い — 台帳に入れてはならないからである。
> したがってソケットは CONNECT-UDP セッションと同じだけ生き、リースは**次の
> チケットを出すかどうかの条件**としてしか効かない。

**押しても何も動かないレバーを付けない。** 付ければ「リースを更新しているのだから
生きている」という誤った安心が生まれる。

### 4.3 では何が切るのか

- **CONNECT-UDP セッションが切れたとき**（QUIC が切れた、DP が落ちた、プロセスが
  終わった）
- **Endpoint が失効したとき** — 失効ストリームに乗るので、次のチケットは出ない。
  ただし**動いているセッションはその場では切れない**（サーバ側 §12.8）

再接続は「チケットを取り直して bind し直す」であり、それが同時に**割当が変わって
いないかの確認**になる（§1.2 の「台帳を引き直す」）。

---

## 5. DP の退役はアドレスを変える

サーバ側計画 §5 が正直に書いているとおり、**パブリックアドレスは移せない**。
リレーのレグは移せるが、これは文字通りその DP の IP である。

クライアントにできるのは 2 つだけ：

1. **気づく** — 再チケット時に `public_address` が変わる、または §3.3 の食い違い
2. **言う** — 古いアドレスは死んだ、と利用者に伝える

**自動で吸収しようとしない。** 外に配ったアドレスは、こちらの知らないところで
DNS や設定ファイルに書かれている。黙って新しいアドレスに移ると、「繋がらない」が
**どこにも記録されないまま**利用者の外側で起きる。

## 6. 段取り

| # | やること | 出口 |
| --- | --- | --- |
| **P0** | DTO と 3 つの API 呼び出し、`RelayRole::Public`（§2.1） | **チケットが読める** |
| **P1** | `open_public_bind_session`（§2.2）。セッション ID を付けない bind | **名指された DP に bind できる** |
| **P2** | `PublicEndpoint`：create → ticket → bind と、再接続時の再チケット（§2.3） | 公開したサービスが外から届く |
| **P3** | 突き合わせと警告（§3.3）、`role` の検査（§3.2）、退役の見え方（§5） | **アドレスが変わったことが分かる** |
| **P4** | `portal-server` から使えるようにする（`--publish` 相当） | 運用者が使える |

**P1 で止めても価値がある。** そこまでで「DP のアドレスに bind できる」が成立し、
残りは寿命と見え方の話である。

## 7. テスト

- **セッション ID ヘッダを付けない。** これは実装の内部ではなく**サーバとの契約**
  なので、要求ヘッダを見て確かめる
- `relay` が無ければ設定された proxy にダイヤルし、チケットを送らない（§3.1）
- `relay` があればそのホストにダイヤルし、チケットを送る
- `role` が `public` でないチケットは bind に進まない（§3.2）
- CP の `public_address` と DP の報告が食い違ったら警告し、**DP の値を採る**（§3.3）
- 再チケットで `public_address` が変わったら、それが呼び出し側に見える（§5）
- 期限切れ Listener の `/ticket` が `404` を返したとき、「作り直せ」と言う
- `403 insufficient-permission` が、足りない権限の名前とともに出る（§3.4）

## 8. この計画で解かないもの

1. **アドレスの移行**（§5）。サーバ側が「破壊的」と決めたものを、クライアントが
   無停止にすることはできない
2. **緊急ブロック**（サーバ側 §8）。DP に届いていない。クライアント側の話ではないが、
   **この経路のトラフィックは止まらない**ことは知っておく必要がある
3. **マネージド証明書の名前**（サーバ側 §6）。`hostname` は応答が言うとおりに使う
4. **到達性の能動確認**。§0.3 のとおり、無音が正常な経路では作れない
5. **複数 region への同時公開**。割当は `sub` ごとに 1 つで永続（§7.7.1）という
   サーバ側の約束がそれを許さない
