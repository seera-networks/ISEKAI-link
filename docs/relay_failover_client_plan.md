# DP が落ちたときにセッションを移す — クライアント側

`relay_failover_plan.md`（サーバ側）が決めているのは**移してよい条件**と**移し方**で
ある。§7 の変更一覧は全て CP 側で、その末尾が「**DP 側の変更もワイヤ変更も無い。
`dp` は 1 台のままで、応答にフィールドが増える**」と書いている。

本書は、その増えたフィールドを**誰が読み、脚をどう張り替えるか**を決める。

> 以下、`§n` は本書の節を指す。サーバ側の設計書を指すときは
> 「**サーバ側 §n**」と書く。

---

## 0. 結論を先に

サーバ側の判定はすべて **`/ticket` の中**にある。CP は自分から押し付けてこない
（`relay_changed` イベントは target に**早く**伝えるためのもので、移動そのものの
経路ではない）。**移動は、当事者が `/ticket` に来て初めて起きる。**

**そして initiator と target は、この件に関してまったく違う状態にある。**
一括りに論じると両方を取り違えるので、最初から分ける。

| | 脚の死に気づくか | 気づいたら | 張り替えられるか |
| --- | --- | --- | --- |
| **initiator** | **気づかない**（§1.1） | — | socket の作り直しが要る（§3.1） |
| **target** | **3 秒で気づく**（§1.2） | `Unbound` を出し、**`spent` に入れて二度と張らない** | **既存の番人に止められる**（§1.2） |

### 0.1 いま case A で何が起きるか — 「遅れて移る」ではない

サーバ側の case A（ノードの退役）は実装済みで、`/ticket` は**成功する**。CP は行の
`dp_id` を書き換え、新しい DP を名指した `relay` を返す。

**しかしクライアントはそれを読まない。** そして `RelayLegLease` は
`relay_origin` を **spawn 時に固定**している（#208 で、脚と `/renew` の宛先を
一致させるために意図的にそうした）。だから更新は**退役した DP に送られ続ける**。

```
/ticket   → CP、成功。新しい DP を名乗る（読まれない）
/renew    → 古い DP。届かない → Retry を 30 秒ごと
            → lapses_at → leg.cancel()
```

**結果は「10 分遅れて移る」ではなく「脚が死ぬ」である。** 初版はここを取り違えて
いた。移動の実装が入るまで、case A は**壊れたままである**。

### 0.2 case B は、いまのクライアントからは起こせない

サーバ側 §4.4 の B は「両当事者がチケット TTL + 許容ずれ（**既定 50 秒**）のうちに
再チケットに来たこと」を、両方のレグが死んだ証拠とする。

initiator は気づかないので来ない。target は気づくが、来るのではなく
**`spent` に入れて降りる**。**どちらも窓に入らない。**

## 1. いまの検知能力 — 両側で違う

### 1.1 initiator は気づかない

`open_connect_relay` が回すタスクは、レグを張ったあと
**`session_shutdown.cancelled().await` で待つだけ**である（`bind.rs`）。DP への QUIC が
壊れてもこのタスクは待ち続け、`ConnectRelay` は生きているように見える。

**症状は「転送が黙る」。** 接続は張れていて、バイトが流れなくなる。

### 1.2 target は 3 秒で気づき、そして降りる

`poll_signaling` は `guard.handle.is_finished()` を見て、終わった脚を `unbind` し、
`SignalingEvent::Unbound` を出す。周期は `SIGNALING_POLL_INTERVAL = 3 秒`
（イベントストリームがあるときは 60 秒が保険）。**気づくのは速い。**

問題はその次である。

```rust
state.spent.insert(id.clone());
```

そして張り直しのループは `spent` に入っている接続を `continue` で飛ばす。
**`spent` が消えるのは、CP がその接続を列挙しなくなったときだけ**である
（`forget_gone` の `retain`）。

**退役した DP のセッションを CP は列挙し続ける** — 移すつもりなのだから当然である。
つまり **`spent` は永久に消えず、target の脚は二度と張られない。**

**P3 を実装しても、この番人に止められる。** 初版はこの存在を書いていなかった。

## 2. サーバ側に既に入っているもの（実装から読んだ）

**仕様書ではなくハンドラを読んだ。** ISEKAI-identity#35 の教訓である。

- **`/ticket` の応答は `relay` を持つ。** 形は `connect` の `relay` と同じ
  （`masque_uri` / `session_id` / `dp_id` / `spki_sha256`）で、
  `isekai-p2p-core` の `RelayInfo` がそのまま使える
- **常に返る。** ハンドラのコメントがそう書いている:

  > Always, not only when the session has moved: a client that has to read
  > "it is here if I say so, otherwise where you were" has two paths, and one
  > of them is the one nobody tests.

  **クライアントは「移動したか」を分岐で判断しない。毎回、応答が名指す DP に合わせる。**
- **case A は実装済み。** `relay_history` の列と条件付き更新も入っている
- **case B は見当たらない。** サーバ側 §8 の「**2 で止める判断はありうる**」の
  とおりと思われる

## 3. 連続性の代償 — `local_addr` は両側にある

初版は「listener 側はこの問題が軽い」と書いた。**誤りである。両側にあり、
target 側のほうが波及が広い。**

### 3.1 initiator 側

`ConnectRelay::local_addr` は、アプリケーションが送る先のローカル UDP アドレスで、
**脚を張るときに作った socket のもの**である。素直に張り替えると番号が変わり、
アプリは古い番号へ送り続ける。

> **初版の根拠は的外れだった。** `RelayOptions { unconnected, registration }` と
> 「msquic の binding を共有できるか」は**ネットワーク側の binding**の話である。
> ここで問題になっている socket は `local_bind` に渡される
> **`127.0.0.1:0` の素の `tokio::net::UdpSocket`** で、`initiator.rs` の doc コメントが
> そう書いている。msquic は関係が無い。**難しさは socket の型ではなく §3.3 にある。**

### 3.2 target 側 — こちらのほうが重い

target の転送 socket は `0.0.0.0:0` に張って `forward_to` へ connect したもので、
**その `local_addr` が、アプリから見た「ピアの送信元アドレス」**である。
張り替えれば変わる。

**そして `camera-core` の `video.rs` はその組で `relay_path` を判定している。**
アドレスが変われば、**新しいリレー経路が直接経路として分類される。** 経路の統計も
表示も、そこから狂う。

**「listener 側は軽い」は逆だった。**

### 3.3 socket を持ち回すことと、脚を重ねることは両立しない

初版は「新しい脚が張れてから古いのを畳む」と書いた。**socket を持ち回すなら
できない。**

`run_bridge(socket: Arc<UdpSocket>, ...)` は socket を持って `recv_from` で回る。
**同じ socket に 2 つの bridge が生きていると、アプリの上り方向が非決定に割れる**
（どちらが受け取るか決まらない）。さらに `last_src` はタスクごとなので、
**新しい bridge はアプリが次に送ってくるまで下り方向を捨てる。**

したがって順序は逆になる。

```
古い bridge を止める  →  socket は保持  →  新しい脚に渡す  →  新しい bridge を回す
```

**その間、通信は落ちる。** サーバ側 §10-1 が「フェイルオーバーであって無瞬断では
ない」と書いているとおりで、**クライアント側でもそれは避けられない。**
やるべきは短くすることであって、重ねることではない。

## 4. クライアントがやること

| # | やること | どちら側 |
| --- | --- | --- |
| 1 | `RelayTicket` に `relay: Option<RelayInfo>` を足して**読む** | 両方 |
| 2 | **脚の死を検知する** | **initiator のみ**（target は既に気づく） |
| 3 | **`spent` の番人を、張り替えを許す形に直す** | **target のみ** |
| 4 | 応答の DP が今と違えば**脚を張り替える**。接続は終えない | 両方 |
| 5 | `relay_changed` を購読で受ける | target |

**2 と 3 は別々の欠落で、別々の側にある。** 初版は 2 だけを両側の問題として
書いていた。

### 4.1 脚の死をどう知るか（initiator）

`MasqueClient` を回すタスクが待つのをやめ、**接続の終了を上へ返す**。
`ConnectRelay` に完了を観測する口を付ける（`BindSession::events` に載せる案は
使えない — `drive_bind_session` が全て消費していてアプリケーションに届かない）。

**沈黙を死と読んではならない。** `InboundActivity` の「最近バイトが来ない」は
「相手が送っていない」でもある。portal の転送は待ち受けが普通で、カメラは配信して
いないかもしれない。沈黙で動くと、健全な DP から自分の都合でセッションを剥がそうと
する — サーバ側 §4.3 がクライアント側で再演される。

### 4.2 `spent` をどう直すか（target）

`spent` は「この接続は試して終わった、CP が列挙をやめるまで放っておく」ための
番人である。**それ自体は正しい** — 無ければ死んだ脚を 3 秒ごとに張り直し続ける。

必要なのは「**張り替えてよい理由がある**」を表現することで、**番人を外すことでは
ない。** 具体的には、`Unbound` の原因を「脚が終わった」と「接続が消えた」で
区別し、前者かつ `/ticket` が新しい DP を名乗ったときだけ `spent` から戻す。

**理由なしに戻すと、張り直しの暴走に戻る。**

### 4.3 群れになる

**DP が 1 台落ちれば、そこに載っていた全セッションが同時に気づく。** 全員が同じ
瞬間に `/ticket` を叩けば CP に山が立つ。

- 再チケットに**短いランダム遅延**を入れる
- ただし **case B の窓（50 秒）より十分小さく**。遅らせすぎると両者がそろわず、
  移動そのものが起きない。**この 2 つの要求が上下から挟む**のが、この値の決め方である

## 5. 移動を実際にやる

```
（initiator）脚の死を検知 / （target）脚の終了を検知
  → 短いランダム遅延
  → /ticket
      → 応答の relay.dp_id を見る
          → 今と同じ  : 同じ DP に張り直す
          → 違う      : 新しい DP に張る
          → relay 無し: 登録 relay の無い配備。proxy_url に張る
  → 古い bridge を止める（§3.3。重ねられない）
  → socket を保持したまま新しい脚を張る
  → lease ループを新しい origin で回し直す
```

### 5.1 上限と、あきらめ方

サーバ側は `relay_history` で戻りを防ぎ、**3 台使い切ったらフェイルオーバーは終わり**
とする（サーバ側 §5.1）。そのときクライアントは `connection-closed` 相当を受け取る。

**それはアプリケーションに見えなければならない。** initiator は `ended` トークンで
伝わる。**target は伝わらない** — `RelayLegLease::spawn` に渡している 2 つの
トークンはどちらも使い捨ての `CancellationToken::new()` である。
**target 側に伝える口を作る必要がある**（`SignalingEvent` に足すのが素直）。

### 5.2 lease ループとの関係

`RelayLegLease` は既に `/ticket` を叩き、その応答で lease を延ばしている。
**移動の検知はそこに同居させるのが自然である** — 同じ応答を読むので往復が増えない。

そして §0.1 のとおり、**`relay_origin` の固定を解く必要がある**。#208 は脚と
`/renew` の宛先を一致させるためにそれを固定した。フェイルオーバーは
「**脚が動いたら宛先も動く**」を足すのであって、一致の要求を緩めるのではない。

## 6. 段取り

| # | やること | 出口 |
| --- | --- | --- |
| **P0** | `RelayTicket` に `relay` を足して読む。**記録するだけ**、張り替えない | 実配備で「退役時に CP が別の DP を名指すこと」が観測できる。**移動の実装前に、サーバが本当に移すかを確かめられる** |
| **P1** | initiator の脚の死を検知（§4.1）。**まだ再チケットしない**、記録だけ | 「どれくらいで気づけるか」が数字で出る（§7-3） |
| **P2** | **socket を脚の外へ出し、bridge を止めて張り直せるようにする**（§3.3）。同じ DP への張り直しで検証 | **`local_addr` が変わらないことと、落ちる時間**が測れる。移動先が変わらないので、切り分けが 1 つで済む |
| **P3** | target の `spent` に「張り替えてよい」を足す（§4.2） | target が張り直せるようになる |
| **P4** | 検知 → 遅延 → 再チケット → 別 DP へ張り替え（§5） | **case A が直る。case B が到達可能になる** |
| **P5** | `relay_changed` の購読（§4-5）と、上限の通知（§5.1） | 早くなる。黙って死なない |

**P0 と P1 は観測だけで、単独で入れられる。** サーバ側の case B がまだ無いので、
**P4 を入れても効くのは case A である** — そこは正直に見積もる。

**P2 を P3・P4 より前に置いた**のは、`local_addr` の連続性が取れなければ以降が
意味を持たないからである。同じ DP への張り直しなら移動の判定を巻き込まずに試せる。

## 7. 確かめていないこと

1. **socket を保った張り替えで、落ちる時間がどれだけか**（§3.3）。重ねられない以上
   ゼロにはならない。P2 が数字を出す
2. **direct path と両立するか。** 移行済みのセッションで脚を差し替えたとき、
   `observed` の再報告が直接経路の候補を壊さないこと。§3.2 の `relay_path` 判定は
   ここにも関わる
3. **QUIC の切断がどれくらいで上がってくるか。** msquic の idle timeout は 30 秒、
   keepalive は 10 秒（`transport.rs`）。**最悪 30 秒気づかない可能性がある**が、
   case B の窓は 50 秒なので、両者の検知が 30 秒以内にそろえば間に合う — **ぎりぎり
   である**。P1 が数字を出す
4. **サーバ側の case B が入るのか。** 入らなければ P4 の価値は case A だけになる

## 8. この計画で解かないもの

1. **無瞬断ではない**（サーバ側 §10-1）。§3.3 のとおり、socket を持ち回す以上
   クライアント側でも重ねられない
2. **片側だけのレグ障害**（case C）。意図的に移さない設計であり、そのときは
   アプリケーションのやり直しに戻る
3. **CP が落ちているとき**。唯一の経路が `/ticket` である
4. **移動回数の上限**。使い切ったらやり直し（サーバ側 §5.1）
