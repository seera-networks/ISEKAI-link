# DP が落ちたときにセッションを移す — クライアント側

`relay_failover_plan.md`（サーバ側）が決めているのは**移してよい条件**と**移し方**で
ある。§7 の変更一覧は全て CP 側、§157 は「**DP 側の変更もワイヤ変更も無い。
`dp` は 1 台のままで、応答にフィールドが増える**」と書いている。

本書は、その増えたフィールドを**誰が読み、脚をどう張り替えるか**を決める。

---

## 0. 結論を先に — 移動は CP が決めるが、始めるのはクライアントである

サーバ側の判定はすべて **`/ticket` の中**にある。CP は自分から押し付けてこない
（イベントは §7-6 で「target に**早く**伝える」ためのもので、移動そのものの経路では
ない）。**つまり移動は、当事者が `/ticket` に来て初めて起きる。**

そして今のクライアントは、**lease の半分に一度しか来ない**（`relay_lease.rs`、
既定 1200 秒の半分で約 10 分）。ここから 2 つの帰結が出る。

| 場合 | サーバ側 | 現状のクライアントで |
| --- | --- | --- |
| **A. ノードが退役** | 実装済み | **動く。ただし最大 10 分遅れる** |
| **B. 両当事者が 50 秒の窓のうちに来る** | 設計のみ（§8 が「A で止める判断はありうる」） | **到達できない**（§0.1） |

### 0.1 case B は、いまのクライアントからは起こせない

§4.4 の B は「両当事者がチケット TTL + 許容ずれ（**既定 50 秒**）のうちに再チケットに
来たこと」を、両方のレグが死んだ証拠とする。

**両者は独立した約 600 秒周期で目を覚ます。** 位相は無関係なので、50 秒の窓に
偶然そろう確率は低い。DP がクラッシュしても、両者はそれぞれ次の更新まで眠っている。

**窓に入るには、脚が死んだことに気づいて即座に来る必要がある。** それが本計画の
中心である（§2）。

### 0.2 いまは脚の死に誰も気づかない

`open_connect_relay` / `open_bind_session` が回すタスクは、レグを張ったあと
**`session_shutdown.cancelled().await` で待つだけ**である。DP への QUIC が壊れても
このタスクは待ち続け、`ConnectRelay` / `BindSession` は生きているように見える。

**症状は「転送が黙る」。** アプリケーションから見ると、接続は張れていて、
バイトが流れなくなる。lease の半分が来るまで、誰も何も言わない。

---

## 1. サーバ側に既に入っているもの（実装から読んだ）

**仕様書ではなくハンドラを読んだ。** ISEKAI-identity#35 の教訓である。

- **`/ticket` の応答は `relay` を持つ。** 形は `connect` の `relay` と同じ
  （`masque_uri` / `session_id` / `dp_id` / `spki_sha256`）で、
  `isekai-p2p-core` の `RelayInfo` がそのまま使える
- **常に返る。** ハンドラのコメントがそう書いている:

  > Always, not only when the session has moved: a client that has to read
  > "it is here if I say so, otherwise where you were" has two paths, and one
  > of them is the one nobody tests.

  **クライアントは「移動したか」を分岐で判断しない。毎回、応答が名指す DP に合わせる。**
- **case A（退役・登録抹消）は実装済み。** `relay_history` の列、条件付き更新も入っている
- **case B は見当たらない。** §8 の「2 で止める判断はありうる」のとおりと思われる

---

## 2. クライアントがやること

| # | やること | なぜ |
| --- | --- | --- |
| 1 | `RelayTicket` に `relay: Option<RelayInfo>` を足して**読む** | 応答は既に返っている |
| 2 | **脚が死んだら即座に再チケット**（周期を待たない） | case A を速く、case B を可能にする |
| 3 | **応答の DP が今と違えば脚を張り替える**。接続は終えない | 移動そのもの |
| 4 | `peer.connect.relay_changed` を listener の購読で受ける | target が早く追随する |

**3 が「フェイルオーバー」で、2 がそれを間に合わせる。** 1 が無ければ 3 は判断材料が
無く、4 は無くても動く（遅くなるだけ）。

---

## 3. いちばん難しいのは `local_addr` の連続性

`ConnectRelay::local_addr` は「アプリケーションが送る先のローカル UDP アドレス」で、
**脚を張るときに作った socket のもの**である（`bind.rs`)。

**素直に張り替えると、この番号が変わる。** そしてアプリケーションは古い番号へ
送り続ける。§1 が買うと言った「アプリケーションの状態が続く」は、**ここが変わった
時点で嘘になる。**

取りうる道は 2 つ。

| 案 | 中身 | 評価 |
| --- | --- | --- |
| **socket を跨いで持ち回す** | socket を `open_connect_relay` の**外**で作り、脚に貸す。張り替えても同じ socket を新しい脚に渡す | **本命。** 番号が変わらない。`RelayOptions` は既に registration を外から渡す形を持っており、同じ方向の拡張である |
| 間に一段挟む | アプリは固定のローカルアドレスに送り、内側の脚だけ差し替える | **採らない。** データ経路にコピーが 1 回増える。移動は稀な事象であり、常時の費用を払う理由が無い |

> **socket の共有は既に要求されている。** `RelayOptions { unconnected: true }` は
> 「direct path はこの脚の binding から開く」ためにあり、**socket が脚より長生き
> することは前提として存在する**。フェイルオーバーはその前提を一段強くするだけである。
>
> ただし **direct path と同時に成り立つかは確認が要る**（§7-2）。移行済みの
> セッションで脚だけ差し替えたとき、`observed` の再報告が直接経路の候補を
> 壊さないこと。

**listener 側はこの問題が軽い。** `BindGuard` は接続ごとに作り直す仕組みが既にあり
（`poll_and_bind` が proxy の列挙に追随する）、`forward_to` はアプリの
サービスであって脚のアドレスではない。

## 4. 脚の死をどう知るか

**これが 0.2 の穴を埋める部分で、実装の中身でもある。**

### 4.1 信号は 2 種類あり、意味が違う

| 信号 | 言えること | 使い方 |
| --- | --- | --- |
| **QUIC/H3 の接続が壊れた** | **その DP に届かない。確実** | **即座に再チケット** |
| 一定時間バイトが来ない | 相手が黙っているだけかもしれない | **単独では使わない**（§4.2） |

前者を拾えばよい。いま捨てているのはこちらで、`MasqueClient` を回すタスクが
待つのをやめて、**接続の終了を上へ返す**ようにする。`BindSession` は既に
`events` チャネルを持っているので、そこに載せるのが素直である。

### 4.2 沈黙を死と読んではならない

`InboundActivity` は「最近バイトが来たか」であって、来ないことは
**相手が送っていないこと**でもある。portal の転送は待ち受けが普通で、
カメラは配信していないかもしれない。

**沈黙で移すと、§4.3 がクライアント側で再演される** — 健全な DP から、片方の都合で
セッションを引き剥がす。CP がその申告を受け付けないので実害は小さいが、
**無駄な再チケットを撃ち続ける**ことになる。

### 4.3 群れになる

**DP が 1 台落ちれば、そこに載っていた全セッションが同時に気づく。** 全員が同じ
瞬間に `/ticket` を叩けば、CP に山が立つ。

- 再チケットに**短いランダム遅延**を入れる（数百 ms 〜 数秒）
- ただし **case B の窓（50 秒）より十分小さく**。遅らせすぎると、両者がそろわず
  移動そのものが起きない。**この 2 つの要求が上下から挟む**のがこの値の決め方である
- 失敗したら指数的に下げる。`relay_rtt` の報告で入れたのと同じ考え方
  （到達できない相手に一定間隔で叩き続けない）

## 5. 移動を実際にやる

```
脚の死を検知
  → （短い遅延）
  → /ticket
      → 応答の relay.dp_id を見る
          → 今と同じ  : 同じ DP に張り直す（DP が再起動しただけ）
          → 違う      : 新しい DP に張る
          → relay 無し: 登録 relay の無い配備。proxy_url に張る
  → 新しい脚を張る（socket は持ち回す、§3）
  → 古い脚を畳む
  → lease ループを新しい origin で回し直す
```

**古い脚を畳むのは新しいものが張れてからにする。** 先に畳むと、張り替えに失敗した
ときに何も残らない。§6 のとおりサーバ側では古いレグがリースまで残るので、
こちらが急いで畳んでも得るものは無い。

### 5.1 上限と、あきらめ方

サーバ側は `relay_history` で戻りを防ぎ、**3 台使い切ったらフェイルオーバーは終わり**
とする（§5.1）。そのときクライアントは `connection-closed` 相当を受け取る。

**それはアプリケーションに見えなければならない。** 「移せなくなった」は
「やり直せ」という意味であり、黙って諦めると §0.2 の「黙る転送」に戻る。
`ended` トークンを撃つ。

### 5.2 lease ループとの関係

`RelayLegLease` は既に `/ticket` を叩き、その応答で lease を延ばしている。
**移動の検知はそこに同居させるのが自然である** — 同じ応答を読むので、往復が増えない。

つまり `relay_lease.rs` は「lease を延ばすループ」から
「**脚を生かし続けるループ**」になる。名前もそう変える価値がある。

## 6. 段取り

| # | やること | 出口 |
| --- | --- | --- |
| **P0** | `RelayTicket` に `relay` を足して読む。**変化をログに出すだけ**、張り替えはしない | 実配備で「退役時に CP が別の DP を名指すこと」が観測できる。**移動の実装前に、サーバが本当に移すかを確かめられる** |
| **P1** | socket を脚の外へ出す（§3）。**張り替えても `local_addr` が変わらない**ことを試験 | 連続性の土台。ここが取れなければ以降は意味を持たない |
| **P2** | 脚の死の検知（§4.1）。**まだ再チケットしない**、記録だけ | 「どれくらいで気づけるか」が数字で出る |
| **P3** | 検知 → 遅延 → 再チケット → 張り替え（§5） | **case A が 10 分ではなく数秒になる。case B が到達可能になる** |
| **P4** | `relay_changed` イベントの購読（listener） | target がさらに早く追随する |
| **P5** | 上限に達したときアプリケーションへ返す（§5.1） | 黙って死なない |

**P0 と P2 は観測だけで、単独で入れられる。** サーバ側の case B がまだ無いので、
**P3 を入れても効くのは case A である** — そこは正直に見積もる。

## 7. 確かめていないこと

1. **`local_addr` を保ったまま脚を張り替えられるか**（§3）。msquic の binding が
   複数の H3 接続で共有できるかは、`RelayOptions` の registration 共有が示唆する
   だけで、**やってみていない**。P1 が答える
2. **direct path と両立するか**（§3 の注）。移行済みのセッションで脚を差し替えたとき、
   `observed` の再報告が直接経路を壊さないこと
3. **QUIC の切断がどれくらいで上がってくるか。** msquic の idle timeout は 30 秒、
   keepalive は 10 秒（`transport.rs`）。**最悪 30 秒気づかない可能性がある**が、
   case B の窓は 50 秒なので、両者の検知が 30 秒以内にそろえば間に合う — **ぎりぎり
   である**。P2 が数字を出す
4. **サーバ側の case B が入るのか。** 入らなければ P3 の価値は case A だけになる

## 8. この計画で解かないもの

1. **無瞬断ではない**（サーバ側 §10-1）。移動中のパケットは落ちる
2. **片側だけのレグ障害**（case C）。意図的に移さない設計であり、そのときは
   アプリケーションのやり直しに戻る
3. **CP が落ちているとき**。唯一の経路が `/ticket` である
4. **移動回数の上限**。使い切ったらやり直し（§5.1）
